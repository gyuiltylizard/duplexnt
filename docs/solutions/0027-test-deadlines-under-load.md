# Эмуляторные тесты под нагрузкой: срок проекта и гонка в тесте прерывания (журнал)

Пункт из «Входящих» `docs/bugs.md` (2026-10-29): `test:all` при работающем рядом приложении
(`duplexnt.exe` ×4, CPU ~30 %) роняет по одному случайному эмуляторному тесту — `two-pass` AE6
(укреплён точечно, `52c67b0`), `pass.emulator` AE5 и «DELETE молчит», `blank-backs` AE3/AE4,
`added-pair-mismatch` AE3; повтор файла — зелёный. Плана нет — правка тестовой обвязки, ADR нет.

## Диагноз

Три разные причины под одной картиной.

- **Срок теста короче бюджета ожидания.** Дефолт vitest — 5 с на тест. `until` из
  `test/support/until.ts` ждёт 2000 × 5 мс = 10 с и только потом падает с внятным
  `expect(condition()).toBe(true)`. Под нагрузкой подача эмулятора (`pass.emulator` AE5 — 30
  листов с обрывом и досканированием) или оценки пустоты (`blank-backs`) растягиваются за 5 с, и
  тест падает по таймауту vitest раньше, чем `until` сказал бы, чего не дождался. Точечные
  `20_000` стояли у 9 тестов в четырёх файлах — у тех, где это уже ловили; остальные 100+ тестов
  эмулятора шли на дефолте.
- **Гонка в тесте «прерывание возвращается не позже срока, даже если DELETE молчит».**
  `PassService.interrupt(deadlineMs)` — `Promise.race([run.done, delay(deadlineMs)])`: контракт
  — вернуться не позже срока, а не дождаться записи состояния. Тест сверял
  `passes[0].state === 'interrupted'` сразу после `interrupt(100)`; под нагрузкой цикл прохода за
  100 мс до записи «прерван» не доходил — `expected 'running' to be 'interrupted'`. Проверка
  срока (`< 800 мс`) при этом честная и остаётся.

- **Срок простоя страницы 300 мс в сжатых правилах задания.** Всплыло на гейте `main` после
  первого merge: `blank-backs` «режим сессии заморожен» и `separate-sets` «Остановить» на первом
  листе добавленного прохода» — проход `interrupted` вместо `completed` при 5 и 0 страницах.
  `pageIdleTimeoutMs: 300` — тишина сокета между байтами страницы (`request.setTimeout` в
  транспорте); эмулятор живёт в том же процессе, под нагрузкой заголовки страницы приходят позже
  300 мс (в `separate-sets` сценарий ещё и сам держит паузу `pageDelayMs: 150`), и задание
  обрывается «простоем» без всякого сбоя в сценарии. Блок `FAST` был скопирован в 18 файлов;
  `added-pair-interrupts` под той же нагрузкой уже поднимали до 1500 / 5000 (журнал 0008), файлы
  коррекции — 1500 / 6000, остальные 13 так и шли на 300.

Проверки «повторных оценок нет» через `delay(200)` (`blank-backs` AE6, `added-pair-mismatch`
AE3) — отрицательные и от нагрузки только крепче; не трогались.

## Исправление

- `tooling/test-projects.ts`: поле `testTimeout?` у `TestProject`, у проекта `integration` —
  `20_000` с комментарием-причиной; `vitest.config.ts` пробрасывает поле в проект. Один срок на
  весь эмуляторный прогон вместо точечных: тот же 20 с, что раньше выставляли вручную; тесты
  коррекции (30–120 с) держат свой. `worst-case` — свои сроки в тестах, не задет.
- Точечные `, 20_000)` сняты: `added-pair-interrupts` ×6, `added-pair-mismatch`, `blank-backs`,
  `two-pass` — теперь это дефолт проекта.
- `test/integration/pass.emulator.test.ts`, «DELETE молчит»: сверка срока → `await running` →
  сверка состояния `interrupted`. Второй тест с `Date.now()` в файле («ждали не больше одного
  срока DELETE», `< 1500`) состояние сверяет уже после `await running` — без изменений.
- `test/support/pass-service.ts`: общая `FAST_JOB_LIMITS` (1500 / 5000, остальное как было) с
  комментарием-причиной; 13 файлов эмуляторных тестов вместо своей копии `FAST` берут её (с
  точечными `...FAST_JOB_LIMITS, …` там, где тест правит один срок). Свои лимиты оставлены у
  `scan-job.emulator` (тестирует сами сроки транспорта: 200 / 150 / 5000) и у файлов коррекции
  (6000 под настоящий исполнитель). Тесты `stall` в `pass.emulator` ждут теперь 1,5 с вместо
  0,3 — в срок 20 с укладываются с запасом.

## Проверка

Первый заход (срок проекта + гонка): `typecheck`, `lint`, `format:check`; `npm run test` 2530;
`vitest run --project integration` дважды подряд при работающем приложении (`duplexnt.exe` ×4 —
условие, при котором падало) — 269 / 269, 25 и 22 с. Merge в `main` `d5d22a3` — и гейт `test:all`
на `main` уронил два теста простоем страницы (третья причина выше).

Второй заход (общие лимиты): `typecheck`, `lint`; `vitest run --project integration` — 269 / 269,
21 с; `test:all` на ветке при работающем приложении — 143 / 2530, интеграция 31 / 269 (4 пропущены), worst-case 3 / 5, зелёный с первого прогона.

## На чём встали

Оба захода закоммичены на ветке `fix/test-deadlines-under-load`; ручного смоука нет — правки
только в тестовой обвязке. Первый заход влит по ОК автора, второй — тем же ОК как доводка того же
бага (гейт `main` после первого merge красный — закрытие без него не считается).
