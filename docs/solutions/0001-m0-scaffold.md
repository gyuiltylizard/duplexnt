# M0 — Каркас и фундамент (журнал)

Живой журнал реализации [плана](../plans/2026-09-19-001-feat-m0-scaffold-foundation-plan.md). План —
замороженный артефакт решений; этот файл копит **отклонения, грабли и «на чём встали»** по ходу
сессий. Финализируется на закрытии (`status: done`).

ADR вехи: [0001](../decisions/0001-test-framework.md) (тестовый фреймворк),
[0002](../decisions/0002-language.md) (язык), [0003](../decisions/0003-shell-build-delivery.md)
(оболочка, сборка, поставка и спайк из трёх критериев). Новых ADR M0 не заводит; 0001 и 0003
получают амендменты по итогам спайка (U11).

## Окружение (выверено в начале сессии 1)

Node 24.17, npm 11.13, git 2.52, Windows 11. `core.autocrlf=true` глобально — перекрыт
`.gitattributes`. Remote не задан. `ELECTRON_RUN_AS_NODE=1` унаследована терминалом редактора на
уровне процесса: Electron из такого терминала стартует как Node.

**Связка версий (факт реестра на 2026-09-19).** Ведёт `electron-vite` 5.0.0, и это сразу дало два
ограничения против «просто latest»:

- `electron-vite` 5 принимает Vite `^5 || ^6 || ^7`, а `latest` у Vite уже 8 → **Vite 7.3**;
  отсюда `@vitejs/plugin-react` **5.2** (6-я ветка требует Vite 8).
- `typescript-eslint` 8.70 принимает TypeScript `<6.1.0`, а `latest` у TypeScript уже 7.0 →
  **TypeScript 6.0**. Пересмотр — когда typescript-eslint поддержит 7-ю.

## Сессия 1 — тулчейн

### U1. Гигиена репозитория и форматер — ✅ зелёный

`package.json` без поля `type` (KTD-31), `engines.node >= 22.12` — минимум, общий для
`electron-vite`, vitest и Electron 44. `.gitattributes`: общее правило LF первым, бинарные типы,
`test/fixtures/** -text`. Prettier: `singleQuote`, `printWidth: 100`, `endOfLine: lf` — под то, как
доки уже были набраны. Hook — husky 9 + lint-staged, форматирует застейдженное и больше ничего;
страж приватности добавит U15.

Проверено: `git check-attr` даёт `eol: lf` на markdown и `text: unset` под `test/fixtures/`; hook
отрабатывает на пути проекта с апострофом; застейдженный файл с CRLF и кривым форматированием
выходит из lint-staged отформатированным и с LF.

Первый прогон форматера — отдельный коммит-база: 7 файлов доков, только выравнивание таблиц,
`*курсив*` → `_курсив_` и развёрнутый блок `:root` в дизайн-системе. Смысл не тронут.

**Грабли:** `husky init` кладёт в hook `npm test` — заменено на `npx lint-staged`.

**Готово:** `format:check` зелёный. Коммиты `chore(m0): U1 …`, `style(m0): U1 …`.

### U2. Проекты TypeScript, electron-vite, окно — ✅ зелёный

Пять проектов TypeScript по KTD-5, корень solution-style. Закрыт отложенный вопрос плана про
`typecheck`: **`tsc -b` с `noEmit` и `incremental`, без `composite`** — TypeScript 6 принимает
ссылки на такие проекты из корня с `files: []`; `tsBuildInfoFile` уведён в `node_modules/.tmp/`.
В TypeScript 6 `types` по умолчанию пуст, и это работает на изоляцию: `shared` собирается без
Node и DOM, `core` — с Node, но без DOM. Проверено подставными файлами: `document` в ядре и
`node:fs` в `shared` роняют `typecheck`.

Таблица алиасов — `tooling/aliases.ts` (`@shared`, `@core`, `@locales`), корень берётся от
`process.cwd()`: конфиги бандлятся загрузчиками в разные форматы, где `__dirname` и `import.meta`
ведут себя по-разному. Входы и выходы `electron-vite` — по умолчанию; preload вышел одним
CJS-файлом.

Закрыт отложенный вопрос про `ELECTRON_RUN_AS_NODE`: **`electron.vite.config.ts` сам удаляет
переменную из `process.env`** — конфиг грузится в процессе `electron-vite` до запуска Electron, и
дочерний процесс наследует уже чистое окружение. Проверено: `npm run dev` с нарочно выставленной
`ELECTRON_RUN_AS_NODE=1` открывает окно. Это лечит `dev`; запуск `electron.exe` напрямую и
установленного приложения из терминала редактора по-прежнему требует снять переменную руками.

Проверено: `build` кладёт выход в `out/`, собранное приложение открывает окно с заголовком
приложения, события `preload-error` нет — preload грузится под sandbox и вне `dev`.

**Грабли:**

- Electron 44 убрал postinstall: бинарник качается лениво, при первом запуске. После чистой
  установки — `npx install-electron --no`, иначе первый `dev` молча ждёт загрузку.
- `electron-vite` по умолчанию не минифицирует ни один из трёх выходов — бандл renderer с React
  весит около 640 КБ. Это продакшен-сборка React, не dev; при загрузке с диска размер не важен.
- **Процессы Electron закрывать только по PID своего дерева** (`taskkill /PID <id> /T /F`), никогда
  по имени: `Stop-Process` по имени `electron` закрывает и чужие приложения на Electron,
  запущенные из `node_modules` соседних проектов. В этой сессии агент так закрыл dev-экземпляр
  Shelfory автора.

**Не проверено агентом:** отсутствие ложных ошибок JSX в открытом `.tsx` в редакторе — проверка
глазами автора.

**Готово:** `typecheck`, `format:check` зелёные. Коммит `feat(m0): U2 …`.

### U3. Харнес vitest — ✅ зелёный

Один `vitest.config.ts`, три проекта: `node`, `jsdom`, `integration`; алиасы — из общей таблицы.
`test` называет первые два поимённо. Проверено ловушкой: заведомо падающий тест под
`test/integration/` не попадает в `test` и попадает в `test:integration`. До U5 у
`test:integration` стоит `--passWithNoTests`; U5 его снимает.

Глобалы выключены, поэтому авто-очистка testing-library сама не срабатывает — `afterEach(cleanup)`
стоит в тесте явно. Когда jsdom-тестов станет больше одного файла (U7), это уезжает в setup-файл
проекта `jsdom`.

**Отклонение от плана (осознанное):** добавлены `@testing-library/react` и `@testing-library/dom` —
план их не называл, но сценарии U7 ищут текст в разметке, и писать это на голом `react-dom`
дороже.

**Готово:** `typecheck`, `format:check`, `test:all` зелёные. Коммит `test(m0): U3 …`.

## Сессия 2 — оболочка, границы, сквозной срез

Разовый вызов `openssl s_client` до сессии не делался: сканер не был подтверждён в сети. Риск
«прошивке нужен TLS, которого нет в BoringSSL» остаётся открытым до U8.

### U14. Усиление оболочки и CSP — ✅ зелёный

`src/main/shell/`: `web-preferences.ts` и `csp.ts` — чистые модули без импорта Electron;
`guards.ts` импортирует из Electron только типы, `app` и сессия приходят аргументами. Значения
`webPreferences` — литеральные типы: ослабление ломает и тест, и компиляцию.

Закрыт отложенный вопрос плана про доставку CSP: **мета-тег, который вставляет плагин Vite**
(`cspMeta` в `electron.vite.config.ts`) из того же билдера. Профиль выбирается по наличию
dev-сервера в контексте `transformIndexHtml`: у `build` его нет, поэтому профиль разработки в
сборку попасть не может. Заголовки отклонены: для страниц с диска перехват ответов ненадёжен, а
два механизма на два режима — лишняя развилка.

Сборочный профиль: `default-src 'none'`; `script-src`, `style-src`, `font-src`, `img-src` —
`'self'`; `connect-src`, `base-uri`, `form-action`, `object-src` — `'none'`. Профиль разработки
добавляет только `'unsafe-inline'` (преамбула React Refresh, теги `<style>` от Vite), origin
dev-сервера и его `ws://`; origin не с localhost билдер отклоняет.

Гвард навигации пропускает перезагрузку той же страницы (HMR) и отклоняет всё остальное;
редиректы, `webview` и `window.open` отклоняются; обработчики разрешений отвечают отказом.

Проверено вживую одноразовым скриптом (не в репозитории): в собранном приложении `sandbox` и
`contextIsolation` включены, React отрисовался под строгим CSP, нарушений CSP в консоли окна нет,
`location.href` на чужой адрес и `window.open` не сработали. В `dev` HMR подключился, нарушений нет.

**Отклонение от плана (осознанное):** добавлен `guards.test.ts` — план его не называл, но гварды
получились тестируемыми без Electron, и тест стоил десяти минут.

**Готово:** `typecheck`, `format:check`, `test:all` зелёные. Коммит `feat(m0): U14 …`.

### U4. ESLint и границы слоёв — ✅ зелёный

ESLint 10.11, typescript-eslint 8.70 (`strictTypeChecked` + `stylisticTypeChecked`), правила
хуков React для renderer. Проекты TypeScript перечислены поимённо, от строгого к широкому.
Границы — `no-restricted-imports` с `regex`-паттернами: один паттерн на слой покрывает и алиас,
и относительный путь любой глубины. Каждый блок несёт полный набор запретов своего каталога,
собирает их хелпер `layer()`. Для тестовых файлов слоя — отдельный блок: он открывает `test/`, но
не границы слоя. Глобальные механизмы ослабления TLS закрыты `no-restricted-syntax` по всему
`src/`.

**Отклонение от плана (осознанное):** конфиг собран на **`defineConfig` из `eslint/config`**, а не
на `tseslint.config()`. План предписывал обратное по опыту Shelfory, но в typescript-eslint 8.70
`tseslint.config` помечен устаревшим, и строгий пресет сам роняет на нём `lint`
(`no-deprecated`). Поломка типов, о которой предупреждал план, воспроизвелась — и оказалась
обходимой: свои блоки типизированы `Linter.Config[]` из самого ESLint, а не `ConfigArray` из
typescript-eslint. С `exactOptionalPropertyTypes` эти два типа несовместимы, и мешать их нельзя
ни в конфиге, ни в тесте.

Проверено вживую (AE1): настоящий файл под `src/core/` с импортом `electron` роняет `lint` с
сообщением, куда класть адаптеры. Тест — 15 сценариев, включая `import type`, относительные
пути, тестовый файл внутри ядра и соседние модули с похожими именами (`./main-loop`,
`../core-utils`) — они за слой не принимаются.

**Готово:** `typecheck`, `lint`, `format:check`, `test:all` зелёные. Коммит `feat(m0): U4 …`.

### U5. Контракт моста и команда-проба — ✅ зелёный

Контракт — `src/shared/bridge.ts`: карта команд, каналы, выводимые типы `Api` и `BridgeHandlers`,
правила моста — комментарием в шапке. Запрос пробы — объект `{ token }`, а не голая строка:
проверке есть что назвать по имени, и форма расширяется без смены сигнатуры. Ядро берёт версии
Electron и Chromium из `process.versions` — импорт Electron не нужен; под обычным Node там `null`.

`src/main/bridge.ts` Electron не импортирует: `ipcMain` и окно описаны структурно и приходят
аргументами. Отправитель принимается, только если это `webContents` окна приложения, его главный
фрейм, и окно не уничтожено. `sharp` — в `dependencies`; `electron-vite` сам оставил его внешним
(`require("sharp")` в выходе main), ядро вбандлено.

Проверено вживую одноразовым скриптом в собранном приложении:

- в окне результат пробы: Electron 44.4.3, Chromium 152, Node 24.21, sharp 0.35.4, libvips 8.18.6,
  JPEG 8×8 — **prebuilt N-API `sharp` работает в main-процессе Electron без пересборки**
  (подтверждает KTD-12 в части `sharp`);
- `Object.keys(window.api)` — только `probe`; `ipcRenderer`, `require`, `process` в `window` нет;
- `probe(42)` и `probe({ token: '' })` — отклонённый промис с `TypeError` и названием поля;
- лишний аргумент с чужим именем канала игнорируется — канал зашит в preload;
- вызов из второго окна с тем же preload отклонён в main, до ядра не дошёл.

Послабление `--passWithNoTests` у `test:integration` снято.

**Грабли:** отказ `ipcRenderer.invoke` приходит в интерфейс как `Error` с текстом «Error invoking
remote method '…': TypeError: …» — класс ошибки теряется, остаётся строка. Для M0 этого хватает;
транспорт доменных ошибок — решение M1 (KTD-29).

**Готово:** `typecheck`, `lint`, `format:check`, `test:all` зелёные. Коммит `feat(m0): U5 …`.

## Сессия 3 — поставка и страж

**Отклонение от нарезки (осознанное):** порядок внутри сессии — U10 → подготовка U16 → U15, а
ручной прогон U16 отдан автору в конце. U15 от U16 не зависит, и так никто никого не ждёт.

### U10. Установщик NSIS — ✅ зелёный

`electron-builder` 26.15.3 точной версией (тег `latest`; 27-я — альфа с другой схемой).
`electron-builder.yml`: состав — белый список `out/**` + `package.json` (KTD-36); `sharp` и
`@img/*` распакованы из asar явными паттернами; NSIS assisted, per-user,
`deleteAppDataOnUninstall: false`; `publish: null`.

Закрыты два отложенных вопроса плана:

- **fuses задаются прямо в конфиге** (`electronFuses`) — закреплённая версия это умеет,
  отдельный шаг сборки не нужен. Факт по `@electron/fuses read`: `RunAsNode` включён (временно,
  до конца U11), `EnableNodeOptionsEnvironmentVariable` и `EnableNodeCliInspectArguments`
  выключены, `OnlyLoadAppFromAsar` включён;
- **`npmRebuild: false`** — prebuilt N-API `sharp` пересборки не требует, установленное
  приложение это подтвердило.

Апостроф NSIS не сломал — ни в пути проекта, ни в `productName`. Запасной вариант со сборкой с
подставного диска не понадобился. Расклад имён получился удачнее, чем ждал план: каталог
установки — ASCII (`%LOCALAPPDATA%\Programs\duplexnt`, берётся из `name` в `package.json`), а
апостроф остался только в отображаемом названии — ярлык «Duplexn't», запись «Duplexn't 0.0.0» в
«Приложениях». Правило файрвола в U11 привяжется к пути без апострофа.

Проверено: в `app.asar` — только `out/`, `package.json` и production-зависимости (`sharp`,
`@img/*`, `detect-libc`, `semver`); `docs/`, `src/`, `spikes/`, `test/`, `local-test-data/` нет.
Упакованное приложение и приложение, установленное на основной машине тихой установкой, грузят
страницу из `app.asar` и показывают libvips 8.18.6; мусорный вызов моста отклоняется. Деинсталлятор
убрал каталог установки и ярлык, `%APPDATA%\duplexnt` остался на месте.

**Грабли:**

- Скрипт внутрь упакованного exe не подсунуть, поэтому окно читалось через
  `--remote-debugging-port` и протокол DevTools. Fuse `EnableNodeCliInspectArguments` этот порт
  не закрывает: он про инспектор Node, а не Chromium. Это пункт для hardening, рядом с DevTools.
- **Установленное приложение и `dev` делят один каталог данных** — `%APPDATA%\duplexnt`: Electron
  берёт имя из `name` в `package.json`, `productName` из конфига сборщика на это не влияет. Пока
  данных нет, это безвредно; с M1 отладочный запуск будет ходить по настоящим данным пользователя.
  Вход для ADR по модели данных перед M1.
- Проверку «нет запрещённых каталогов в asar» нельзя делать грепом по имени каталога без якоря:
  `node_modules\sharp\src\*.h` даёт ложные совпадения с `src/`.

**Готово:** `typecheck`, `lint`, `format:check`, `test:all` зелёные. Коммит `feat(m0): U10 …`.

### U16. Спайк поставки: чистая машина — ✅ пройден

Подготовлено: шаблон `spikes/sandbox.template.wsb` (сеть выключена, буфер обмена выключен,
единственная папка — на чтение), генератор `spikes/make-sandbox-config.mjs` — кладёт установщик в
отдельный `release/sandbox-share/` и подставляет абсолютный путь; чеклист —
`docs/output/2026-09-19-smoke-checklist-m0-u16-sandbox.md`. В Sandbox уезжает каталог с одним
установщиком, а не весь `release/`.

**Критерий 3 ADR 0003 — прошёл** (2026-09-19, прогон автора в Windows Sandbox по чеклисту, все
три сценария зелёные). Установщик `duplexnt-0.0.0-setup.exe`, собранный в U10 с `runAsNode: true`:

- установка assisted, per-user прошла без ошибок и без запроса прав администратора — на машине,
  где нет ни Node, ни проекта;

### U15. Страж приватности — ✅ зелёный

`scripts/privacy-guard.ts` по KTD-34: паттерны в четырёх областях плюс список настоящих значений
по всем файлам. Сначала были написаны тесты на синтетических утечках, потом страж. 33 теста, один
из них — прогон по всем отслеживаемым файлам репозитория.

Решения по ходу:

- **Поблажка «это номер версии» не действует на частные адреса.** Четырёхчастное число после
  слова «версия», `v` или `@` — версия; `192.168.…`, `10.…`, `172.16–31.…`, `169.254.…` —
  нарушение в любом контексте. Домашняя сеть — главный канал утечки, и эвристика не должна его
  открывать. Первым на стража наступил сам этот журнал: пример такого числа без слова «версия»
  перед ним остановил коммит — и правильно; фраза переписана, страж не ослаблен.
- IPv6 ловится только в формах с `::` и в полной из восьми групп — время вида `12:34:56` и
  селекторы `a::before` за адрес не принимаются.
- Имена `*.local` ловятся все, не только `EPSON…`; `.env.local` и `config.local.yaml` отсекаются
  окружением.

**Отклонение от плана (осознанное):** «сырые данные есть, а списка нет» проверяется по
`local-test-data/device/`, а не по всему `local-test-data/`. По `.gitignore` этот каталог — ещё и
место для личных файлов ручного смоука; страж не должен падать оттого, что автор положил туда PDF.
Снимки с устройства идут строго в `device/`, список значений — `local-test-data/privacy-values.txt`.

Закрыт отложенный вопрос про форму запуска из hook'а: **Node запускает `.ts` напрямую** (снятие
типов), отдельный JS-вход не нужен. Hook: сначала страж, потом lint-staged.

**Грабли:** без поля `type` Node на каждом запуске печатает `MODULE_TYPELESS_PACKAGE_JSON`. В
корень `type` ставить нельзя (KTD-31: от него зависит формат preload), поэтому в `scripts/` лежит
свой `package.json` с одним полем `"type": "module"` — он действует только на этот каталог.
Сборка проверена: preload по-прежнему CJS.

Проверено вживую (AE9): коммит файла под `docs/solutions/` с частным адресом остановлен hook'ом с
именем файла и строкой, в историю ничего не попало; чистый коммит проходит.

| «Отмена»           | два входящих **блокирующих** правила: TCP и UDP, частный профиль | оба сервиса найдены — 4 из 4 |

- **Отклонённый запрос обнаружение не сломал.** Риск из плана «запрос отклонён — обнаружение
  молча пустое» на этой машине не сработал: при блокирующих правилах сканер нашёлся и в прогоне с
  запросом, и в трёх последующих, уже без запроса. Причина не установлена. Гипотеза: порт 5353
  общий, и multicast-ответ система пропускает по правилу другого слушателя, а доставляет всем.
  Полагаться на это нельзя — на машине без других слушателей 5353 поведение может быть иным;
  текст для интерфейса на случай пустого обнаружения остаётся задачей M1.
- **Правило появляется в момент показа запроса, а не по клику:** во всех прогонах — на второй
  секунде, сразу блокирующее; ответ «Разрешить» меняет его на разрешающее. Из-за этого первая
  попытка ветки «отклонить» у агента сорвалась: правило возникло так же быстро, как в ветке
  «разрешить», агент не смог отличить клик от автоматики и спросил автора. Автор оба раза нажал
  «Разрешить»; ветка повторена.
- Имя правил — `duplexnt.exe`; удаляются одной командой по `-DisplayName`. **Блокирующее правило
  переживает деинсталляцию** и досталось бы следующей установке в тот же путь.

Итоги спайка оформлены амендментами: [ADR 0003](../decisions/0003-shell-build-delivery.md) — три
критерия, библиотека mDNS (`bonjour-service`) с двумя условиями работы на Windows, уточнение про

Приложение деинсталлировано, каталог данных на месте.

## Ревью вехи (simplify + code-review)

Перед U12, по всей ветке относительно `main`. Код спайка (`spikes/`) в область качества не входил.

**Simplify** (три ревьюера: переиспользование, качество, эффективность) — применено 3, пропущено 3.
Применено: общий разбор строк в страже, одна пара путей токенов для скрипта и теста, два
интерфейса моста без потребителей перестали экспортироваться. Пропущено: батч-чтение
застейдженных файлов одним процессом git — выигрыш около секунды на больших коммитах против
парсера бинарного протокола в коде, где ошибка необратима. Коммит `refactor(m0): simplify …`.

**Code-review** (восемь ревьюеров: correctness, security, adversarial, testing, maintainability,
project-standards, agent-native, learnings). Каждая находка перед правкой подтверждена
исполнением — настоящим модулем стража и ESLint в памяти. Три находки пришли независимо от
двух-трёх ревьюеров. Коммит `fix(m0): review …`.

Страж приватности — закрытые дыры, все воспроизведены до правки:

- заводское имя Epson ловилось только с суффиксом `.local` и только вдали от `-`, `_` и
  расширений. Мимо проходили `EPSON….lan`, `EPSON….fritz.box`, имя mDNS-сервиса
  `EPSON…._uscan._tcp.local` — ровно то, что естественно написать в журнале спайка. То же с UUID
  в имени файла и в URL-кодировке;
- текст в UTF-16 (перенаправленный вывод PowerShell 5.1) считался бинарным и пропускался
  **обоими** механизмами;
- существующий, но пустой список значений рапортовал «список значений проверен»;
- имена файлов и каталогов не проверялись вовсе;
- значение из списка в другой записи (MAC через дефис, отпечаток сплошным hex) не находилось;
- отпечатки сертификатов в записи через двоеточие не имели паттерна; `MAC:00:1A:…` без пробела
  после метки проходил мимо;
- точка входа сравнивала пути строками — через junction hook молча вышел бы с нулём.

Главный вывод: по ужесточённым правилам, с настоящим списком значений, **репозиторий чист** —
дыры были в страже, утечек через них не случилось.

ESLint — закрытые дыры: динамический `import()` и `require()` проходили любую границу слоя
(`no-restricted-imports` видит только статические импорты); голое `'fs'` проходило в preload, где
его не ловит и typecheck; запрет глобального ослабления TLS не знал ключей Chromium
`ignore-certificate-errors` и `allow-insecure-localhost`, шаблонных строк, доступа по строковому
ключу и `checkServerIdentity`. **Грабли:** в грамматике селекторов ESLint внутри `/…/` слэш
недопустим даже экранированным — в регулярном выражении он записывается hex-кодом.

Остальное: билдер CSP переехал из `src/main/shell/` в `tooling/csp.ts` (единственный потребитель —
конфиг сборки, а границы слоёв не видят файлы вне `src/`; хвост из сессии 2 закрыт); окно без
моста показывает строку об ошибке вместо вечного «Проверяю…»; `denyAllPermissions` и
`installShellGuards` получили тесты (R4 требовал «закрыты тестом»); `engines.node` поднят до
22.18 — на 22.12–22.17 Node не запускает `.ts` напрямую, и hook падал бы на каждом коммите;
статус плана переведён в «в работе».

Не применено, оставлено автору:

- **отдельный git worktree** — там нет ни списка значений, ни установленного hook'а, страж
  работает одними паттернами. Предложение ревью: искать список через общий каталог git и добавить
  `pre-push` с полным прогоном. Это изменение процесса — решение автора;
- паттерн слоя срабатывает на любой каталог с именем слоя: будущая папка `main` внутри renderer
  дала бы ложное срабатывание. Лечится либо правилом «имена слоёв зарезервированы», либо
  правилом на основе резолвера — решение на M1;
- сообщения коммитов и история стражем не проверяются — перед первым публичным push нужен прогон
  списка значений по `git log -p --all`; техбаза — известный случай.

Тестов после ревью: 135 в `test`, 3 в `test:integration`.
