## Сессия 1 — факты с устройства

### U1. Живой след задания ET-3850 — ✅ зелёный

**Скрипт съёмки** — `spikes/escl-job-trace.mjs`, описание сценариев и ключей — `spikes/README.md`.
Ведёт настоящее задание автоподачи и пишет каждый обмен (запрос, статус, сырые заголовки, времена,
тело) в `local-test-data/device/trace/`. По каждой странице — первые и последние байты, байты после
маркера конца, размеры из заголовка JPEG против региона, метаданные `sharp`.

Порядок приватности встроен в скрипт: UUID заданий он сам дописывает в
`local-test-data/privacy-values.txt` в момент получения ответа — раньше, чем о них можно написать
строку журнала; в stdout адрес и UUID заменены метками.

До похода к сканеру скрипт прогнан на одноразовой локальной заглушке (вне репозитория): сценарии
`job`, `abandon`, `wake`, ключи `--delete-after`, `--pause`, `--keepalive`, `--wait-loaded`, отказ
соединения. Это проверка скрипта, а не факт об устройстве.

**Наблюдения с устройства** — ниже, по сценариям; записываются только после съёмки. Гипотезы
помечаются словом «гипотеза».

#### Соединение и обрамление ответов

- Каждый ответ несёт `Connection: close`: соединение на запрос. Протокол HTTP/1.1, TLS 1.2,
  шифр тот же, что в M0.
- Полное рукопожатие TLS на бодром устройстве — около 0,7 с (три замера: 711, 717, 735 мс).
  Следующие соединения того же агента идут с возобновлённой сессией — 8–20 мс. Автор подтвердил,
  что устройство при этом не спало: 0,7 с — цена рукопожатия, а не пробуждения.
- XML-ответы (`ScannerStatus`) — с `Content-Length`, тип `text/xml;charset="utf-8"`.
- Страницы — `Transfer-Encoding: chunked`, без `Content-Length`, тип `image/jpeg`, с заголовком
  `Content-Location: <задание>/file-N`. Имена заголовков устройство пишет прописными
  (`CONTENT-LENGTH`, `TRANSFER-ENCODING: CHUNKED`).
- Ответы без тела (`201`, `404`, `503`) несут `Content-Length: 0`.
- Сертификат на всех соединениях один.

#### Пустой лоток

Статус до задания — `Idle`, `ScannerAdfEmpty`. Физически устройство не делает ничего: ни роликов,
ни сообщения на панели (наблюдение автора).

| Запрос                | Ответ                                                                                        |
| --------------------- | -------------------------------------------------------------------------------------------- |
| `POST /ScanJobs`      | `201`, `Location` абсолютный, с портом 443                                                   |
| `ScannerStatus`       | `Processing`, лоток `ScannerAdfEmpty`, задание `Processing`                                  |
| первый `NextDocument` | `404` через 28 мс                                                                            |
| `ScannerStatus`       | задание `Aborted`, `ImagesCompleted` 0; устройство — `Processing`, следующим запросом `Idle` |
| `DELETE` задания      | `404`; повторный — тоже `404`                                                                |

Задание при пустом лотке **создаётся**. Отличить «бумаги нет» можно до задания — по `AdfState`, и
после — по `404` на первой странице вместе с состоянием задания `Aborted`.

#### Проход: три листа, серый, 300 dpi

| Шаг                        | Ответ и время                                                                     |
| -------------------------- | --------------------------------------------------------------------------------- |
| `POST /ScanJobs`           | `201` через 37 мс                                                                 |
| `ScannerStatus`            | `Processing`, лоток ещё `ScannerAdfLoaded`, задание `Processing`                  |
| `NextDocument`, страница 1 | заголовки через 15,9 с, тело ещё 10,3 с; 540 КБ                                   |
| `ScannerStatus`            | лоток `ScannerAdfProcessing`, `ImagesCompleted` 1                                 |
| `NextDocument`, страница 2 | **`503`** с `Retry-After: 20`; повтор через секунду — `200`, тело 10,2 с; 1,19 МБ |
| `NextDocument`, страница 3 | `503`, повтор через секунду — `200`, тело 10,3 с; 606 КБ                          |
| `NextDocument`, страница 4 | `503` четыре раза подряд (4,5 с), затем `404`                                     |
| `ScannerStatus`            | задание `Completed`, `ImagesCompleted` 3, лоток `ScannerAdfEmpty`                 |
| `DELETE` задания           | `404`; повторный — тоже `404`                                                     |

- **`503` на `NextDocument` — штатное «страница ещё не готова», а не обрыв.** Он приходит после
  каждой страницы, и перед финальным `404` — тоже. Заголовок `Retry-After: 20` устройство шлёт, но
  повтор через секунду проходит.
- **После `404` задание само становится `Completed`,** и `DELETE` по нему отвечает `404`.
  Устройство закрыло задание без нас.
- Тело страницы идёт потоком около 10 с — столько же, сколько лист едет через сканер.
- Список заданий в статусе держит два последних; `Age` идущего задания — 0, у закрытых растёт в
  секундах.
- Значения `AdfState`, которые встретились: `ScannerAdfEmpty`, `ScannerAdfLoaded`,
  `ScannerAdfProcessing`.

**Страница.** Baseline JPEG, один скан: `SOI`, `APP0` JFIF 1.2 с плотностью 300×300 точек на дюйм,
`DQT`, `DHT`, `SOF0`, `SOS`, данные, `EOI`. Файл начинается с `FF D8 FF E0`, кончается `FF D9`,
после маркера конца — ноль байт. Размер в `SOF0` — 2480×3507, ровно запрошенный регион; маркера
`DNL` и маркеров перезапуска нет. Серый — один канал. EXIF и ICC нет. `sharp` читает без отказа.

#### Занятость печатью

Устройство печатало три страницы, в автоподаче лежал лист.

- `ScannerStatus` во время печати — `Processing`, хотя ни одного задания сканирования в работе
  нет; лоток — `ScannerAdfLoaded`.
- `POST /ScanJobs` — `503` с `Retry-After: 20` и пустым телом, пятнадцать раз подряд при повторе
  раз в секунду (16 с от первой попытки; печать началась раньше).
- Шестнадцатая попытка — `201`; дальше задание прошло как обычное: заголовки первой страницы
  через 15,5 с, после страницы четыре `503` и `404`.
- Сканирование физически началось после того, как печать закончилась (наблюдение автора).
  Очереди у устройства нет: только отказ и повтор.

#### Размер страницы A4

Серый, листы автора (не одинаковые — оценка порядка величины, а не точное сравнение):

| Разрешение | Пиксели   | Размер файла | Тело идёт |
| ---------- | --------- | ------------ | --------- |
| 200 dpi    | 1653×2338 | 0,46 МБ      | 10 с      |
| 300 dpi    | 2480×3507 | 0,54–1,19 МБ | 10 с      |
| 600 dpi    | 4960×7014 | 2,8–3,1 МБ   | 40 с      |

Размеры в `SOF0` во всех прогонах равны региону, пересчитанному в пиксели по разрешению;
плотность в JFIF равна запрошенному разрешению. При 600 dpi заголовки первой страницы пришли
через 15,9 с, тело — ещё 40 с.

#### Где лист лежит в поле автоподачи

Измерено на калибровочных листах: три листа A4 с миллиметровыми линейками от левого и верхнего
края, генератор — `spikes/make-calibration-pdf.mjs`, печать на том же устройстве в масштабе 100 %.
Листы подаются верхним краем вперёд. Края бумаги найдены по переходу «серый фон → белая бумага» в
трёх полосах строк. Единицы — 1/300 дюйма от левой границы поля шириной 2550.

| Прогон                              | Левый край листа          | Правый край листа                 |
| ----------------------------------- | ------------------------- | --------------------------------- |
| полная ширина (регион 0…2550)       | 31–41 вверху, 57–59 внизу | 2515–2521 вверху, 2541–2546 внизу |
| A4 со смещением 35 (регион 35…2515) | 43–66                     | за границей региона               |
| листы автора, смещение 0 и 70       | 40–57                     | 2505 вверху, за 2550 внизу        |

- **Лист A4 лежит примерно по центру поля,** а не прижат к краю: ширина листа на скане 2481–2488,
  слева и справа от него остаётся фон. В capabilities устройство заявляет
  `Justification`/`XImagePosition` = `Right` — наблюдение с этим не сходится: при юстировке вправо
  левый край был бы на 70.
- **Положение гуляет от подачи к подаче** — левый край от 31 до 66, то есть ±1,5 мм вокруг
  среднего около 48 — и листы перекошены: край уходит на 20–28 единиц на длине листа (около
  0,6°), на всех трёх листах в одну сторону.
- **Смещение 0 режет правый край листа, смещение 70 — левый** (проверено на листах автора:
  сдвиг содержимого между сканами ровно 70 пикселей при 300 dpi). Смещение 35 даёт слева полосу
  фона 8–31 единиц и срезает столько же бумаги справа.
- Ведущий край листа — на 5–22 единицах от верха региона: сверху в кадр попадает до 2 мм фона,
  снизу на столько же обрезан лист. Фон подачи — серый (яркость около 235 из 255), у самой левой
  границы поля — тёмная полоса шириной 6 единиц.

**Правило для U7:** смещение региона по горизонтали — по центру поля,
`XOffset = (MaxWidth − ширина листа) / 2`; для A4 это 35, для Letter — 0. Вертикальное смещение — 0. Заявленная устройством юстировка в расчёт не идёт. Потери при этом правиле — до 2,6 мм бумаги с
одной стороны из-за разброса подачи; полностью их снимает только скан на всю ширину с обрезкой на
своей стороне — это постобработка, вне M1.

#### Цвет

Три калибровочных листа, `RGB24`, 300 dpi: 834–871 КБ на страницу, три компонента, субдискретизация
4:2:0, тот же набор маркеров, что у серого. Те же листы в сером — 876–912 КБ: цветной скан
почти белого листа не тяжелее серого. Времена те же: тело около 10 с.

#### Пауза 45 с между запросами `NextDocument`

- После страницы устройство **само затягивает следующий лист в тракт и останавливается** — ждёт
  запроса; после `NextDocument` лист едет дальше (наблюдение автора: «начал загружаться, затем
  пауза, продолжил»). Первый лист проходит без остановки.
- След это подтверждает: после паузы `NextDocument` отвечает `200` сразу, без `503`, заголовки
  через 90 мс, а тело идёт те же 10 с — страница сканируется по запросу, а не заранее в память.
- Отсюда смысл `503` между страницами в обычном проходе: устройство ещё затягивает следующий лист
  (около секунды). Четыре `503` перед финальным `404` — оно пытается взять лист, которого нет.
- Пока клиент молчит, задание остаётся `Processing`: и с листами в лотке, и после последней
  страницы при пустом лотке (45 с — без изменений). `Completed` оно становится только после
  `404`, отданного клиенту. После паузы при пустом лотке `404` приходит сразу, без `503`.
- В паузе `AdfState` возвращается в `ScannerAdfLoaded` (или `ScannerAdfEmpty` после последнего
  листа); `ScannerAdfProcessing` держится только рядом с передачей страницы.
- `Age` идущего задания — секунды с последнего обращения к нему, а не с создания: в паузе растёт,
  после каждой страницы сбрасывается.

#### `DELETE` посреди задания

Три листа, `DELETE` сразу после первой страницы.

| Запрос                           | Ответ                                           |
| -------------------------------- | ----------------------------------------------- |
| `DELETE` идущего задания         | **`200`**, пустое тело                          |
| `ScannerStatus` сразу после      | задание `Canceled`; через 2 с устройство `Idle` |
| `NextDocument` закрытого задания | **`410 Gone`**                                  |
| повторный `DELETE`               | `404`                                           |

- `DELETE` отвечает `200` только идущему заданию; завершённому (`Completed`) и оборванному
  (`Aborted`) — `404`.
- **Оставшиеся листы устройство прогоняет через тракт без остановки** (наблюдение автора); окно
  «Сканирование» на панели пропало на втором листе. Статус всё это время — `Idle`, лоток
  `ScannerAdfLoaded` (20 с наблюдения). Для «Остановить» это значит: остаток пачки окажется в
  выходном лотке несканированным, в подаче он не останется.

#### Параметры, которые устройство отклоняет

Проверено при пустом лотке — исправное задание при этом получает `201`, так что отказ относится
к параметрам, а не к бумаге.

| Параметры задания                             | Ответ на `POST`                 |
| --------------------------------------------- | ------------------------------- |
| `BlackAndWhite1` + `image/jpeg`               | **`409 Conflict`**, пустое тело |
| `Grayscale8`, 1200 dpi (у автоподачи его нет) | **`409 Conflict`**, пустое тело |
| ширина региона 2600 при пределе 2550          | `201` — принято без возражений  |

- **Чёрно-белый режим с JPEG устройство не принимает,** хотя capabilities перечисляют
  `BlackAndWhite1` и `image/jpeg` в одном профиле. Причина отказа в ответе не названа; что дело в
  несовместимости однобитного режима с JPEG — гипотеза. Для M1 следствие одно: список цветовых
  режимов нельзя брать из capabilities как есть — `BlackAndWhite1` при формате JPEG исключается.
- `409` — ответ устройства на параметры, которые оно не берёт. Повторять его бессмысленно: это не
  занятость.
- **Регион шире поля устройство не отклоняет** — проверка пределов региона остаётся на нашей
  стороне (U7).

#### Цвет, 600 dpi

Три калибровочных листа: 3,38–3,51 МБ на страницу, 4960×7014, 4:2:0. Заголовки первой страницы
через 14,8 с, тело каждой — 40,5 с.

#### Брошенное задание

Три листа; после первой страницы клиент перестал запрашивать страницы и не отправил `DELETE`.

- **Устройство задание не отпускает.** 182 с наблюдения: задание `Processing`, `Age` растёт,
  `POST /ScanJobs` раз в 5 с — каждый раз `503` с `Retry-After: 20` (36 попыток).
- `DELETE` брошенного задания — `200`, задание `Canceled`, статус сразу `Idle`.
- **После `DELETE` устройство ещё около 25 с отвечает на `POST` отказом `503`,** хотя статус уже
  `Idle`: 24 попытки раз в секунду, на 25-й — `201`. В это время оно прогоняет оставшиеся листы
  через тракт (см. «`DELETE` посреди задания»). Новое задание после этого получает `404` на
  первой странице: лоток уже пуст, хотя статус до последнего показывал `ScannerAdfLoaded`.
- Адрес идущего задания виден в статусе: `JobUri` в секции заданий, состояние `Processing`. Это
  выход из положения «задание создано, адрес не записан» — закрыть его можно по статусу.
- **Устройство само снимает брошенное задание через 5 минут без обращений** (отдельный прогон:
  один лист, пробы раз в 20 с). Через 286 с после последней страницы задание ещё `Processing`, при
  следующей пробе — `Aborted` с `Age` 6, то есть снято на 300-й секунде. Ещё одну пробу `POST`
  отвечал `503` (статус уже `Idle`, лоток `ScannerAdfLoaded`), следующая — `201`. `DELETE` снятого
  задания — `404`.
- Физически (наблюдение автора): первый лист прошёл, второй начал затягиваться и остановился —
  долгая пауза; что стало с третьим, автор не видел.

#### Сбой подачи: крышка автоподачи открыта на втором листе

Три листа; первая страница получена целиком, крышка открыта, пока ехал второй лист.

| Запрос                     | Ответ                                                                                          |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| `NextDocument`, страница 2 | `503` шесть раз подряд (7 с), затем **`410 Gone`**                                             |
| `ScannerStatus`            | лоток **`ScannerAdfJam`**, задание **`Aborted`**, `ImagesCompleted` 1, устройство `Processing` |
| `DELETE` задания           | `404`                                                                                          |
| `ScannerStatus` через 12 с | по-прежнему `Processing` и `ScannerAdfJam`                                                     |

**Сбой подачи отличим от конца прохода по одному ответу:** конец — `404` и задание `Completed`,
сбой — `410` и задание `Aborted`, лоток `ScannerAdfJam`. Чтение статуса после `404`, которое
KTD-9 держал запасным ходом, не понадобилось.

На панели (наблюдение автора): «замятие» → «удалите замятую бумагу» → после удаления —
«сканирование остановлено»; оставшиеся листы при этом лежали в лотке. Когда бумага вынута,
статус возвращается в `Idle` без запросов с нашей стороны; в списке заданий остаётся `Aborted`.

#### Сбой подачи: лист придержан рукой

Сбой пришёлся на первую страницу — до того, как устройство отдало заголовки ответа.

| Запрос                     | Ответ                                                                                                                            |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `NextDocument`, страница 1 | **ответа нет:** соединение установлено, запрос ушёл, через 11,5 с устройство закрыло соединение без единого байта (`ECONNRESET`) |
| `ScannerStatus`            | лоток `ScannerAdfJam`, задание `Aborted`, `ImagesCompleted` 0, устройство `Processing`                                           |
| `DELETE` задания           | `404`                                                                                                                            |

Вторая форма того же сбоя: если запрос страницы уже висит, когда подача срывается, устройство не
отвечает `410`, а рвёт соединение. Состояние в статусе то же — `ScannerAdfJam` и `Aborted`.

**Сбой не ушёл сам.** Через 7 минут статус всё ещё показывал `Processing` и `ScannerAdfJam`, на
панели — ошибка автоподачи; вынуть бумагу не помогло, автор перезапустил устройство. Причина не
установлена, два объяснения — оба гипотезы: устройство держит состояние замятия до перезагрузки;
либо сместился датчик в тракте (автор при выключенном питании открывал крышку и трогал механизм).
После сбоя с открытой крышкой, несколькими минутами раньше, перезапуск не понадобился.

Вывод для интерфейса M1 от причины не зависит: состояние «проход прерван» может требовать от
пользователя действий у самого устройства вплоть до перезапуска, и приложение этого по сети
починить не может.

**Сценарий больше не повторять:** придержанный лист — риск для механизма. Осталось непроверенным,
что отвечает устройство, когда ролик не смог взять очередной лист посреди пачки (гипотеза:
обычный `404`, неотличимый от конца пачки). Защита от этого — не протокол, а сверка числа страниц
глазами пользователя; в M2 её даёт несовпадение проходов.

#### После перезагрузки устройства

- Первый запрос: TCP 67 мс, полное рукопожатие TLS 0,79 с — как у бодрого устройства.
- Список заданий в статусе пуст: секции `scan:Jobs` в ответе нет вовсе (291 байт). История заданий
  перезагрузку не переживает.
- Отпечаток сертификата после перезагрузки тот же: запомненный отпечаток (KTD-40) перезапуск
  устройства не сбивает.

#### Уснувшее устройство

Экран погас (наблюдение автора) через пять с небольшим минут после последнего задания: `Age`
последнего задания в статусе — 330 с.

| Запрос                    | TCP     | Ответ целиком | Рукопожатие TLS     |
| ------------------------- | ------- | ------------- | ------------------- |
| первый, устройство спит   | 89 мс   | 875 мс        | полное              |
| второй и третий           | 3–6 мс  | 22 мс         | сессия возобновлена |
| первый, устройство бодрое | 5–16 мс | 0,72–0,74 с   | полное              |

Сон добавляет к первому ответу около 0,15 с: устройство отвечает из сна само, будить его
кнопкой не нужно. Таймаут соединения в 5 с (KTD-14) покрывает это с большим запасом. Совет
техбазы «перед первым запросом разбудить сканер кнопкой на панели» на этом устройстве не
подтверждается.

#### Что наблюдения меняют в решениях плана

План заморожен и не правится; ниже — то, по чему пишутся юниты, где наблюдение разошлось с планом
или уточнило его.

**KTD-9 (конец и обрыв прохода) — исправлено.** Правило плана «любой отказ, кроме `404`, — обрыв»
оборвало бы каждый проход на второй странице. Правило по наблюдённому:

| Ответ на `NextDocument`                              | Что это                                |
| ---------------------------------------------------- | -------------------------------------- |
| `200`, тело дочитано, JPEG от `SOI` до `EOI`         | страница                               |
| `503`                                                | «ещё не готово» — повтор через секунду |
| `404` после хотя бы одной страницы                   | конец прохода                          |
| `404` на первой странице                             | пустой проход: бумаги не было          |
| `410`                                                | обрыв: сбой подачи                     |
| соединение закрыто без ответа, таймаут, другой отказ | обрыв                                  |

Подряд идущих `503` наблюдалось до шести (7 с). Потолок серии `503` на `NextDocument` — стартовое
значение 30 с, после него обрыв. Запасной ход плана — читать `ScannerStatus` после `404` — не
нужен: сбой подачи отвечает `410`, а не `404`. Остаётся непокрытым случай «ролик не взял лист»:
как он выглядит по сети, не снято.

**KTD-10 (занятость) — подтверждено с уточнением.** `503` на `POST` повторяется раз в секунду;
`Retry-After: 20` игнорируется, как и записано в KTD-31. Занятость после «Остановить» длится,
пока устройство прогоняет остаток пачки, — около 12 с на лист. На большой пачке это дольше
потолка в 60 с: состояние «сканер занят» после остановки — штатное, а не сбой.

**KTD-11 (`DELETE`) — подтверждено.** `200` — идущему заданию, `404` — завершённому и оборванному;
оба исхода — успех. После обычного конца прохода `DELETE` ничего не закрывает: устройство закрыло
задание само, но запрос безвреден. Незакрытое идущее задание блокирует устройство на 5 минут,
потом устройство снимает его само, — закрытие перед следующим `POST` остаётся обязательным: ждать
пять минут пользователю незачем. Отложенный вопрос плана «задание с
неизвестным адресом» решается статусом: `JobUri` задания в состоянии `Processing`.

**KTD-14 (таймауты) — стартовые значения годятся.**

| Что                        | Значение плана | Наблюдение                                     |
| -------------------------- | -------------- | ---------------------------------------------- |
| соединение                 | 5 с            | TCP до 67 мс, полное рукопожатие TLS 0,7–0,8 с |
| XML-запрос                 | 10 с           | до 40 мс                                       |
| тишина при приёме страницы | 90 с           | до заголовков первой страницы — до 16 с        |
| ожидание занятости         | 60 с           | печать трёх страниц — больше 16 с              |
| `DELETE`                   | 5 с            | до 30 мс                                       |
| XML-ответ                  | 1 МБ           | статус — до 0,9 КБ, capabilities — 7 КБ        |

Страница целиком: 17–26 с при 300 dpi, 40–56 с при 600 dpi. Общий срок приёма страницы (KTD-31)
— стартовое значение 5 минут.

**KTD-31 (приём страницы) — подтверждено.** Обрамление страницы — `chunked` без `Content-Length`;
соединение закрывается после каждого ответа. Все снятые страницы (больше тридцати) начинаются с
`SOI`, кончаются `EOI`, после него ноль байт — правило приёма по маркерам работает. Самая тяжёлая
страница — 3,5 МБ (цвет, 600 dpi). Потолок размера страницы — стартовое значение 64 МБ: несжатый
максимальный регион при 600 dpi в цвете — 128 МБ, JPEG устройства на порядок меньше. Потолок
числа страниц задания — 500.

**KTD-36 (место на диске).** Оценка на проход: 50 листов × 3,5 МБ = 175 МБ при 600 dpi в цвете,
60 МБ при 300 dpi. Запас перед проходом — 500 МБ.

**KTD-37 (предел пикселей) — подтверждено.** Размер страницы в `SOF0` во всех прогонах равен
региону, пересчитанному по разрешению. Предел — наибольший регион автоподачи при наибольшем
разрешении: 2550×4200 при 600 dpi = 5100×8400.

**KTD-6 (транспорт).** `Connection: close` на каждом ответе: соединение на запрос, keep-alive
устройство не даёт. Возобновление сессии TLS делает повторные соединения дешёвыми (10–20 мс), так
что сверка отпечатка на каждом новом соединении (KTD-40) ничего не стоит.

**R4, U6 (варианты из capabilities) — уточнено.** Цветовой режим `BlackAndWhite1` устройство
перечисляет, но с JPEG не принимает (`409`). Варианты для интерфейса M1 — режимы из capabilities
минус `BlackAndWhite1`. `409` на `POST` получает свой код отказа «параметры отклонены
устройством» и не повторяется. Чёрно-белый результат через порог на своей стороне — во «Входящие»
бэклога.

**U7 (регион).** Смещение по горизонтали — по центру поля (см. «Где лист лежит в поле
автоподачи»). Пределы региона проверяются у нас: устройство слишком широкий регион принимает молча.
Версия в запросе — `2.9`, элемента `Intent` нет; принятое тело — фикстура
`ScanSettings.a4-gray-300.xml`.

**R15, U17, U23 («Остановить»).** После `DELETE` идущего задания устройство прогоняет остаток
пачки в выходной лоток несканированным. Текст интерфейса обязан об этом сказать: после остановки
пачку собирают из выходного лотка заново. Это вход для handoff U19.

**R16 (прерванный проход).** Сбой подачи может требовать действий у устройства вплоть до
перезапуска. «Досканировать остаток» предлагается, но приложение не обещает, что сканер готов.

**Отклонения от плана (осознанные):**

- Добавлен генератор калибровочных листов `spikes/make-calibration-pdf.mjs` (предложение автора
  по ходу съёмки): положение листа в поле меряется по линейкам, а не по чужим документам.
- «Лист вытащен посреди подачи» снят открытой крышкой автоподачи, а не вытягиванием листа.
- Занятость печатью воспроизвелась — снята.
- Цвет при 200 dpi не снят: размеры при 300 и 600 dpi в цвете и при 200 dpi в сером дают оценку.
- Наблюдений больше, чем перечислял план: отклонённые параметры (`409`), `410` после `DELETE`,
  поведение `Age`, состояние после перезагрузки.

## Сессия 2 — фундамент

### U2. Мост: конверт, схемы, события — ✅ зелёный

Мост приведён к [ADR 0005](../decisions/0005-bridge-validation-errors-events-images.md) до первой
продуктовой команды.

- **Конверт.** `src/shared/errors.ts` — перечисление кодов `ERROR_CODES`, тип `Result` и
  конструкторы `ok` / `fail`. Карта команд несёт тип значения, `Api` и обработчики main возвращают
  `Result`. Отказ `invoke` остался только для ошибок программы: чужой фрейм по-прежнему получает
  исключение.
- **Схемы.** `src/core/commands/schemas.ts` — схема пробы на `zod` и `parseInput`: мусор на входе
  даёт `fail('invalidInput')` с путём поля и кодом нарушения. Само значение входа в детали не
  попадает — оно может быть большим или чужим. Рукописный валидатор удалён.
- **События.** Карта `BridgeEvents` рядом с картой команд; `src/main/events.ts` отправляет событие
  в канал контракта и молчит, если окно или его `webContents` разрушены. Preload отдаёт
  `on<Событие>(обработчик)` с отпиской; обработчик получает только данные события.
- **Интерфейс.** Proof-shell читает конверт; доменный отказ показывается текстом из локали по ключу
  `errors.<код>`. Ключ типизирован шаблоном, поэтому код без строки в локали ломает `typecheck`.

Решения, которые план оставил юниту:

- **Коды ошибок — camelCase** (`invalidInput`): код одновременно ключ локали и литерал TypeScript.
- **Схема строгая** (KTD-39): лишнее поле в запросе пробы теперь отказ. Валидатор M0 лишние поля
  молча отбрасывал.
- **Тип запроса объявлен в `shared`, схема в ядре сверяется с ним через `satisfies`.** ADR 0005
  хочет типы из схем, но `shared` не может импортировать ядро; для входа команд описаний два, и
  расхождение ловит компилятор. Журнал и настройки (U13, U15) живут в ядре целиком — там тип
  выводится из схемы.
- **Событие в карте одно — `snapshotChanged` с номером снимка.** Событие обнаружения заведёт U12
  вместе со своим источником: его форма зависит от того, что решит обнаружение.

**Отклонение от плана (осознанное):** сборка `window.api` вынесена из `src/preload/index.ts` в
`src/preload/api.ts` с тестом `api.test.ts` — этих файлов в списке юнита нет. Сценарий «после
отписки обработчик не вызывается» иначе проверить нечем: `index.ts` импортирует Electron. Отправитель
событий в `src/main/index.ts` пока не подключён — у него нет источника до службы прохода (U17, U18).

**Проверено в `dev`:** окно прочитано через отладочный порт — проба зелёная («Обработка изображений
работает — libvips 8.18.6»), в `window.api` ровно `probe` и `onSnapshotChanged`.

**Готово:** `typecheck`, `lint`, `format:check`, `test:all` зелёные (175 + 3). Коммит
`feat(m1): U2 мост на конверте…`.

### U4. Атомарная запись и удаление — ✅ зелёный

`src/core/storage/atomic-file.ts` — один помощник, на котором встанет хранилище:

- `writeFileAtomic` и `writeStreamAtomic` — временный файл рядом с конечным → `fsync` → закрытие →
  переименование. Сбой на любом шаге до переименования оставляет прежний файл нетронутым и убирает
  временный. Поток принимается как асинхронный итератор — так отдаёт тело ответа `node:http`.
- `renameWithRetry` — для файла и каталога: `EPERM`, `EBUSY`, `EACCES` повторяются с отступом
  10 → 250 мс до потолка 5 с суммарного ожидания; `ENOSPC` и остальное отказывают сразу.
- `removeByPrefix` — удаляет файлы, у которых имя начинается с префикса **и** подходит под шаблон
  ключа; возвращает отчёт с удалёнными и неудалёнными.
- `isTempName` — временный файл записи: `<конечное имя>.<12 hex>.tmp`.

Сценарии сбоя написаны до реализации (execution note плана): файл тестов сначала упал на
отсутствующем модуле, затем прошёл целиком. Сбои вводятся подменой среза файловой системы
`AtomicFs` поверх настоящей; время — подставными часами, тесты не ждут.

Решения, которые план оставил юниту:

- **Ошибка записи — исходная ошибка файловой системы с её кодом**, без своей обёртки. В доменный
  код (нет места, файл занят) её переведёт хранилище (U13), которое знает, что именно писалось.
- **Шаблон ключа — обязательный аргумент `removeByPrefix`**, а не константа помощника: шаблон

### U6. Разбор XML: capabilities и status — ✅ зелёный

- `src/core/escl/xml.ts` — сборщик дерева поверх `saxes` 6.0.0 и все правила недоверенного входа
  ([ADR 0006](../decisions/0006-device-xml-parsing.md), KTD-32): строгий UTF-8, отказ на `<!DOCTYPE`
  и `<!ENTITY` до разбора и на событии разборщика, потолки размера (1 МБ), глубины (32) и числа
  узлов (20 000). Элементы сопоставляются по URI пространства имён. Имя элемента — значение поля,
  а не ключ объекта: `<__proto__>` ничего не подменяет.
- `src/core/escl/capabilities.ts` — идентичность устройства, наличие планшета и двусторонней
  автоподачи, пределы региона, режимы, форматы и разрешения **односторонней автоподачи**.
- `src/core/escl/status.ts` — состояние устройства и лотка, список заданий с адресом, состоянием,
  числом страниц и возрастом.

Коды отказа — в `ERROR_CODES` со строками локали: `scannerBadResponse` (причина в деталях),
`notEsclScanner`, `scannerNoAdf`, `scannerNoJpeg`.

Решения, которые план оставил юниту:

- **Обработчика ошибок у `saxes` нет намеренно:** без него разборщик бросает исключение на первой
  ошибке разметки, и разбор останавливается, а не продолжается по испорченному документу. Потолки
  глубины и числа узлов срабатывают тем же путём — исключением из обработчика события.
- **Профиль настроек берётся один** — первый с JPEG, хотя бы одним режимом и одним разрешением.
  Значения разных профилей между собой не сочетаются, и объединение предложило бы пользователю
  сочетание, которого устройство не обещало.
- **Диапазон разрешений** (`ResolutionRange`) раскладывается в ходовые значения 75–2400 dpi,
  попадающие в диапазон и на шаг: предлагать 137 dpi незачем.
- **Список заданий в статусе разбирается** сверх «состояния устройства и лотка» из плана: по нему
  U10 найдёт задание с неизвестным адресом (журнал, U1, KTD-11).
- **Неизвестное значение состояния — `null`,** а не строка устройства.

Найдено по ходу: управляющий символ C0 в ответе (кроме табуляции и переводов строк) — уже ошибка
разметки XML, до чистки строк для показа дело не доходит. Чистка оставлена для того, что XML
пропускает: табуляция, переводы строк, диапазон C1.

**Отклонение от плана (осознанное):** варианты для интерфейса — «размеры листа, которые помещаются
в регион автоподачи» — выводятся не здесь, а в U7: лист помещается тогда и только тогда, когда
функция региона его принимает, а она появляется в U7. Здесь capabilities отдаются как заявлены,

### U7. Регион в 1/300 дюйма и ScanSettings — ✅ зелёный

- `src/core/escl/region.ts` — `regionFor(лист, пределы автоподачи)`: единственное место, где
  размер листа переводится в единицы протокола. Параметра разрешения у функции нет — независимость

- `src/core/escl/scan-settings.ts` — `scanOptionsOf` (варианты для интерфейса) и
  `buildScanSettings` (тело `POST /ScanJobs`). Проверка параметров и список вариантов — один и тот
  же расчёт: что не предложено, то и не принимается.

Правила, взятые из наблюдений U1:

- **Лист ставится по центру поля:** `XOffset = ⌊(MaxWidth − ширина) / 2⌋`, для A4 на ET-3850 — 35,
  для Letter — 0; `YOffset` — 0. Заявленная устройством юстировка в расчёт не идёт.
- **Доли единицы отбрасываются:** A4 — 2480 × 3507, а не 3508; регион не выходит за лист.
- **Пределы региона проверяются у нас:** лист шире, длиннее или меньше пределов автоподачи —
  отказ `scanParamsUnsupported` с полем в деталях, а не молчаливая обрезка.
- **`BlackAndWhite1` не предлагается и не принимается** ни для какого устройства: страницы
  приложение берёт только в JPEG, а ET-3850 на это сочетание отвечает `409`.
- **Запрос для A4, серого, 300 dpi совпадает с принятым устройством байт в байт** (фикстура
  `ScanSettings.a4-gray-300.xml`); элемента `Intent` нет.

Решения, которые план оставил юниту:

- **Листов два — A4 и Letter,** как в `UI_SPEC.md`; «Авто» в M1 не показывается (KTD-25).
- **Версия протокола в запросе повторяет версию устройства,** если та вида «число.число»; иначе —

  запасное значение — допущение.
- **Значения подставляются через экранирование,** хотя до шаблона доходят только числа и значения
  перечислений: проверка по вариантам стоит раньше.

Устройство, у которого после исключения `BlackAndWhite1` не остаётся ни одного режима, получит
пустой список вариантов; отказ подключения для такого устройства — дело U11.

### U8. Транспорт и изоляция TLS — ✅ зелёный

- `src/core/escl/transport.ts` — `createTransport(профиль)`: свой агент на профиль, запрос с телом
  в памяти (`request`) и страница потоком (`stream`). Единственный файл в `src/` с ослабленной
  проверкой TLS.
- `src/core/escl/device-path.ts` — проверка путей устройства (KTD-7): базовый путь, путь под базой,
  путь задания из `Location` или `JobUri`.
- `eslint.config.ts` — исключение `duplexnt/tls-scanner-transport`: файлу транспорта разрешена
  ровно опция агента; переменная окружения, обработчики Electron, ключи Chromium и границы слоя
  остаются под запретом и в нём.
- `test/integration/tls-isolation.test.ts` — R11 и AE13 на продуктовом коде.
- `test/support/self-signed-cert.ts`, `test/support/loopback-server.ts` — сертификат на лету и
  локальный сервер для тестов сетевого слоя.

Как устроены инварианты:

- **Отпечаток сверяется до отправки запроса** (KTD-40). Запрос не уходит в сеть, пока не вызван
  `end`, а он вызывается из обработчика `secureConnect` после сверки. Тест поднимает на том же порту
  сервер с другим сертификатом: соединение одно, до обработчика сервера не дошло ничего.
- **Соединение на запрос** (`keepAlive: false`): каждое соединение — новая сверка. Устройство и так
  отвечает `Connection: close`.
- **Путь проверяется до сети:** абсолютный URL, `//хост`, соседний префикс, точечные сегменты,
  запрос — отказ без единого соединения.
- **Ответ 3xx отдаётся вызывающему статусом;** `node:http` переходов не исполняет, тест это
  закрепляет для 301, 302, 307 и 308.
- **Потолок XML** — по заявленному `Content-Length` до чтения и по сосчитанным байтам при чтении.
  При лживом `Content-Length` лишнее не принимается.
- **Страница — потоком** с потолком по сосчитанным байтам, таймаутом тишины и общим сроком обмена.
  Тело отдаётся только у ответа `200`; у остальных статусов соединение закрывается сразу.
- **Сбои — кодами в конверте:** `scannerUnreachable` с причиной (`refused`, `tls`, `timeout`,
  `reset`, `dns`, `network`), `scannerCertificateChanged`, `canceled`. Причина нужна U11: переход на
  HTTP разрешён при отказе соединения и сбое рукопожатия, но не при таймауте (KTD-8).
- Из заголовков ответа наружу выходят только `Location` и `Content-Type` — сырыми значениями;
  `Retry-After` не читается, сжатие не запрашивается.

**Способ генерации тестового сертификата (KTD-29, отложенный вопрос плана) — третий вариант:**
сертификат собирается вручную в DER и подписывается `node:crypto`. Ни пакета в `devDependencies`,
ни `openssl` из поставки Git: `test:all` не зависит от внешнего бинарника, ключ живёт только в
памяти. Сертификат выписан на `localhost` и `127.0.0.1`, поэтому строгий клиент отклоняет его по
одной причине — самоподпись; проверено отдельно: с этим сертификатом в доверенных корнях тот же
клиент сервер принимает.

Грабли:

- **Разборщик URL молча чинит `Location`:** превращает обратный слэш в прямой, схлопывает точечные
  сегменты, выбрасывает табуляцию и переводы строк. Проверки пути задания поэтому идут по сырому

**Отклонение от плана (осознанное):** добавлены `src/core/escl/device-path.ts` с тестом и

### Ревью сессий 2–3: simplify

По решению автора ревью не ждёт U25: фундамент и клиент до транспорта смотрятся сейчас. Первый шаг
— упрощение кода сессий 2 и 3 (восемь коммитов после `7b3b24f`) тремя независимыми ревьюерами:
повторное использование, качество, эффективность. Находок 18, применено 7, поведение сохранено.

Применено:

- причины отказа `scannerBadResponse` собраны в один тип `BadResponseReason` — опечатка в причине
  больше не компилируется (`xml.ts`, `capabilities.ts`, `transport.ts`);
- `rangeResolutions` берёт потомка готовым `descendantOf` вместо двух ручных проверок на `null`;
- проверка пути в `device-path.ts` стала предикатом `isCleanPath`; из `jobPathFromLocation` убрано
  условие, которое `isUnderBase` и так проверяет;
- **слушатель ошибки запроса в транспорте — `on`, а не `once`:** ошибка сокета после заголовков
  ответа приходит и в запрос; вторая такая ошибка осталась бы без слушателя и стала бы
  необработанным исключением в main. Находка ревьюера эффективности, по сути — баг;
- страж тестовых прогонов не ходит по каталогам с точкой и `coverage`;
- обход `src/` в тесте изоляции TLS заменён рекурсивным `readdirSync`.

Не применено и почему:

- **Поток страницы, который не начали читать, держит соединение до таймаута тишины.** Если
  `writeStreamAtomic` упал на открытии временного файла, до итерации тела дело не доходит, и
  `finally` генератора не исполняется. Починка меняет контракт `stream` (явное закрытие) — это не
  упрощение, а решение для код-ревью и U10. Утечка ограничена таймаутами.
- Общий загрузчик разобранных capabilities ET-3850 в `test/support`: помощник там, импортирующий
  `src/`, стал бы ловушкой для эмулятора — линтер проверяет только прямые импорты.
- Объединение `errorCode` из двух модулей, общий `encode` в тестах, общий помощник «список
  дочерних элементов», снятие `export` с констант без потребителей — выигрыш меньше цены.

Гейт после упрощения: `typecheck`, `lint`, `format:check`, `test:all` зелёные (427 + 8). Коммит
`refactor(m1): U6–U8 упрощение…`. Следующий шаг — код-ревью того же объёма.

### Ревью сессий 2–3: код-ревью

Многоагентное ревью того же объёма: десять ревьюеров (корректность, безопасность, состязательный,
надёжность, тесты, сопровождаемость, стандарты проекта, контракт моста, агентная доступность,
прошлые уроки). Находки, требующие суждения, прошли независимую проверку; проверяемые фактом —
подтверждены падающим тестом до правки. Применено одиннадцать правок, поведение закреплено тестами.

**Главная находка — P1, её независимо воспроизвели три ревьюера.** Под обычным Node (OpenSSL)
возобновлённая сессия TLS не отдаёт сертификат вовсе: `getPeerCertificate()` возвращает пустой
объект. Сверка отпечатка получала `null` и отвечала «по адресу другое устройство» на втором и
следующих запросах к настоящему сканеру. Под Node из Electron (BoringSSL) сертификат на
возобновлённой сессии есть, поэтому в приложении ошибка не проявилась бы — но `npm test` и живые
тесты идут под обычным Node, и живой тест задания в сессии 4 упал бы на втором запросе. Тесты
этого не видели: ни один не делал двух успешных запросов подряд через транспорт с запомненным
отпечатком. Запись журнала U1 «сертификат на всех соединениях один» была верна для полных
рукопожатий; на возобновлённых скрипт съёмки отпечатка не получал.

Исправление — транспорт сам ведает возобновлением: кэш сессий агента выключен (он запоминает
сессию до сверки, то есть и сессию подменного устройства); запоминается сессия только соединения,
прошедшего сверку, вместе с отпечатком; на возобновлённом соединении берётся отпечаток, привязанный
к предложенной сессии. Соединение HTTPS, на котором отпечаток узнать нельзя, — отказ. Дешёвые
повторные соединения (10–20 мс против 0,7 с) сохранены.

Остальные правки:

- **Обмен, который не кончается.** На ответ `101 Switching Protocols` Node закрывает запрос без
  события ответа и без ошибки — `request` и `stream` висели вечно, таймауты и отмена до закрытого
  сокета не дотягивались. Добавлен слушатель закрытия запроса.
- **Общий срок запроса по умолчанию — 10 с** (KTD-14). Раньше срока не было: ответ, который цедят
  по байту чаще таймаута тишины, держал запрос сколько угодно. У страницы потолок размера, таймаут
  тишины и общий срок стали обязательными параметрами — умолчаний у них нет.
- **Контракт страницы изменён: `stream(параметры, получатель)`.** Тело отдаётся получателю, а
  соединение, таймеры и подписку на отмену закрывает транспорт — когда получатель вернул значение
  или бросил исключение, в том числе не начав читать. Это снимает вопрос, отложенный при упрощении:
  уборка больше не зависит от дисциплины вызывающего. Исключение получателя, не связанное с сетью
  (например, отказ записи на диск), пробрасывается как есть.
- **Исключение обработчика команды больше не уходит в окно дословно:** в сообщении бывают пути.
  Полная ошибка остаётся в журнале main, в окно — только имя команды. Сам вызов без защиты — код
  M0, но обработчиков с файлами и сетью до сих пор не было.
- `regionFor` на листе мимо перечисления отвечает отказом, а не `TypeError`.
- `jobPathFromLocation` отклоняет любой `%` по сырому значению: `/eSCL/ScanJobs/x/%2e%2e/y`
  проходил как `/eSCL/ScanJobs/y`. Вреда не было — путь оставался под коллекцией, — но
  документированное правило «кодирование — отказ» не выполнялось.
- `removeByPrefix` отклоняет шаблон с флагом `g` или `y`: такой шаблон помнит позицию между
  вызовами, половина файлов осталась бы на диске при отчёте «неудалённых нет».
- Исключение при запуске main завершает процесс: иначе он остался бы без окна, но с блокировкой
  экземпляра, и приложение не открылось бы и повторным запуском.
- Страховочные тесты: каждый код ошибки имеет строку в локали и лишних строк нет; скрипты
  `package.json` называют каждый проект vitest; тест с лживым `Content-Length` закрепляет точный
  исход вместо «подойдёт любой».

Отклонено проверкой: «нет кода ошибки хранилища» — это записанная отсрочка до U13, в этом объёме
ошибки `atomic-file` через мост не идут.

### U10. Задание автоподачи — ✅ зелёный

`src/core/escl/scan-job.ts` — `runScanJob`: `POST /ScanJobs` → страницы в приёмник → `DELETE`.
Правила конца и обрыва — по разделу «Что наблюдения меняют в решениях плана», а не по исходному
KTD-9: `503` на `NextDocument` — повтор, `404` после страниц — конец, `404` на первой — пусто,
`410` и любой сбой обмена — обрыв.

Что возвращает задание:

- **отказ в конверте — задания на устройстве нет**, закрывать нечего: `scannerBusy` (занятость
  дольше потолка), `scanParamsRejected` (`409`), сбой сети на `POST`, неожиданный статус;
- **отчёт — задание создавалось:** исход (`completed`, `empty`, `canceled`, `interrupted`), число
  целых страниц, адрес задания и признак, удалось ли его закрыть. У `interrupted` причина одного
  из двух родов: отказ устройства (доменная ошибка) или отказ на нашей стороне — исключение
  приёмника, например запись на диск.

Как устроено:

- **Страница проверяется внутри потока, до переименования.** Приёмник получает тело, обёрнутое в
  проверку маркеров JPEG: начало сверяется раньше, чем первый байт уйдёт приёмнику, конец — когда
  тело дочитано по обрамлению. Сбой проверки — исключение из потока, и `writeStreamAtomic` до
  `rename` не доходит. Пустой ответ `200` — отказ `emptyPage`, а не файл нулевой длины. Приёмник,
  вернувшийся не дочитав тело, страницу не получает: она не проверена.
- **`POST` и `DELETE` сигнала отмены не получают** (KTD-10). Отмена при `POST` в полёте дожидается
  ответа и закрывает задание; отмена в паузе ожидания занятости задания не создаёт.
- **`DELETE` идёт при любом исходе,** `2xx` и `404` — успех (KTD-11). После обычного конца
  устройство отвечает `404`: задание оно закрыло само.
- **Обработчики вызывающего:** `onJobCreated` — адрес сразу после `201`, до первой страницы
  (KTD-11); `onEnd` — исход до `DELETE` (KTD-17: «завершён» пишется раньше закрытия задания);
  `onPhase` — «занят» и «сканирую» для состояния ожидания (R7). Их исключение обрывает задание так
  же, как исключение приёмника; `DELETE` всё равно уходит.
- Пределы — `SCAN_JOB_LIMITS`: повтор `503` раз в секунду, занятость до 60 с, серия `503` между
  страницами до 30 с, тишина 90 с, страница целиком до 5 минут и до 64 МБ, до 500 страниц,
  `DELETE` 5 с. Время и пределы подставляются — тесты не ждут.

Решения, которые план оставил юниту:

- **Негодный `Location` — задание закрывается по статусу** (отложенный вопрос плана, ответ из U1).
  Клиент читает `ScannerStatus`, берёт `JobUri` единственного задания в состоянии `Processing` и
  шлёт ему `DELETE`. Очереди у устройства нет, поэтому сразу после нашего `201` идущее задание —
  наше. Если таких заданий не одно или статус не читается — исход «задание не закрыть»: адрес
  `null`, устройство снимет задание само через пять минут. Страницы по найденному адресу не
  берутся: устройство, приславшее негодный адрес, — уже ошибка протокола.
- **Три новых кода со строками локали:** `scannerBusy`, `scanParamsRejected`, `scanFeedFailed`
  (причина в деталях: `gone` — ответ `410`, `notReady` — серия `503` дольше потолка). Причины
  `scannerBadResponse` пополнены: `status`, `location`, `notJpeg`, `emptyPage`, `tooManyPages`.
- **Задание принимает готовое тело запроса,** а не параметры: `buildScanSettings` может отказать, и
  вызывающий (U17) обязан узнать об этом до записи сегмента в журнал.
- **Лоток перед заданием здесь не читается** — это шаг службы прохода (U17), как и закрытие
  незакрытых заданий. Для него экспортирован `closeScanJob`.

Тесты — в два слоя. `scan-job.test.ts` (39) — логика на подставном транспорте с подставным
временем: потолки, отмена в каждой точке, порядок обработчиков, разбор маркеров по байту.
`test/integration/scan-job.emulator.test.ts` (31) — настоящая цепочка: продуктовый транспорт по

### U11. Подключение по адресу — ✅ зелёный

`src/core/escl/connect.ts`:

- `parseScannerAddress` — ручной ввод в структуру: хост, хост с портом или полный URL. Разбор
  своим шаблоном, без разборщика URL: тот молча чинит ввод (схлопывает `..`, нормализует хост), а
  здесь всё непонятное — отказ `invalidInput` с названием поля, без обращения к сети.
- `createConnector().connect(адрес)` — проба capabilities временным транспортом; профиль
  создаётся только когда устройство ответило, capabilities разобраны, есть автоподача, JPEG и хотя
  бы один вариант каждого параметра. Транспорт пробы уничтожается при любом исходе (KTD-39).

Правила:

- **Схема (KTD-8).** Не названа — HTTPS первым; переход на HTTP только при отказе соединения
  (`refused`) и сбое рукопожатия (`tls`), не при таймауте, DNS и обрыве. Явная схема не меняется
  никогда. Выбранная схема записана в профиль.
- **Порт при переходе на HTTP** (отложенный вопрос плана): названный пользователем сохраняется, не
  названный — 443 для HTTPS и 80 для HTTP. Это же правило подходит обнаружению: ET-3850 объявляет
  оба сервиса на одном порту.
- **Обе попытки отказали — возвращается отказ второй:** в обычном случае (устройство только на
  HTTP) он содержательнее.
- **Отпечаток — из первого ответа,** проба идёт без запомненного. Подключение — явное действие
  пользователя; сверка с запомненным отпечатком — дело транспорта профиля и настроек (U15).
- **Одно подключение за раз:** новое отменяет идущее; отменённое возвращает `canceled`, даже если
  его проба успела завершиться успехом.
- **Пустой путь и одиночный слэш — `/eSCL`.** Корень как базовый путь ручным вводом не задать;
  запись `rs` из mDNS идёт через `normalizeBasePath` напрямую.
- **Имя хоста — ASCII:** буквы, цифры, дефис, подчёркивание, точки; IPv4 под это правило подходит.
  Литерал IPv6 и имена не в ASCII — `invalidInput`: IPv6 в M1 не используется (KTD-12).

`reason`, а не отдельными кодами. Интерфейсу M1 нужны четыре состояния устройства, а не словарь
причин; текст по причине, если понадобится экрану `device`, выбирается в renderer по
`details.reason`. Типизация деталей в `shared` — когда появится первый такой текст (U21).

Тесты: `connect.test.ts` (57) — разбор ввода и выбор схемы на подставной фабрике транспортов;
`test/integration/connect.emulator.test.ts` (10) — эмулятор на HTTPS и HTTP, закрытый порт,
молчащий сервер, страница HTML. Отказ «хост не найден» воспроизводится только подставным
транспортом: настоящий запрос DNS сделал бы `test:all` зависимым от сети. Проверено мутациями:

### U12. Обнаружение по mDNS — ✅ зелёный

- `src/core/discovery/txt.ts` — чистые функции: разбор TXT, запись о сканере из объявления,
  слияние записей по KTD-12.
- `src/core/discovery/mdns.ts` — `startDiscovery`: по экземпляру библиотеки на каждый внешний
  IPv4-интерфейс с `reuseAddr` (амендмент ADR 0003), оба сервиса на каждом. Библиотека спрятана за
  узким интерфейсом `MdnsBackend`; тесты подменяют его и сокетов не открывают.
- `src/shared/discovery.ts` — то, что видит интерфейс: `DiscoveredScanner` (идентификатор, имя,
  адрес, порт, признак автоподачи) и `DiscoveryState` (список и причина сбоя).
- Событие `discoveryChanged` с номером — в карте `BridgeEvents`, подписка `onDiscoveryChanged` — в
  preload. Источника у события пока нет: команды поиска и отправку подключает U18.

Новая зависимость — `bonjour-service` 1.4.4 в `devDependencies` (тянет `multicast-dns` 7.2.5);
`npm audit` чист.

Правила:

- **Список строится только по объявлениям** (KTD-12): capabilities у найденных устройств не
  запрашиваются, ссылки из TXT наружу не выходят. В снимке для интерфейса нет ни UUID, ни пути.
- **Слияние:** записи — одно устройство, когда совпадают адрес с портом и UUID; объявление без
  UUID схлопывается по адресу и порту. Один UUID с двух адресов — две записи. Слияние идёт на месте
  записи, список только растёт — до потолка в 64 записи.
- **Идентификатор — метка поиска и место в списке.** Интерфейс передаёт ядру его, а не адрес;
  идентификатор прошлого поиска в новом не действует. Устройство без `adf` в TXT в списке есть, но
  адреса по идентификатору не получает — выбрать его нельзя.
- **Адрес для подключения — IPv4 из объявления, схема не названа:** HTTPS первым, HTTP — при
  отказе, на том же порту. Адреса IPv6 в M1 не используются.
- **`rs` идёт через `normalizeBasePath`;** отсутствующий, пустой и негодный (`?`, `..`, кодирование)
  дают `/eSCL`: устройство остаётся в списке, а подключение само проверит capabilities.
- **Сбой отличим от пустого результата:** `noNetwork` — внешних интерфейсов нет, `socket` — ни один
  сокет не открылся или все отказали позже. Сбой одного интерфейса из двух поиск не останавливает.

Решения, которые план оставил юниту:

- **TXT разбирается своим кодом из сырых записей,** а не берётся разобранным у библиотеки. Её
  разбор наивен: запись `note=` у неё становится ключом `note=` со значением `undefined` — отсюда
  «буквальный ключ `note=`» в плане. Свой разбор делит запись по первому знаку равенства, сводит
  ключи к нижнему регистру, не даёт повтору ключа перезаписать первое значение и кладёт всё в
  `Map`, а не в объект.
- **Запрос повторяется: через 1, 2, 4 с и дальше каждые 8 с, пока идёт поиск.** Библиотека шлёт
  запрос один раз, при старте. См. «Грабли».
- Имя для показа — `ty` из TXT, иначе имя экземпляра сервиса, иначе `null`; текст-заглушку
  выбирает интерфейс.

**Грабли: первый живой прогон вернул пустой список без единой ошибки.** Шесть секунд поиска на
двух интерфейсах, сокеты открыты, сбоя нет — и ноль устройств. Спайк M0, запущенный следом, нашёл
сканер; восемь следующих прогонов продуктового кода нашли его за 0,2 с. Это тот же симптом, что
записан в амендменте ADR 0003 («один прогон из нескольких вернул пустой результат»), и перебор
интерфейсов его, выходит, не исключает. Причина не установлена; гипотезы — потерянный пакет
multicast или устройство, которое после простоя отвечает не на первый запрос. От обеих помогает
одно: повтор запроса. Он добавлен. **Поправка по итогам код-ревью сессии 4:** утверждение «после
повтора пустой прогон не повторялся» замер опроверг — причина и цифры в разделе «Что показал
замер на устройстве».

**Проверено на этой машине и сети:** настоящая библиотека под обычным Node — два внешних
интерфейса (Ethernet и виртуальный Hyper-V), ET-3850 найден, объявления `_uscan` и `_uscans`
слились в одну запись с автоподачей, базовый путь `/eSCL`, порт 443; остановка освобождает
сокеты, процесс завершается сам. В вывод проверки шли только счётчики.

**Не проверено агентом:** библиотека внутри бандла main и в установленном приложении — модуль
пока никто не импортирует из main; проверится сборкой, когда U18 подключит команды поиска, и живым
смоуком U25. Запрос файрвола Windows при первом поиске из установленного приложения — там же.

**Отклонения от плана (осознанные):** добавлены `src/shared/discovery.ts` и событие в
`src/shared/bridge.ts` с подпиской в preload — в списке файлов юнита их нет; событие обещал журнал
сессии 2. Повтор запроса — сверх описанного в плане подхода.

**Готово:** `typecheck`, `lint`, `format:check`, `test:all` зелёные (624 + 49, живой тест
пропущен); `npm run build` проходит. Коммит `feat(m1): U12 обнаружение по mDNS…`.

### Ревью сессии 4: simplify

По решению автора ревью кода сессии 4 (U9–U12, пять коммитов после `775fe16`) идёт сейчас, не
дожидаясь сессии 5. Первый шаг — упрощение тремя независимыми ревьюерами: повторное использование,
качество, эффективность. Находок 30, применено 16, из них одна — баг; ещё одна закрыта тестом.

**Баг, найденный ревьюером эффективности: брошенный открытым сокет mDNS.** Экземпляр попадал в
список живых только после начала поиска. Если `browse` бросал исключение, сокет на порту 5353 уже
был открыт, но в списке его не было: его не закрывали ни обработчик сбоя, ни `stop()`. Теперь
экземпляр учитывается сразу после открытия; закреплено тестом, который на прежнем порядке падает.
Заодно уведомление `onChange` не уходит, пока поиск собирается: вызывающий в этот момент ещё не
получил объект поиска.

Применено, поведение сохранено:

- базовый путь по умолчанию — одна константа `DEFAULT_BASE_PATH` в `device-path.ts`; обнаружение
  больше не пересобирает `/eSCL` из `eSCL` и не несёт мёртвую ветку;
- причины отказа в подключении сверяются по типам `BadResponseReason` и `UnreachableReason`, а не
  по строкам: опечатка в причине перестала компилироваться;
- в задании отказ с неожиданным статусом на `POST` собирается тем же помощником, что и на
  странице; конструкторы исходов стоят рядом;
- обнаружение: открытие экземпляра вынесено в функцию с объяснением, зачем состояние лежит в
  объекте; таймер повтора запроса гаснет, когда отказали все сокеты; поиск записи по
  идентификатору — без промежуточного индекса;
- эмулятор: убраны опции `basePath` и `cert`, которыми никто не пользовался; страницы-фикстуры
  читаются с диска один раз на процесс, а не на каждый запуск; слушатель закрытия сокета ставится,
  только когда есть кому сообщать; запись в уже закрытое соединение не ждёт события, которое не
  придёт; путь к фикстурам устройства — из общего помощника;
- тесты задания: транспорт к эмулятору строится в одном месте.

**Два теста ждали времени, а не состояния** — и под нагрузкой могли упасть. «Отмена во время
страницы» отменяла задание через 150 мс и требовала, чтобы первая страница к этому моменту была
записана; теперь тест ждёт, пока эмулятор начнёт отдавать вторую страницу. «Занятость, затем
успех» шла с потолком ожидания 80 мс на три повтора; потолок там не предмет проверки и поднят.
Таймаут тишины в соседнем тесте — со 100 до 200 мс.

**Непокрытое поведение эмулятора получило тест,** а не было удалено: «занятость после остановки»
(`busyAfterCancelMs`) ни один тест не включал. Наблюдение U1 за ней стоит, и службе прохода (U17)
оно понадобится.

Не применено и почему:

- общие тестовые помощники (`address`, `errorOf`, `deviceError`, транспорт к эмулятору) в
  `test/support` — тот же довод, что в ревью сессий 2–3: помощник там, импортирующий `src/`, —
  ловушка для эмулятора, линтер проверяет только прямые импорты;
- общий помощник для двух циклов повтора `503` в задании — потолки, причины и уведомления у них
  разные, общий код читался бы хуже двух блоков по десять строк;
- разбор индекса из идентификатора найденного сканера, отдельные переменные вместо пары в проверке
  маркеров JPEG, потолок журнала запросов эмулятора — выигрыш меньше цены: записей не больше 64,
  частей страницы — тысячи;
- замена своей проверки IPv4 на `net.isIPv4` — поведение не то же: она отклоняет октеты с ведущим
  нулём.

Оставлено следующим: объявления приходят пачкой — по одному на сервис и интерфейс, — и на каждое
новое `onChange` срабатывает отдельно; склеивать их перед отправкой события в окно — дело U18.

Гейт после упрощения: `typecheck`, `lint`, `format:check`, `test:all` зелёные (628 + 49, живой
тест пропущен); интеграционные тесты задания и подключения под Node из Electron — 41 из 41. Коммит
`refactor(m1): U9–U12 упрощение…`. Следующий шаг — код-ревью того же объёма.

### Ревью сессии 4: код-ревью

Многоагентное ревью того же объёма: десять ревьюеров (корректность, безопасность,
состязательный, надёжность, тесты, сопровождаемость, стандарты проекта, контракты, агентная
доступность, прошлые уроки). После слияния дублей — шесть находок выше порога уверенности; пять
подтверждены независимой проверкой или воспроизведением и исправлены, одна отклонена. Семь находок
низкой уверенности отсеяны порогом.

**P1 — ошибка сокета mDNS роняла бы main.** `bonjour-service` зовёт обработчик из конструктора
только при сбое ответа на чужой запрос. Ошибки самого сокета — порт не открылся, адреса интерфейса
уже нет — приходят событием `error` вложенного `multicast-dns`, на которое библиотека не
подписана: необработанное исключение. Находку независимо принесли три ревьюера, двое воспроизвели
на установленной библиотеке, проверяющий воспроизвёл третий раз. Тесты этого не видели: подставная
библиотека моделировала путь ошибки, которого у настоящей нет. Адаптер подписывается на сокет сам;
закреплено тестом на настоящей библиотеке с адресом интерфейса, которого у машины нет.

**P2 — первое объявление побеждало.** Для известного сервиса библиотека адреса не обновляет вовсе,
а о смене хоста, порта и TXT сообщает событиями `srv-update` и `txt-update`. Мы слушали только
`up`, поэтому неполное или чужое объявление под тем же именем заслоняло настоящее до конца
поиска; повтор запроса не помогал — ответ на него библиотека считала уже известным. Исправлено
тремя шагами в адаптере: обновления сервиса пересылаются как объявления; список известных
сервисов библиотеки очищается перед каждым повтором; адреса хостов запоминаются из всех ответов и
подставляются объявлению, пришедшему без записи A. Проверено на настоящем классе поиска
библиотеки с подставным сокетом — без сети.

**P2 — исключение `onPhase` после создания задания оставляло задание открытым.** Вызов стоял вне
защищённого блока, хотя журнал U10 утверждал обратное. Теперь он внутри, после записи адреса:
исключение обрывает задание с причиной `sink`, `DELETE` уходит. Исключение `onPhase('busy')`
пробрасывается — задания ещё нет; это записано в описании контракта.

**P2 — локальный помощник `badResponse` в задании** делил имя с помощником из `xml.ts` при другом
типе результата. Переименован в `protocolError`; сводить три модуля к одному помощнику проверяющий
счёл лишним.

**P3 — список известных сервисов библиотеки рос без потолка** мимо наших 64 записей. Закрыто той
же очисткой перед повтором запроса; память адресов ограничена 256 хостами.

Отклонено проверкой: «при негодном `Location` не вызываются `onJobCreated` и `onEnd`». Сегмент
пишется в журнал до `POST` и при запуске считается прерванным, так что исход восстановим без
обработчиков; адрес и признак закрытия несёт отчёт. Правило записано в описании контракта и
закреплено тестом.

#### Что показал замер на устройстве

Живая проверка после правок сначала дала пустой прогон — и опровергла запись выше, в U12, о том,
что повтор запроса пустые прогоны убрал. Замер на сыром уровне библиотеки (56 прогонов) и
продуктовым кодом (130 прогонов):

- **Первый запрос ET-3850 оставляет без ответа часто:** в 7 прогонах из 24 первый ответ пришёл
  только после повтора через секунду, а при прогонах вплотную — почти всегда. Это и есть «пустой
  результат без ошибки» из M0; перебор интерфейсов, которому амендмент ADR 0003 приписал
  исправление, тут ни при чём.
- **Устройство иногда молчит несколько секунд подряд:** один прогон из сорока не получил ни одного
  ответа за 4 с при трёх отправленных запросах.
- **Запись A приходит не в каждом ответе:** в одном из прогонов из двух ответов адрес был только в
  одном. Находка ревью про объявление без адреса — наблюдаемое поведение, а не гипотеза.
- **Итог для приложения:** при поиске до 20 с сканер найден в 60 прогонах из 60. За полсекунды —
  в 9, до полутора секунд — в 46, до трёх с половиной — в 4, самый долгий — 7,3 с. Текст «ничего
  не нашлось» через 10 с при идущем поиске (KTD-14) с этим согласуется.

Причина молчания не установлена; гипотеза — ограничение частоты ответов в самом устройстве:
замеры шли вплотную друг за другом, чего приложение не делает.

Отсеяно порогом уверенности и оставлено записью:

- **устройство только на HTTP, которое рвёт соединение в ответ на рукопожатие TLS:** Node сообщает
  обрыв, а не сбой рукопожатия, и перехода на HTTP не будет. Эмулятор этого не показывает: сервер
  Node отвечает на рукопожатие текстом `400`. Правка — в транспорте (обрыв до конца рукопожатия
  считать его сбоем); без такого устройства под рукой не делалась;
- объявление mDNS может указать на loopback или адрес вне сети — подключение всё равно проверяет
  capabilities, а адрес виден пользователю;
- пустые `catch` при закрытии сокета, который мог не открыться;
- словарь причин сбоя поиска лежит вне `ERROR_CODES` — решить в U18;
- причина `sink` несёт исходную ошибку без доменного кода — перевод за U13.

Сверх находок: тест «занятость после остановки» ждёт конца окна повторами, а не паузой; подписка
`onDiscoveryChanged` проверена на свой канал.

## Сессия 5 — сессия на диске: хранилище, сверка, настройки, миниатюры

### U13. Хранилище сессии — ✅ зелёный

- `src/core/storage/layout.ts` — раскладка каталога данных и ключ страницы
  `p<проход>-s<сегмент>-<номер>`: по две цифры на проход и сегмент, четыре на номер в сегменте.
- `src/core/storage/journal.ts` — строгая схема журнала на `zod` с маркером версии и то, что из
  журнала выводится: состояние прохода, страницы, идущий сегмент.
- `src/core/storage/session-store.ts` — `createSessionStore`: операции над сессией, строго по
  очереди.
- `src/core/storage/unclosed-jobs.ts` — незакрытые задания сканера, свой файл в корне данных.
- `src/shared/snapshot.ts` — часть снимка, которую отдаёт хранилище: сессия, проходы, страницы.

Порядок записи — то, на чём держится «отсканированное не теряется»:

- **Начало сегмента обязано записаться до старта** (KTD-17). Не записалось — операция отклонена,
  состояние прежнее.
- **Страница: временный файл → `fsync` → переименование → перезапись журнала** (KTD-18). Отказ
  журнала после переименования страницу не теряет: состояние в памяти помечается несохранённым,
  следующая запись журнала его доводит (KTD-36); есть и явный `flush()`.
- **«Остановить»: пометка в журнале → удаление по префиксу → снятие пометки** (KTD-20). Пометка
  не записалась — файлы целы, сегмент становится прерванным. Неудаляемый файл оставляет пометку.
- **Остановка, после которой в сессии нет страниц, закрывает сессию** — переименованием каталога
  в `session.closing-<id>` и очисткой (KTD-33). Не переименовался — сегмент становится прерванным,
  страницы целы. Пофайлового удаления взамен нет.
- **Закрытие и удаление сегмента дожидаются идущих чтений страниц;** пока идёт закрытие, новые
  чтения не начинаются. Страница читается в буфер, дескриптор не остаётся открытым.

Записи журнала двух родов. Та, от которой зависит следующий шаг, — начало сегмента, пометка об
удалении, «оставить как есть» — обязана пройти. Остальное — страница, исход сегмента, снятие
пометки — при отказе остаётся в памяти несохранённым.

Решения, которые план оставил юниту:

- **Состояние прохода в журнале не хранится — выводится:** это состояние последнего сегмента и
  признак «принят как есть». Двух полей, которые могут разойтись, нет.
- **Страницы сегмента — счётчик `pageCount`, а не список записей.** Ключ и имя файла выводятся из
  номеров; у списка были бы состояния, которых не бывает: пропуск, повтор, порядок. План называл
  в журнале «страницы» — они там есть, но числом.
- **«Страница потеряна» в журнал не пишется:** запись есть, файла нет — это видно по диску.
  Журнал из-за потери не переписывается, а вернувшийся файл возвращает страницу.
- **Адрес задания лежит только в `unclosed-jobs.json`,** в журнале его нет: записывается сразу
  после `201`, убирается, когда задание закрыто. Так он один раз и переживает удаление сессии; в
  журнале его пришлось бы переносить при «Остановить».
- **Сканер, параметры и предел пикселей прохода — одно поле `origin`;** `null` — журнал
  пересобран по файлам, досканировать такой проход нельзя.
- **Сканер на диске — одна форма на три места** (настройки, журнал, незакрытые задания) и одно
  правило «то же ли устройство»: сравнивается всё, что известно у обоих, — отпечаток и UUID;
  расхождение в любом — другое устройство; сравнить нечем — остаётся адрес.
- **Сегмент не начинается на префиксе с файлами или пометкой** — номер сдвигается на следующий
  свободный. Потолки: 99 проходов, 99 сегментов на проход, 9999 страниц в сегменте.
- **Проверка свободного места — в начале сегмента,** запас 500 МБ (KTD-36). Не удалось узнать —
  проход не блокируется: настоящий отказ даст сама запись.
- **`acceptPage` бросает исключение, остальные операции возвращают конверт.** Ошибка источника
  (сеть, проверка маркеров в задании) пробрасывается как есть — её различает задание; отказ
  хранилища — `StorageError` с доменной ошибкой. Пустое тело до переименования не доходит.
- **Пустая сессия для интерфейса — отсутствие сессии:** журнал без единой страницы снимок не
  отдаёт. Он может остаться на диске только ради пометки об удалении.
- **Отодвинутая копия нечитаемого журнала лежит в каталоге сессии** и уходит вместе с ней при
  «Новой пачке».
- **Коды со строками локали:** `storageFull`, `storageFailed` (код файловой системы в деталях),
  `storageIncompatible`, `sessionConflict` (причина в деталях: `passRunning`, `noRunningPass`,
  `notInterrupted`, `paramsUnknown`, `noSession`), `sessionCloseFailed`, `pageUnavailable`,
  `thumbnailFailed`. Тексты черновые.

**Отклонения от плана (осознанные):** добавлены `storage-fs.ts` (срез файловой системы для
ввода сбоев и перевод её ошибок в доменные коды), `versioned-file.ts` (чтение файла с маркером
версии — одно на журнал, настройки и незакрытые задания), `stored-scanner.ts` и
`test/support/intercept-fs.ts` — в списке файлов юнита их нет. В `snapshot.ts` — только часть

**Порядок «тесты до реализации» выдержан наполовину:** сценарии порядка записи написаны раньше
кода, но первый их прогон был уже с реализацией — падающими на отсутствующем модуле я их не

### U14. Сверка при запуске — ✅ зелёный

`src/core/storage/reconcile.ts` — `reconcileSession` и `openSessionStore` (сверка и хранилище на
её результате). Таблица плана применяется сверху вниз; каждая строка — тест с тем же названием.

- **Журнал читается первым.** Маркер версии новее понятного или неизвестное поле — возврат до
  любого изменения: ни временные файлы, ни пометки, ни закрываемый каталог, ни чужой кэш не
  трогаются.
- **Пересборка — это возврат файлов в пустой журнал.** Отдельного пути нет: тот же код возвращает
  страницу без записи в свой сегмент и создаёт прерванными сегмент и проход, которых в журнале
  нет. У созданного прохода `origin` — `null`.
- **Число страниц сегмента — наибольший номер непустого файла;** пропуск в нумерации становится
  записью без файла, то есть потерянной страницей на своём месте.
- **Идемпотентность:** журнал переписывается, только если изменился; повторный прогон не делает
  ни одной записи.

Решения, которые план оставил юниту:

- **Файл нулевой длины не удаляется** — сверка его не трогает; страницей он не считается. Убирается
  только вместе с пустой сессией.
- **Размер файла не узнать — файл считается страницей:** потерянной её объявит чтение, а не
  догадка.
- **Журнал без страниц, но с пометкой об удалении остаётся:** без него неудалённые файлы
  отброшенного сегмента вернулись бы страницами при следующем запуске.
- **Нечитаемый журнал отодвигается переименованием, а если не вышло — копируется.** Не удалось ни
  то ни другое — новый журнал остаётся в памяти несохранённым, сверка старый не затирает.
- **Уведомления запуска:** `journalRebuilt` (один раз — после записи нового журнала он читается) и
  `pagesLost` (пока потерянные страницы есть).

**Баг, найденный своими же тестами до коммита:** файлы под пометкой об удалении принимались
обратно. Опись каталога снималась до удаления, и возврат страниц смотрел на список пометок уже
после того, как успешно доведённая пометка была снята. Теперь возврат смотрит на пометки, какими
они были при запуске.

**Табличный тест сбоя.** Сценарий — проход, обрыв, досканирование, «Остановить», новое
досканирование, «Новая пачка» — прогоняется столько раз, сколько в нём изменений диска: на шаге N
хранилище «убито», этот и все следующие шаги не выполняются. После каждого — сверка дважды:
подтверждённо принятая страница на месте, подтверждённо удалённая не вернулась, оборванное
удаление доведено целиком или не начато, оборванная «Новая пачка» оставила сессию целой или убрала
её, второй прогон не изменил ни байта.

Тесты написаны до реализации и упали на отсутствующем модуле (execution note плана). После —
проверены мутациями: 14 поломок, каждая роняет тесты.

**Не закрыто этим юнитом:** неожиданная ошибка чтения каталога данных (нет прав, каталог сессии —
файл) выходит из сверки исключением. Что делать с ней при запуске — решение U18.

**Готово:** `typecheck`, `lint`, `format:check`, `test:all` зелёные (725 + 51). Коммит
`feat(m1): U14 сверка при запуске…`.

воспроизведены прогоном или принесены двумя ревьюерами независимо; тринадцать прошли независимую
проверку — пять из них отклонены как вкус или косметика. Осталось пятнадцать, все P2 и P3;
применены все, кроме части одной. Каждая правка поведения сначала закреплена падающим тестом: 33
новых теста были красными до исправлений.

**Запись не проверялась собственной схемой** (корректность и стандарты проекта независимо;
воспроизведено). Схемы файлов строгие: неизвестное поле при текущей версии — несовместимость. А
запись сериализовала что дали. Лишнее поле в параметрах прохода записывалось в журнал, и после
перезапуска хранилище уходило в режим отказа на собственных данных: ни прохода, ни «Новой пачки».
Теперь запись журнала, настроек и незакрытых заданий проходит ту же схему, которой файл читается,
и перечитывается после записи — «с валидацией структуры до и после», как требует `CLAUDE.md`.
Негодное значение не попадает ни в файл, ни в память. Не удалось перечитать (файл занят) — не
отказ: атомарная запись уже прошла. Сканер для записи на диск собирается из явно перечисленных
полей профиля.

**Нечитаемый журнал мог быть затёрт** (корректность и состязательный; воспроизведено). Если сверке
не удалось ни отодвинуть, ни скопировать нечитаемый журнал, она его не трогала — но первая же
запись хранилища писала новый журнал поверх. Признак `unpreserved` идёт из сверки в хранилище:
первая запись сначала отодвигает прежний файл, а не выйдет — не делается. То же для нечитаемого
журнала без страниц: новая сессия его не затирает.

**Предел пикселей задавало само устройство** (безопасность; замер на `sharp` из репозитория).
Предел выводится из capabilities; границы разбора — 30 000 единиц и 9600 dpi — давали до
9,2·10¹¹ пикселей, и это значение заменяло встроенный предел `sharp`. Прогрессивный JPEG
30 000 × 30 000 весом 5,3 МБ строил миниатюру с пиком памяти 2,8 ГБ в main. Потолок в коде —
встроенный предел `sharp` (16 383 × 16 383): устройство и журнал могут предел только понизить.

**Проход-призрак** (состязательный; воспроизведено). «Остановить» до первой страницы при отказе
закрытия каталога оставляло в журнале пустой прерванный проход: снимок говорил «сессии нет»,
`resumeTarget()` — «можно досканировать», а следующий проход получал номер 2. Правило «пустая
сессия равна отсутствию» теперь одно на снимок, досканирование, «оставить как есть» и новый
проход. Пустой журнал с пометкой об удалении пометку и счётчики сохраняет.

Остальные правки:

- досканирование создаёт каталог страниц: без него каждый лист проходил через податчик впустую;
- **занятый сканер — «не отвечает», а не «другое устройство»** (надёжность и контракты
  независимо): ответ `5xx` и ответ, который не дочитался или не разобрался, — так ведёт себя и
  тот же сканер. Причина идёт кодом в обоих состояниях;
- проверка режима отказа — одна обёртка над всеми изменяющими операциями, а не семь копий;
- файл незакрытых заданий, который не прочитался, не переписывается: что в нём, неизвестно, в том
  числе его версия;
- имя отодвинутой копии и идентификатор сессии собираются в одном месте.

**Ошибка в собственной правке, пойманная новыми тестами:** сверка начинала запись нового журнала
раньше, чем проверяла, сохранён ли прежний, — запись шла и тогда, когда писать было нельзя.

Тесты-покрытие, которые прошли сразу:

- таблица сбоев сверяет байты принятых страниц, а не только ключи; сценарий расширен вторым
  проходом и «оставить как есть»;
- **сверка, убитая на каждом своём шаге,** доводится следующими запусками до того же — на журнале
  с пометкой, временными файлами и закрываемым каталогом и на нечитаемом журнале; нечитаемый журнал
  при этом не теряется и не размножается;
- потолки счётчиков: страница 9999 принимается, 10 000-я — отказ без файла; то же для 99 проходов и
  сегментов;
- чистка миниатюр отброшенного сегмента — в хранилище и в сверке;
- миниатюра отдаётся, когда кэш не записался; пустой файл кэша перестраивается.

Не применено: общий образец прохода для тестов (`ORIGIN` в трёх файлах) — помощник, импортирующий
`src/`, в `test/support` не кладём, а файл-помощник внутри `src/` ради трёх копий объекта — цена
выше выигрыша. Снимок каталога вынесен в `test/support/dir-snapshot.ts`: он из `src/` ничего не
берёт.

Отклонено проверкой: сетевая проба в слое хранилища (цикла импортов нет, план U15 сам помещает её
в юнит); «две копии хранилища версионного файла разошлись» (расхождение записано как намеренное);
общая проверка маркеров JPEG (потоковая и по буферу — общими были бы две константы); выражения
`writable` и `unsaved` в сверке (стиль); причина `unknown` вместо `lost` у миниатюры (ни один
потребитель по причине не ветвится).

Что показал состязательный ревьюер сверх находок — прогонами вне репозитория:

- **рандомизированный тест** (4200 сидов: случайные операции, переходные сбои на любом шаге
  записи, залипшие блокировки, перезапуски) нарушений «принятое не потеряно, отброшенное не
  вернулось, исходник не изменился, вторая сверка ничего не меняет» не нашёл;
- **настоящие блокировки Windows:** переименование каталога сессии даёт `EPERM` при любом
  открытом дескрипторе внутри; удаление занятого файла отказывает, пометка остаётся; чтение
  занятого файла — `EBUSY`. Коды совпадают со списком повторов, поведение — с задуманным. Это
  первое подтверждение не на подмене; под тестом в репозитории его по-прежнему нет.

тест пропущен). Коммит `fix(m1): U13–U16 правки по код-ревью…`.

## Сессия 6 — сквозной срез: служба прохода, команды моста, handoff состояний

### U17. Служба прохода — ✅ зелёный

`src/core/scan/pass-service.ts` — `createPassService` и `openPassService` (сверка, три хранилища
и служба над ними — то, что main создаёт один раз). Служба держит сканер, идущий запуск и выдаёт
снимок целиком; `test/integration/pass.emulator.test.ts` — 36 сценариев плана против эмулятора по
HTTPS во временном корне, «перезапуск» — новая служба над тем же корнем.

Старт прохода по шагам: режим отказа → сканер подключён → новый проход или досканирование →
`buildScanSettings` → транспорт профиля → закрыть незакрытые задания этого сканера (KTD-11) →
прочитать лоток (R9) → `beginPass` / `resumePass` (KTD-17) → `runScanJob`. Исход сегмента пишется в
обработчике `onEnd` задания — до `DELETE`; если обработчик не вызывался (задание не создано,
негодный `Location`, отмена до `POST`), исход переводится по отчёту тем же `settleSegment`.

Решения, которые план оставил юниту:

- **В M1 проход один: новый проход начинается только без сессии.** Сессия есть — только
  досканирование прерванного; завершённый и принятый проход дают `sessionConflict.notInterrupted`.
  Хранилище второй проход разрешает (M2), запрет — политика службы.
- **Ноль страниц — не проход** (R9): `empty`, обрыв на первой странице нового прохода и отмена
  до `POST` идут через `discardSegment` — сегмент убран, сессии нет. Пустой лоток по статусу —
  отказ `scanNoPaper` до задания; `404` на первой странице при «полном» лотке — тот же код после
  `DELETE`. Обрыв на первой странице досканирования оставляет пустой прерванный сегмент: проход
  остаётся прерванным с прежними страницами, выбор тот же.
- **Два вида обрыва по сигналу:** «Остановить» (`intent: 'stop'`) удаляет сегмент, закрытие окна
  (`intent: 'shutdown'`) помечает его прерванным (KTD-26). `stopPass` дожидается закрытия задания
  и возвращает отказ закрытия каталога (`sessionCloseFailed`), если он был: тогда проход прерван со
  страницами. `interrupt(deadlineMs)` возвращается не позже срока, даже если `DELETE` молчит.
- **Ответ `startPass` — `PassReport`:** `completed` / `interrupted` (страницы на месте, причина в
  `error`) / `stopped`. Отказ — проход не начался или не оставил ни страницы, ни сессии
  (`scanNoPaper`, `scannerBusy`, `scannerCertificateChanged`, обрыв на первой странице).
- **Сбой сети на самом `POST` по статусу не закрывается** (вопрос сессии 4): `Processing` в
  статусе может быть чужим заданием, а своё устройство снимает само через пять минут; до тех пор
  следующий `POST` получит `503` и пользователь увидит «занят».
- **Отказ закрытия незакрытого задания проход не блокирует:** адрес остаётся в файле, `POST`
  уйдёт и получит `503`, если задание ещё держит устройство.
- **Сертификат сменился при старте** — сканер в снимке переходит в `otherDevice` (KTD-40); новый
  отпечаток запомнит только повторное подключение.
- **Сканер и параметры — в службе:** `checkRememberedScanner` при запуске (состояние `checking`
  видно в снимке), `useScanner` после подключения (запоминает и сверяет параметры по KTD-13),
  `setParams` проверяет значение против вариантов устройства и пишет настройки. Отказ записи
  настроек подключение не отменяет — сканер остаётся в памяти.
- **Снимок целиком** (`src/shared/snapshot.ts`): сканер (`none` / `checking` / `ready` /
  `unreachable` / `otherDevice`, с адресом и схемой), сессия, ход прохода (`starting` / `busy` /
  `scanning` / `stopping`, признак досканирования, страниц за запуск), явные `canResume` и
  `canAccept`, режим отказа и признак несохранённого журнала, уведомления запуска — читаются без
  сброса. Номер снимка растёт на каждое изменение; `onChange(seq)` — для события моста.
- **Типы параметров сканирования переехали в `shared`** (`scan-params.ts`): они идут в снимок, а
  `shared` ядро не импортирует. `scanParamsSchema` — одна на журнал, настройки и вход команды.
- **Коды со строками локали:** `scannerNotConnected`, `scanNoPaper`.

**Отклонения от плана (осознанные):** команда досканирования отдельно не заведена — `startPass`
сам выбирает новый проход или досканирование по снимку; `snapshot.ts` расширен здесь, а не в U18.

**Грабли:** `onEnd` задания не вызывается при негодном `Location` и при отмене до `POST` — первый
вариант службы оставлял сегмент «идёт» в журнале. Теперь исход переводится по отчёту, если
обработчик не отработал.

**Готово:** `typecheck`, `lint`, `format:check`, `test:all` зелёные (789 + 108). Коммит
`feat(m1): U17 служба прохода…`.

### U19. Handoff состояний, которых нет в макете — ✅ утверждён автором

`docs/design/handoffs/2026-10-m1-states.md` — 22 состояния по шаблону handoff'а, собраны из
рецептов дизайн-системы без новых токенов и компонентов; окончательные тексты всех кодов
`errors.*` с подключами по `reason` / `field`; ~90 строк интерфейса по пространствам экранов.

Написан фоновым агентом параллельно с U17–U18, сверен с итоговыми `errors.ts` и `snapshot.ts`.

**Утверждение автора** (в той же сессии): все шесть развилок — по предложению агента (кольцо
фокуса без нового токена; заголовок «Сканируем листы из автоподатчика» / кнопка «Сканировать
листы»; новый текст пустого обнаружения с брандмауэром; `storage.unsaved` не показывать; время
ожидания занятости не показывать; отдельная кнопка «Повторить» — ей нужна команда моста
`recheckScanner`, заводится в U21). Подтверждено: причина обрыва в плашке не называется,
«Досканировать» при `canResume === false` не рисуется.

**Поправка автора: «пачка» — рабочий термин, в интерфейс не идёт.** В handoff'е, `UI_SPEC.md` и
локали заменено: про бумагу в лотке — «листы», про отсканированное — «страницы», действие —
«Новое сканирование» (как в макете; «Новый скан» уходит). Внутренние ключи `newBatch` →
`newScan`. Тексты макета с «пачкой» для экранов M2 (`flip`, карточки `newscan`, подсказка
`setup`) переписываются при реализации этих экранов — отмечено в `UI_SPEC.md` 7.4.

**Что handoff нашёл в доках** — хвосты для U25: `UI_SPEC.md` 7.1 описывает схему текстовым полем
с дефолтами HTTP/80, техбаза и U21 требуют переключатель и HTTPS/443; раздел 2 «Параметры» со
строкой «Пустые обороты» и «Авто» остаётся контрактом на M2+; рецепт «Строка статуса устройства» в
`DESIGN_SYSTEM.md` знает только «готов»/«занят» — модификаторы для «проверяем…», «не отвечает»,
«другое устройство» и бейдж схемы стоит дописать при реализации.

**Для U20–U24:** ключи `errors.<код>` и `errors.<код>.<причина>` в одном JSON не уживаются
(строка и объект под одним ключом) — раскладка в локали: `errors.<код>` базовый и, например,
`errorReasons.<код>.<причина>`; снимок прохода теперь несёт `scanner` — для текста «досканировать
можно только на …»; состояние миниатюры «строится / не построилась» — чисто renderer-ное
(`<img>` load / error); «ничего не нашлось через 10 с» — таймер экрана.

### Ревью сессии 6: код-ревью

По решению автора — сразу после сессии, в том же контексте. Девять ревьюеров: корректность,
стандарты проекта, тесты, сопровождаемость, безопасность, надёжность, контракт моста,
состязательный (локально: другой модели для независимой проверки нет — установлен только
`claude`), прошлые уроки. 21 находка, после слияния дублей — 10, все P2 и P3; блокеров нет, ни
одна не теряет данные. Независимый валидатор был прерван и вердиктов не вернул — все десять
находок проверены по коду оркестратором; это не независимая проверка. Применены все десять.

- **«Остановить» во время `POST` возвращало фазу в «сканирование»** (три ревьюера независимо):
  задание зовёт `onPhase('scanning')` после `201`, и кнопка «Останавливаем…» снова становилась
  «Остановить». Фаза после нажатия больше не меняется.
- **Закрытие незакрытых заданий не смотрело на отмену:** молчащий сканер держал «Остановить» и
  закрытие окна по сроку `DELETE` на каждом задании. Цикл проверяет отмену перед каждым.
- **Проверка запомненного сканера затирала сканер, подключённый за это время** — сегодня этому
  мешала только выключенная кнопка; с `recheckScanner` (U21) путь стал бы обычным. Результат
  применяется, только если слот не сменился.
- **Срок закрытия окна 7 с был короче неотменяемого `POST` (10 с) плюс `DELETE` (5 с)** —
  задание оставалось бы на устройстве без записи адреса. Срок поднят до 16 с. Предложение
  агента было обратным — короткий срок самому `POST`; при реализации отклонено: обрыв `POST` по
  таймауту в обычной работе (уснувшее устройство отвечает до секунды) оставил бы задание с
  неизвестным адресом — ровно то, от чего защищает KTD-10. Окно при закрытии посреди прохода
  может ждать до 16 с, обычно — доли секунды.
- **`stopDiscovery` выбрасывал найденное**, хотя контракт `Discovery.stop` обещает его сохранить:
  модалка, остановившая поиск до «Подключить», получила бы `invalidInput`. Поиск хранится до
  следующего `startDiscovery` или выхода.
- **`openDataFolder` глотал отказ:** `shell.openPath` не бросает, а возвращает строку. Теперь
  отказ — `storageFailed` с причиной `openPath`, кнопка экрана несовместимых данных не молчит.
- **Причины `sessionConflict` — общий тип** `SessionConflictReason` в `src/shared/errors.ts` с
  конструктором `sessionConflict()`: интерфейс выбирает текст по причине, опечатку теперь ловит
  `typecheck`. Новые причины `stopping` и `otherScanner` — в наборе.
- **Грамматика ключа страницы и id сессии — одна, в ядре** (`isPageKey`, `isSessionId` из
  `storage/layout.ts`); копии в `page-protocol.ts` и неиспользуемые схемы в `schemas.ts`
  удалены. Заодно схема изображений отклоняет пароль в адресе, явный порт и нулевой номер.
- **Два теста не доказывали своё:** тест сбоя журнала проходил и без повтора записи перед
  `DELETE` — добавлен сценарий, где падают две записи, а повтор службы проходит; тест `dispose`

Каждая правка поведения проверена мутацией: откат правки роняет её тест (пять из пяти).

Отложено как остаточный риск, не правилось: исключение из `onChange` внутри приёмника страницы

### Пустое окно в dev — StrictMode убивал хранилище снимка (найдено автором после закрытия)

`npm run dev` открывал пустое окно: мост жив, снимок по команде приходил, консоль чистая, но
`#root` пуст. Причина — двойное монтирование StrictMode в dev-сборке React: cleanup-фаза звала
`store.dispose()`, хранилище помечалось мёртвым, повторный mount его не пересоздавал — ответ
`getSnapshot` отбрасывался, и App навсегда оставался в состоянии «снимка ещё нет». В
production-сборке StrictMode эффекты не дублирует, поэтому смоуки сессий 7–8 на собранном
приложении проходили, а dev был сломан с самой сессии 7 (и честно висел в «не проверено»).

Лечение: подписка на мост живёт от первого React-подписчика до последнего (ленивая, внутри
`subscribe`), `dispose` убран — цикл «подписка → отписка → подписка» хранилище переживает,
повторная подписка перечитывает снимок. Регрессионный тест рендерит App в `<StrictMode>`;
тесты хранилища покрывают повторную подписку и отписку последнего слушателя. Проверено живьём
в dev: `setup` рисуется, HMR обновляет экран, консоль чистая. Коммит `fix(m1): U20 пустое
окно в dev…`.

- ~~`dev`-режим с HMR~~ — проверен при разборе пустого окна (см. выше): `setup` в dev

  — новая версия формата и чтение версии 1;
- **остаточные риски, принятые как есть (ревью сессии 5):** пометка об удалении живёт только в
  журнале — неудалённый файл под пометкой и потерянный журнал вместе вернут отброшенные страницы;
  отключение питания может откатить последнее переименование (KTD-19); журнал, занятый другим
  процессом, стоит каждой странице до пяти секунд повторов; `sameScanner` не сравнивает адрес,
  когда совпал UUID, а отпечатка у одной из сторон нет; профиль `https` без отпечатка из правленого
  файла настроек снимает сверку сертификата;
- **ручной смоук:** `npm run emulator` — порт 9443, сценарий меняется строкой в консоли; адрес для
  подключения — `127.0.0.1:9443`; прогон тестов под Node из Electron по-прежнему ручной
  (`ELECTRON_RUN_AS_NODE=1 electron.exe vitest.mjs run …`);
- каждый новый код ошибки — строка в `ERROR_CODES` и в `errors.<код>` локали, иначе падает
  `typecheck`.
