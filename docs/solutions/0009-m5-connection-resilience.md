«не отвечает»; `5xx` кроме `503` — без поиска; профиль без отпечатка не ищется; «Повторить»

«занят» — только в модалке подключения, строка устройства остаётся «не отвечает».

## Сессия 1 — замер на железе, классификация, поиск по UUID

### U1. Замер на живом ET-3850 — ✅

Скрипт `temp/measure-m5.mjs` (вне git; полные значения — в `temp/m5-measure.json`, в выводе —
маски). Автор менял адрес сканера и перезагружал МФУ; три снимка: «до», «после», «после
перезагрузки».

- **Сертификат при смене адреса не меняется** — отпечаток, SAN и срок те же и после
  перезагрузки. В SAN остаётся старый IP: устройство SAN не обновляет. Стоп-условие плана не
  сработало; R3 (отпечаток доказывает «то же устройство») держится.
- **UUID TXT = UUID capabilities**, регистр тоже совпадает.
- **`503` на `GET` нет**: два прогона по 60 с во время печати — `ScannerCapabilities` и
  `ScannerStatus` отвечают `200`, состояние `Processing`. Ожидание «занят» в пробе остаётся
  страховкой (решение автора — строится при любом итоге замера).
- **Два поиска в одном процессе** оба видят сканер за 0,1–1,2 с — запасной вариант «модалка
  останавливает поиск проверки» не нужен.

Итог — в техбазе §8 («Проверено на ET-3850 2026-10-25»). Коммит `docs(m5): U1 …`.

### U2. Классификация исхода пробы и ожидание «занят» — ✅ зелёный

`src/core/storage/probe-outcome.ts` — чистая `classifyProbe(scanner, probed)` → `ok` / `silent` /
`foreign` / `busy` / `garbled` / `canceled` по таблице KTD1; `isSilence` удалён. Проверка
запомненного сканера пока даёт прежние слоты (`foreign` → `otherDevice`, остальное →
`unreachable`); поиск подключает U4.

`src/core/escl/connect.ts`: `probeScanner(profile, options, probe)` — третий параметр теперь
`ProbeOptions { signal?, onResponse?, waitBusy? }`. `503` на capabilities — повтор раз в 1 с до
потолка 15 с (`PROBE_BUSY_WAIT`), затем `scannerBusy`; `onResponse` — один раз, на первый
HTTP-ответ с любым кодом, до паузы; `waitBusy: false` — режим кандидата, `503` сразу
`scannerBusy`. Шов часов `ProbeClock` / `realProbeClock` по образцу `ScanJobClock`; петли
`scan-job.ts` не объединялись (KTD6). Переход на HTTP по `scannerBusy` не идёт — правило
`FALLBACK_REASONS` его и так не включало, добавлены комментарий и тест. Текст `scannerBusy` — без
«за минуту»: он общий для потолков 15 и 60 с.

Эмулятор: поле сценария `busyCapabilities` и именованный сценарий `capabilities-busy`.

**Отклонения от плана (осознанные):** классификатор — в своём модуле с тестом (план называл
`settings-store.ts`), чтобы файлы оставались малыми; `scannerNoAdf` и прочие не названные в
таблице коды — `foreign` (сохраняет прежний слот `otherDevice`). Тексты `scannerBusy` в
исторических handoff'ах M1/M2 не правились.

**Готово:** typecheck, lint, format:check, `test:all` зелёные (2145 + 203). Коммит
`feat(m5): U2 …`.

### U3. Поиск по UUID в обнаружении — ✅ зелёный

`src/core/discovery/find-by-uuid.ts`: `findByUuid({ uuid, onCandidate, windowMs?, signal?,
clock?, discovery? })` → `{ done, stop() }`. Кандидаты (`address`, `port`, `basePath`) — по мере
появления, каждый адрес с портом один раз; UUID в нижнем регистре с обеих сторон. Исход
`done` — `window` / `noNetwork` / `socket` / `canceled` / `stopped`; единственный выход через
`finish`, поиск останавливается всегда, исключение обработчика отклоняет `done` (не роняет main
из события библиотеки). Окно приёма — `UUID_SEARCH_WINDOW_MS` = 8 с; таймер окна не держит
процесс. `Discovery` получил `records()` только для ядра; `state()` и снимок не изменились.

**Отклонения:** две фейковых `Discovery` в `handlers.test.ts` получили `records: () => []` (метод
обязательный). Кандидаты берутся из слитого списка поиска с его потолком 64 записи — для домашней
сети приемлемо.

**Готово:** typecheck, lint, format:check, `test:all` зелёные (2162 + 203). Коммит
`feat(m5): U3 …`.

Граница сессии достигнута: U1–U3 закрыты, гейт зелёный.

## Сессия 2 — повторный поиск, запись адреса, эмулятор переезда

### U4. Вынос слота и повторный поиск в проверке — ✅ зелёный

Два коммита. Сначала вынос без изменения поведения: `src/core/scan/scanner-slot.ts` —
`createScannerSlot({ settings, connector, search, notify, isPassRunning })` с `current()`, `state()`,
`check(signal)`, `use(connected)`, `setParams`, `markOtherDevice`; служба делегирует, `pass-service.ts`
998 → 890 строк (после поиска — 895). Слоту отдан и `setParams` целиком: всё, что пишет в слот, — в одном
модуле.

Затем поиск. Оркестрация — `src/core/storage/remembered-search.ts` (`locateRemembered`,
`SEARCH_THRESHOLD_MS` = 1500, `CHECK_DEADLINE_MS` = 10 000); `settings-store.checkRememberedScanner`
стала тонкой обёрткой и настроек по-прежнему не пишет, исход `ready` несёт `relocated`. Ход — по HTD
плана: два контроллера (старый адрес жёсткий срок обрывает, только пока тот не дал HTTP-ответа;
кандидаты и поиск — всегда), обрыв по сроку — `scannerUnreachable { timeout }`, очередь кандидатов с
сохранённым портом вперёд, `waitBusy: false` у кандидатов, сокеты закрыты во всех исходах. Запись
адреса — в слоте, в том же тике, что сверка `checking` (мутация «запись на микрозадачу позже» ловится
тестом AE4 FIFO). Повторный `check()` во время проверки возвращает тот же промис. Отмена: стартовая
проверка — `AbortController` в `main`, прерывается на `will-quit`; «Повторить» — сигнал обработчика,
прерывается `dispose()`. Шов: `PassServiceOptions.findByUuid` (по умолчанию настоящий),
`test/support/uuid-search.ts` — `noSearch`, виртуальные часы, фейковая сеть и поиск.

**Отклонения и уточнения (осознанные):**

- Старый адрес ответил уже после старта поиска (например, `503`) — его проба жёстким сроком не
  обрывается: сканер на месте. Такая проверка может идти до потолка ожидания «занят» (~15 с), дольше
  10 с. План этот случай прямо не называл; у ET-3850 `503` на GET не наблюдался (U1).
- Кандидаты, принятые в окне приёма, пробуются и после окна — до жёсткого срока (как в KTD3).
- «Чужой» кандидат — любой класс `foreign` (и «не сканер», и «без автоподачи»), не только чужой
  сертификат или UUID.
- Внешняя отмена даёт в слоте `unreachable { canceled }`, а не «без изменений» из таблицы плана — как
  до M5; приложение в этот момент закрывается, запись при отмене не делается.
- Подтвердились и старый адрес, и кандидат — побеждает старый, записи нет.

Нестабильность: в первом полном прогоне после выноса упали два временных интеграционных теста
(`pass.emulator` AE5, `two-pass` AE6), отдельно и в повторе всего набора — зелёные. Вынос их не
касается; та же известная нагрузочная нестабильность (риски плана).

**Готово:** typecheck, lint, format:check, `test:all` зелёные (2200 + 203). Коммиты
`refactor(m5): U4 …`, `feat(m5): U4 …`.

### U5. Эмулятор переезда, сквозные сценарии, CDP-смоук — ✅ зелёный

Эмулятор принимает `cert` прошлого запуска (переезд = тот же сертификат на другом порту); UUID у всех
эмуляторов один — из фикстуры capabilities, поэтому «чужой» — эмулятор по умолчанию.
`test/integration/remembered-scanner-move.emulator.test.ts` — пять сценариев сквозь настоящий
транспорт и `openPassService`: AE1 (адрес B в `settings.json` с диска, следующий запуск без поиска),
AE2 (`otherDevice`, на B ни одного HTTP-запроса — отсечено на TLS, файл байт-в-байт), AE8 (журнал и
незакрытые задания при проверке не переписаны; `DELETE` задания с A приходит на B раньше `POST`,
досканирование завершается), AE6 (`503, 503, 200`, поиска нет), AE4 (ручное подключение во время
поиска остаётся в слоте и в настройках).

CDP-смоук `temp/smoke-m5.mjs` (вне git), подключение через модалку и перезапуск на том же профиле:

| Сценарий                      | built                             | dev                 |
| ----------------------------- | --------------------------------- | ------------------- |
| запомненный на месте          | «готов» через 0,2 с               | «готов» через 0,6 с |
| запомненный на закрытом порту | «не отвечает» через 8,0 с от окна | 8,0 с от окна       |
| capabilities занят дважды     | «готов» через 2,0 с               | 2,0 с               |

Закрытый порт отказывает сразу — поиск стартует без порога 1,5 с, «не отвечает» приходит по окну
приёма 8 с. Консоль renderer чистая. Переезд через настоящий mDNS — на приёмке (U6).

**Готово:** `test:all` зелёный (2200 + 208), сборка, смоук `built` и `dev` зелёные. Коммит
`feat(m5): U5 …`.

### Ревью сессий 1–2

**Simplify** (три линзы: переиспользование, качество, эффективность). Применено: часы пробы — те же,
что у задания сканирования (`ProbeClock = ScanJobClock`, `realProbeClock = realClock`; петли
ожидания по-прежнему раздельные, KTD6), часы поиска — `Pick<ProbeClock, 'sleep'>`; окно фейкового
поиска — константой `UUID_SEARCH_WINDOW_MS`; локальная переменная идущей проверки в слоте —
`inflight` (не путать с `current()`). Отклонено: перестройка `locateWithSearch` на хелперы
(тонкий, хорошо покрытый код), один контроллер отмены вместо двух (main и обработчики — разные
слои, так в плане), мешок параметров у `checkRememberedScanner`, отдельный `failure()` у
`Discovery`. Коммит `fix(review): M5 — упрощение …`.

**Код-ревью** (`ce-code-review`, восемь линз: correctness, security, adversarial, testing,
maintainability, reliability, project-standards, learnings; проверяющего на другой модели нет —
CLI других провайдеров не установлены, adversarial — локальный). Вердикт — «готово с правками»,
одна находка, подтверждённая валидатором:

- **#1 (P2)** — старый адрес, впервые ответивший уже после старта поиска (например, `503`), не был
  закреплён тестом, а поведение было неудачным: поиск шёл дальше, кандидат мог победить, чужой
  кандидат перебивал итог «занят». Теперь любой HTTP-ответ старого адреса останавливает и
  начатый поиск (KTD3, R4 — «сканер на месте»), итог — по старому адресу. Тесты: поздний `503` до
  потолка, `503` → `200`, `503` после отклонённого чужого кандидата, кандидат с нашим
  сертификатом и чужим UUID. Коммит `fix(review): M5 — ответ старого адреса …`.

Остаточные риски (anchor 50 и советы, в бэклог «Хвосты M5»): строка «другое устройство» по чужому
кандидату показывает старый адрес (решение автора R3 — «другое устройство» — не пересматривается);
ручное подключение не останавливает идущий поиск (сокеты до срока 10 с); «занят» на старом адресе
держит «проверяем…» до ~15 с; два зависающих кандидата на сохранённом порту могут съесть срок
(только доступность — отпечаток не даёт подмены); `verify()` без `try/catch` (сейчас недостижимо —
все пути возвращают `Result`); потолок обнаружения 64 записи. Опыт M1 (журнал 0002): гонка проверки
с ручным подключением закрыта сверкой слота; окно брандмауэра при запуске теперь возможно — строка
чеклиста приёмки.

Нестабильность эмуляторных тестов под полным прогоном (`blank-backs`, `scan-job`, `two-pass`,
`added-pass` — проход «прерван» посреди): по отдельности зелёные; на `main` (`eafecf6`) во
временном worktree `blank-backs` тоже падает в одном прогоне из двух — нестабильность старая, M5 её
не вносил. Пункт — в бэклог.

## Закрытие вехи

Приёмка автора 2026-10-26 на упакованном приложении и живом ET-3850 — все восемь сценариев
чеклиста зелёные:

- AE1: сканер на новом адресе (приложение помнило старый) — «готов» почти сразу, в
  `settings.json` поменялся только адрес; листы сканируются.
- AE5: выключенный сканер — «не отвечает» примерно через 8 с (окно приёма поиска; смоук — 8,0 с).
- «Повторить» после включения, запуск во время печати (AE6), закрытие во время поиска (настройки
  не записаны), обычный запуск — как ожидалось.
- Модалка во время поиска: «Сменить» во время «проверяем…» неактивна — так задано handoff'ом M1
  (S2), сценарий чеклиста ошибочно предполагал открытую модалку; одновременная работа двух поисков
  проверена замером U1.
- Окна брандмауэра Windows не было — разрешение уже было дано.

Правок по итогам приёмки нет.
