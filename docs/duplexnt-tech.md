# Duplexn't — техническая база

Справочник по проекту: что это за приложение, как устроен протокол,
какие решения уже приняты и что проверено экспериментально.

Целевое устройство: **Epson EcoTank ET-3850**. Проверено в сентябре 2026.

---

## 0. Что это за приложение

**Duplexn't** — десктопное приложение для Windows, которое сканирует
двусторонние документы на сканере **без автоматического дуплекса**.

Проблема: у ET-3850 есть автоподача на 50 листов, но нет автопереворота.
Штатное приложение умеет сканировать только одну сторону за проход, а собирать
из двух проходов правильный документ пользователю приходится вручную —
перетасовывать страницы в редакторе PDF.

Решение — сценарий в два прохода:

1. Пользователь кладёт пачку в автоподачу лицом вверх, первая страница сверху.
   Приложение сканирует все лицевые стороны.
2. Пользователь берёт вышедшую пачку целиком и **разворачивает её на 180°
   в плоскости стола, не переворачивая листы** — из податчика она вышла
   оборотами вверх. Кладёт обратно в лоток.
3. Приложение сканирует обороты и само собирает документ в правильном порядке,
   зная, что обороты идут задом наперёд.
4. Пользователь проверяет результат, при необходимости правит порядок
   перетаскиванием, размечает границы документов и сохраняет.

Название — шутка про отсутствующий дуплекс.

### Границы проекта

- Приложение делается **под сканеры с автоподачей и без дуплекса**.
  Нет ADF — устройство не подходит, так и сообщаем. Дуплекс не проверяем
  и не поддерживаем: приложение существует именно ради его отсутствия.
- Планшет (стекло) поддерживается как вспомогательная утилита, не как режим.
- Транспорт только сетевой, по eSCL. WIA и TWAIN не используются.

### Стек

> Пересмотрено: стек — Electron, TypeScript, React (`decisions/0001`–`0003`,
> актуальная таблица — `duplexnt.md` → «Технологический стек»). Исходная гипотеза
> ниже оставлена как история; верным остаётся её главный довод — протокол это

## 1. Транспорт

Работаем по **eSCL** (AirScan / Mopria) поверх HTTP.

**Подтверждённые параметры ET-3850:**

| Параметр         | Значение                                                |
| ---------------- | ------------------------------------------------------- |
| Схема            | `https` (на порту 80 только веб-морда, eSCL отдаёт 404) |
| Порт             | 443                                                     |
| Базовый путь     | `/eSCL/`                                                |
| Сертификат       | самоподписанный, проверку отключать                     |
| Версия протокола | 2.9                                                     |
| Сертификация     | mopria-certified-scan 1.4                               |

Базовый URL: `https://<ip>/eSCL`

**Важно:** порт и схему не хардкодить. Точные значения лежат в TXT-записи mDNS
(поле `rs=` — базовый путь). Сервисы: `_uscan._tcp` для HTTP,
`_uscans._tcp` для TLS.

**mDNS: устройство часто молчит на первый запрос** (замер M1, 130 прогонов;
журнал `solutions/0002`, «Что показал замер на устройстве»). Поиск обязан
повторять запрос: с повтором при поиске до 20 с сканер найден в 60 из 60,
обычно за 1,5 с. Запись A приходит не в каждом ответе. Ключи TXT сравнивать
без учёта регистра (`UUID`, `usb_MFG` — прописными). ET-3850 объявляет оба
сервиса на 443, по HTTP eSCL отвечает 404 — схему из типа сервиса не выводить.

## 2. Методы протокола

| Метод              | Запрос                               | Ответ                          |
| ------------------ | ------------------------------------ | ------------------------------ |
| Возможности        | `GET /eSCL/ScannerCapabilities`      | 200 + XML                      |
| Статус             | `GET /eSCL/ScannerStatus`            | 200 + XML                      |
| Создать задание    | `POST /eSCL/ScanJobs` + XML настроек | 201 + заголовок `Location`     |
| Забрать страницу   | `GET <Location>/NextDocument`        | 200 + бинарь, либо 404 = конец |
| Отменить / закрыть | `DELETE <Location>`                  | 200                            |

**Поведение, проверенное на практике:**

- `Location` приходит абсолютным, уже с `:443`.
  Нормализацию (относительный путь, подмена `http://` → `https://`)
  всё равно оставить — страховка на случай обновления прошивки.
- Планшет отдаёт ровно одну страницу, второй `NextDocument` честно даёт 404.
  Зацикливания нет, отдельный костыль для `Platen` не нужен.
- `DELETE` в конце обязателен: незакрытое задание может блокировать следующее.
- `503` на `POST /ScanJobs` = сканер занят (другой сеанс или идёт печать).
  Нужен вежливый ретрай с таймаутом, а не падение.

## 3. Единицы измерения региона

**Регион сканирования задаётся в 1/300 дюйма ВСЕГДА**, независимо от выбранного DPI.
Это главный источник ошибок во всей интеграции.

```
A4: 210 мм = 2480,  297 мм = 3507
```

Пересчёт «пиксели превью → 1/300 дюйма» вынести в отдельную функцию
и закрыть тестом. Это самое хрупкое место в коде.

## 5. Логика двух проходов

**Экспериментально подтверждено** на трёх пронумерованных листах,
физическое действие перепроверено отдельно.

Проход 1 (лицевые): `1 Лицо, 2 Лицо, 3 Лицо` — прямой порядок
Проход 2 (обороты): `3 Оборот, 2 Оборот, 1 Оборот` — **обратный порядок**

```python
def interleave(fronts, backs):
    """Оборот для листа k — это backs[N-1-k]."""
    backs = list(reversed(backs))
    pages = []
    for i, f in enumerate(fronts):
        pages.append(f)
        if i < len(backs):
            pages.append(backs[i])
    return pages
```

### Физическое действие пользователя

**Разворот пачки на 180° в плоскости, БЕЗ переворота листов.**

Из податчика пачка выходит оборотами вверх, поэтому переворачивать её не нужно —
достаточно развернуть целиком, чтобы верхний край снова стал ведущим.
Обороты при этом приходят в правильной ориентации, доворот на 180° в дефолте
не требуется.

Это самое уязвимое место сценария: если человек вместо разворота **перевернёт**
пачку, документ соберётся молча и неправильно. Поэтому инструкция между
проходами должна быть картинкой с анимацией, а не текстом, и формулировка
«не переворачивайте листы» обязана быть явной.

Аварийный переключатель «повернуть обороты на 180°» оставить —
спасает неправильно уложенную пачку без пересканирования.

### Досканирование одного листа оборотом

**Проверено на ET-3850 при приёмке M3.5 (2026-10-09).** Отдельный лист, положенный
оборотом вверх и развёрнутым на 180° — так же, как лежала пачка на втором проходе, —
приходит оборотом в правильной ориентации, доворот не нужен. На этом стоит инструкция
карточки «Один лист» в модалке `add` (UI_SPEC §7.2).

### Калибровка

Стоит сделать мастер первого запуска: прогнать 4 пронумерованных листа,
показать результат, спросить «так правильно?». Снимает неопределённость
на другом железе и делает приложение переносимым.

## 6. Обязательная обработка ошибок

**Несовпадение числа страниц между проходами.** Замятие или двойной захват.
Молча чередовать нельзя — получится сдвиг и каша. Документ собирается
по совпавшим парам, а пользователь решает судьбу лишнего листа.
Первый проход при этом сохраняется — работа не теряется.

**Пустые обороты.** Часть листов односторонняя. Считаем долю «чернильных» пикселей
после бинаризации относительно белого бумаги. Порог сработал — _предлагаем_ скрыть,
а не выкидываем сами: бледный карандаш легко принять за пустоту.
Алгоритм, константы и калибровка — подраздел «Детектор пустых страниц» ниже.

**Подсказка готовности между проходами.** `ScannerStatus` опрашивается раз в секунду.
Значения `AdfState`: `ScannerAdfEmpty` / `ScannerAdfLoaded`.
Поле присутствует даже при пустом лотке — проверено.
Увидели `ScannerAdfLoaded` → подсветили кнопку второго прохода.

**Состояния для UI:** занят другим сеансом, лоток опустел посреди пачки,
замятие, устройство ушло в сон, потеря сети. Внятный статус прямо в интерфейсе
вместо модалки с кодом ошибки — половина ценности продукта.

### Детектор пустых страниц (M4)

Проверено на ET-3850 2026-10-22 (план M4, U2). Код — `src/core/detect/blank.ts`; калибровка —
`test/integration/blank-detector.test.ts` на настоящих сканах
`test/fixtures/escl/et-3850/scans/`.

**Алгоритм** (`blankRatio` → `inkRatioOf`):

1. Байты страницы — JPEG по маркерам; `metadata` и предел пикселей — как у миниатюр. Не JPEG
   или больше предела — `null`.
2. `sharp`: `greyscale` → `resize` до длинной стороны `WORKING_LONG_SIDE` = 1400 px
   (`fit: 'inside'`, без увеличения; ~120 dpi для A4 — шум сканера гасится, штрих карандаша не
   растворяется; миниатюра 320×452 для этого мала) → `raw`.
3. Поля обрезаются на `MARGIN_RATIO` = 0,04 размера с каждой стороны — тень кромки
   автоподатчика и срез листа.
4. Белое бумаги — яркость, ниже которой лежит `PAPER_WHITE_PERCENTILE` = 0,9 пикселей
   обрезанной области (по гистограмме): серая или кремовая бумага не становится «чернилами».
5. «Чернильный» пиксель — темнее белого больше чем на `INK_DELTA` = 40 уровней из 255
   (сравнение строгое); доля = чернильных / всех. Вырожденная область — 0.
6. Вердикт `isBlank`: доля ниже `BLANK_THRESHOLD` = 0,000135 — пусто; `null` — не пусто.

Любой сбой (не JPEG, предел пикселей, ошибка декодирования, исключение `sharp`) — `null`:
страница считается непустой и ошибкой не является. `BLANK_DETECTOR_VERSION` = 2 поднимается
при любой смене констант; кэш оценок с другой версией пересчитывается (версия 2 — порог
снижен на приёмке, см. ниже).

**Кэш** — `derived/<id сессии>/blank/<ключ>.json`, `{ v, ratio }` (`ratio: null` — сбой);
производное, в журнал не пишется (ADR 0004, амендмент 2026-10-22). Оценка считается при приёме
страницы прохода оборотов, одновременно — не больше двух; при открытии кэш читается целиком до
первого снимка. Наружу из ядра уходят только вердикты `ReadonlyMap<ключ, boolean>` — порог
живёт в ядре. `abort()` / `settle()` (B-18, журнал 0028) — как у перекоса: закрытие каталога
сессии отменяет оценки в полёте (проверка до `mkdir` и записи кэша), и `derived/<id>/blank` не
пересоздаётся; при неудавшемся закрытии `resumeDerived` запускает отменённые оценки заново.

**Калибровка** (2026-10-22, уточнена на приёмке 2026-10-23; доли чернильных пикселей на
сканах):

| Скан                     | Доля    | Класс    |
| ------------------------ | ------- | -------- |
| `blank-gray-200/300`     | 0       | пусто    |
| `blank-color-300`        | 0       | пусто    |
| `blank-gray-600`         | 8.5e-7  | пусто    |
| `bleed-gray-300`         | 9.4e-6  | пусто    |
| `punched-gray-300`       | 6.6e-5  | пусто    |
| `pencil-number-gray-200` | 2.82e-4 | не пусто |
| `pencil-faint-color-300` | 3.01e-3 | не пусто |
| `pencil-faint-gray-300`  | 3.04e-3 | не пусто |
| `text-line-gray-300`     | 3.08e-3 | не пусто |
| `signature-gray-300`     | 3.19e-3 | не пусто |
| `text-gray-300`          | 4.84e-2 | не пусто |

Первый порог 5e-4 стоял с запасом 45× между классами, но на приёмке M4 обороты с одним
карандашным номером («1о», 200 dpi, бледный нажим) давали 2.8e-4 … 3.9e-4 и скрывались. Доля
растёт площадью штриха, а не его темнотой: снижение `INK_DELTA` до 20 поднимает номер лишь до
5e-4, а просвечивание — до 2.4e-3, дырокол — до 1.5e-4, так что дельта не лечит. Порог снижен
до 1.35e-4 — геометрическая середина между худшим пустым (дырокол: 77 пикселей, целиком тень
по кромке отверстий) и слабейшим содержимым (номер); запас по 2,05× в обе стороны при
требуемых тестом 2×. Подавление одиночных точек не понадобилось. Лист с дырками дырокола —
пустой: такой оборот пользователь хочет скрыть (план относил его к «не пусто» — осознанное
отклонение). Ч/б-режима в наборе нет: ET-3850 отвергает `BlackAndWhite1` с JPEG (журнал M1).

**Предел метода.** Доля чернильных пикселей — мера площади: одиночная мелкая бледная пометка
(галочка, короткая цифра в углу) может лечь ниже 1.35e-4 и быть сочтена пустой. Страница при
этом не теряется — её показывает переключатель «добавить пустые», а счётчик и ПРОВЕРКА
называют число скрытых. Расширять поля (`MARGIN_RATIO`) ради дырокола нельзя: отверстия лежат
на 4–7 % ширины, а номер страницы в фикстуре начинается на 6 % высоты.

**Грязь на стекле.** На `text-gray-300` и `punched-gray-300` видна бледная вертикальная
полоса — грязь на стекле автоподатчика. Её яркость ≈242/255 при минимуме 236, а чернильным
пиксель становится ниже 214 (белое 254 − 40): полоса даёт ноль чернильных пикселей. Фикстуры
оставлены как есть — артефакт тракта у пользователей обычен. Потемнев ниже 214, полоса стала бы
«чернилами», и пустые обороты перестали бы скрываться: стекло протереть перед приёмкой.

### Перекос подачи: спайк (M6, U1)

План M6 ([журнал](solutions/0023-m6-straighten.md), [ADR 0008](decisions/0008-image-worker.md)).
Код спайка — `spikes/make-fan-sheets.mjs` (листы) и `spikes/straighten-bench.mjs` (прототип
детектора и ресэмплера, анализ сетки, бенч); описание команд — `spikes/README.md`.

**Модель и соглашения.** Профиль наклона θ(u) = a + b·(u − 0,5) + c·(u − 0,5)², u — доля
высоты, градусы; θ > 0 — правый конец строки выше. Коррекция — вертикальный сдвиг столбцов
`out(x, y) = in(x, y − (x − xc)·tanθ(y))`, Catmull-Rom по вертикали; необязательный
горизонтальный проход сдвигает строку на боковой дрейф d(y) = ∫ tanθ (поворот листа целиком
даёт и его; чистый срез — нет). Прототип проверен кругом «искажение известным профилем →
измерение → коррекция → анализ сетки»: заданные 0,3 / 0,8 / 0,5 измеряются как 0,30 / 0,79 /
0,54 (остаток полос 0,005–0,014°), после коррекции расхождение концов строк на сетке 0,05 мм
вместо 2,37 мм; горизонтальный проход возвращает вертикали повёрнутого листа в 0,001° (без
него они остаются под 0,32°).

**Анализ сетки** (`grid`): концы линий ищутся по 17 полосам поперёк, линии прослеживаются от
центра, угол — по прямой через точки; по горизонталям — θ(u) и квадратика с остатком, по
вертикалям — наклон в тех же единицах: при повороте листа tilt ≈ θ горизонталей, при срезе
tilt ≈ 0. На синтетике остаток 0,006°, классификация срез/поворот верна.

**Детектор по полосам** (`measure`; стартовые константы для U2): рабочая картинка 1400 px по
длинной стороне, полосы 50 мм с перекрытием 50 %, маска 3 % по краям, чернила — темнее белого
бумаги на 40 уровней, перебор ±2° шагом 0,2° (каждый второй пиксель при > 20 000) и ±0,25°
шагом 0,05° с параболой; счёт — Σ(p[i+1] − p[i])² строкового профиля. Находки синтетики:

- **Мёртвая зона ±0,1°** без дизеринга: при угле ровно 0° целые координаты ложатся в бины без
  субпиксельного размазывания, и счёт жульнически выигрывает у любого малого угла (0,1° →
  0,02°). Лечится постоянной дробной добавкой строки на пиксель (хэш индекса): 0,1° → 0,104°,
  0,05° → 0,069°. Та же поправка нужна метрике «до/после» — иначе целые строки «до» всегда
  резче дробных «после».
- **Положение полосы — центроид чернил**, не геометрический центр: полоса с текстом только в
  нижней половине меряет угол там, где текст.
- **Гейты по ловушкам** (рендер листов, искажённый 0,3 / 0,8 / 0,5): доля чернил > 30 % →
  полоса невалидна (фото давало «уверенность» 5–12 при max/min-метрике); левая и правая
  половины полосы расходятся > 0,15° → невалидна; остаток подгонки полос > 0,1° → «не по
  чему мерить» (две колонки: 0,21–0,28°, фото: 0,33°, хорошие листы 0,005–0,03°); дыра в
  покрытии валидными полосами > 0,4 высоты → прямая вместо квадратики (штриховка под 12° —
  средние полосы отбрасываются по уверенности 2,2 < 3; бедный лист — три полосы по краям;
  ошибка в середине ≤ 0,09°; с детектора v6 при дыре — ступень и узлы, см. п. 4 гейтов). Итог:
  текст, таблица, сетка — `willStraighten` с верным
  профилем; две колонки, фото — `unmeasurable`; штриховка, бедный — прямая. Среднее половин
  вместо целой полосы точность на хороших листах ухудшает (c 0,54 → 0,68) — целая полоса
  остаётся, половины только как гейт.
- **Метрика «не хуже»** — резкость строкового профиля всей рабочей картинки Σ(Δp)²/Σp² до и
  после сдвига чернил по профилю: 0,05° → ×1,09, 0,1° → ×1,29, дуга 0,125° → ×1,04, градиент
  0,8° (2,6 мм) → ×1,61, смешанный 0,3 / 0,8 / 0,5 → ×1,9–2,2. Порог k = 1,3 — стартовый.
- Артефакт синтетики без шума: после коррекции серого листа половины полос расходятся на
  ±0,08° (пила порога чернил от дробного сдвига с периодом 1/tanθ столбцов); на цветной
  синтетике и, ожидаемо, на настоящих сканах с шумом — нет.

### Детектор перекоса (M6, U2)

Код — `src/core/detect/skew.ts` (измерение, гейты, метрика), `src/shared/skew.ts` (профиль
узлами, типы исхода, версия геометрии), `src/core/detect/gray.ts` (серая рабочая картинка —
общий вход с детектором пустых: один декод на страницу обслуживает оба). Калибровка —
`test/integration/skew-detector.test.ts` на сканах `test/fixtures/escl/et-3850/scans/`;
синтетика — `test/support/synthetic-page.ts`; эталон по сетке на полном разрешении —
`test/support/grid-analysis.ts` (перенос из спайка).

**Алгоритм** (`measureSkewJpeg` → `decodeWorkingGray` → `measureSkew`):

1. Серое рабочего размера (`WORKING_LONG_SIDE` 1400), белое бумаги и чернила — как у
   детектора пустых (`MARGIN_RATIO`, `PAPER_WHITE_PERCENTILE`, `INK_DELTA`), маска по краям
   `EDGE_MASK` 3 %.
2. Полосы `BAND_MM` 30 мм с шагом 50 %: в полосе список чернильных пикселей с окном Ханна по
   высоте (обязательно — без него горизонтальный обрез полосы даёт ложный пик ровно в 0°) и
   дизерингом строки (без него мёртвая зона ±0,1° у 0°); положение полосы — центроид чернил.
   Угол — резкость строкового профиля Σ(Δp)²: грубый перебор ±2° шагом 0,2° (каждый второй
   пиксель при > 20 000), уточнение ±0,25° шагом 0,05°, парабола по трём точкам.
3. Полоса валидна: доля чернил 0,5–30 % (`MIN_INK_FRACTION`; меньше — пятая часть строки
   текста, по ней не померить: пустая бумага с просвечиванием даёт 0,3 % и угол ниоткуда),
   уверенность max/min ≥ `CONFIDENCE_MIN` 3, половины полосы не противоречат целой: вето
   «половины расходятся > `HALVES_TOLERANCE_DEG` 0,25°» действует, только если хотя бы одна
   половина **возражает** — её собственный пик резкости лучше счёта при угле целой полосы в
   ≥ `HALF_OBJECTION_MIN` 1,2 раза. У половины с одной плашкой, рисками линейки или пустой
   бумагой пик плоский (1,00–1,12 на сканах), её угол — шум, и уверенную целую полосу он не
   отменяет; у колонки с другой фазой строк и косой штриховки — 1,28–1,98. Угол — по целой
   полосе, кроме случая, когда обе половины согласны между собой и обе возражают целой (две
   колонки с разной фазой строк — тогда среднее).
4. Гейты страницы: ≥ `MIN_BANDS` 3 валидных полос, покрытие ≥ `MIN_COVERAGE` 40 % высоты,
   форма — min(остаток дуги Huber, остаток ступени) ≤ `SHAPE_RESIDUAL_DENSE_MAX_DEG` 0,2° у
   узлов по плотной опоре (детектор v5, [solution 0030](solutions/0030-skew-shape-tolerance.md):
   графичная страница шумит 0,1–0,2° между соседними полосами при чистом веере); дыра покрытия >
   `MAX_SUPPORT_GAP` 0,4 (две кучки полос по краям, середина пуста или отброшена по
   уверенности) → гладкое семейство — прямая вместо квадратики, остаток формы — min(остаток
   прямой, остаток ступени) со строгим порогом `SHAPE_RESIDUAL_MAX_DEG` 0,1°, профиль — те же
   узлы по полосам (детектор v6, [solution 0033](solutions/0033-b-39-skew-gap-step.md): веер с
   остановкой подачи — две константы, прямая через две кучки внутри каждой наклонена на «наклон ×
   полуширина кучки», остаток рос с веером и резал именно сильный веер — 0,16–0,20° при ступени
   0,03–0,04°; до v6 профиль был прямой по двум узлам u = 0 и 1 и экстраполировался до краёв
   листа: +1,10° при измеренных +0,92°); провал
   формы → повтор полосами `FALLBACK_BAND_MM` 50 мм. Все валидные полосы ниже `LEVEL_DEG` → форма не
   спрашивается, профиль узлами и `level` (детектор v2: почти пустой лист после коррекции с
   тремя полосами −0,08 / +0,10 / −0,08° давал остаток 0,105° и «не по чему мерить» вместо
   «ровная»). Форма по целым полосам не сошлась → **запасной профиль по среднему половин**
   (детектор v4, [solution 0026](solutions/0026-skew-halves-profile.md)) у полос, где половины
   согласны между собой (≤ `HALVES_TOLERANCE_DEG`), с теми же гейтами полос, покрытия и формы:
   у двух колонок с разной фазой строк целая полоса шумит на 0,1–0,2° от наложения фаз, а
   каждая половина видит одну колонку и даёт чистую ступень; веер — свойство подачи, одинаков
   по ширине, и профиль по половинам выправляет обе колонки. `SkewMeasure.basis` —
   `whole` / `halves` (журнал и тесты, в снимок не идёт). Только после этого — повтор
   полосами 50 мм.
5. Профиль — узлы `{u, theta}` по валидным полосам, между ними монотонный кубический сплайн
   (Fritsch–Carlson), за крайними — константа (`skewThetaAt`, `skewTanRows`); дрейф —
   интеграл tanθ от середины (`skewLateralRows`, k = 1).
6. Исход: |θ| < `LEVEL_DEG` 0,1° по всей высоте → `level` (без метрики, оригинал байт в
   байт); иначе `alignmentContrast` — резкость строкового профиля всей картинки до и после
   вертикального сдвига списка чернильных пикселей на (x − xc)·tanθ(y) с тем же дизерингом
   (боковой дрейф на строковый профиль не влияет), отношение ≥ `IMPROVE_RATIO` 1,3 →
   `willStraighten`, иначе `notImproved`. Между полосами и перед метрикой — точка уступки
   (`setImmediate`, в тестах подменяется). У `unmeasurable` — причина `cause` (детектор v3,
   замечание автора на приёмке M6): `content` — полос мало или покрытие (фото, чистый лист,
   одна строка, сбой декода), `shape` — первый проход 30 мм упал на форме (строки есть, но не
   сходятся: две колонки, штриховка), даже если запасной проход 50 мм упал уже по числу полос.
   Интерфейс называет их по-разному — «не по чему мерить» и «наклон строк не сходится».

Подсказка устройства (`SkewPrior`, ступень u0/w/угол низа) принимается в опциях и в M6 не
читается — точка врезки M6.5. Сбой декода, не JPEG, предел пикселей → `null`.

**Две колонки (детектор v4, 2026-10-29, [solution 0026](solutions/0026-skew-halves-profile.md)):**
по целым полосам ступень видна (+0,15…+0,40° → −0,12…−0,55°), но соседние полосы прыгают на
0,1–0,2°, а поднять порог формы нельзя было — штриховка сидела на 0,144° (с детектора v5 мягкий
порог 0,2° дан только узлам по плотной опоре; у штриховки дыра опоры — строгий 0,1°, журнал
0030; с v6 её остаток считается по ступени и она выправляется, журнал 0033). Углы половин при этом
чистые (первая колонка +0,13 → −0,62°, расхождение половин ≤ 0,2°) — профиль по их среднему
выправляет обе колонки: веер 4,78 → 0,74 мм по странице, по колонкам порознь 0,68 / — мм (300
dpi) и 2,91 → 0,81 мм, по колонкам 0,47 / 0,13 мм (скан автора, 200 dpi); плечо половины вдвое
короче, остаток грубее одноколоночного текста (0,2–0,3 мм), на глаз страница ровная. Повторное
измерение двухколоночной страницы само шумит — допуск теста ресэмплера для профиля по
половинам 1 мм.

**Предел метода (честно):** сама косая штриховка не измеряется — её полосы отбрасываются по
уверенности (2–3,5), а после сдвига дают ложные уверенные углы (−0,6…−0,9° при 3,8–4,5), так что
лист со штриховкой выправляется только по тексту сверху и снизу (детектор v6, журнал 0033), и
повторное измерение выправленного листа целиком — «не измерить» (тест ресэмплера судит по
уверенным полосам ≥ 2× порога). Страница из одной штриховки без строк не выправляется. Три
колонки и больше (в половину попадает полторы) половинами не берутся — колонки по
вертикальным просветам чернил, если встретится. Страница без строк (фото, рукопись одной
строкой, подпись) не измеряется; страница «строки сверху, рисунок снизу» получает низ константой
угла верха — подсказка M6.5 (ступень устройства) здесь единственный путь.

### Ресэмплер выравнивания (M6, U3)

Код — `src/core/image/straighten.ts` (`straightenRaw` — чистая коррекция сырых пикселей,
`straighten` — JPEG → JPEG через `sharp`, `rawPaperWhite`, константы), `src/core/image/image-worker.ts`
(`ImageWorker { measure, straighten }` и прямой исполнитель `inlineImageWorker` по ADR 0008),
`src/core/escl/jpeg-markers.ts` (`withJfifDensity` — плотность в APP0 руками). Тесты —
`src/core/image/straighten.test.ts` (round-trip на синтетике без `sharp`),
`test/integration/straighten.test.ts` (фикстуры, сетки на полном разрешении, формат выхода,
размер, чанки), `test/integration/image-worker.test.ts`, `test/integration/straighten-worst-case.test.ts`.

**Алгоритм** (`straighten` → декод → `straightenRaw` → энкод):

1. Декод `sharp(bytes, {limitInputPixels}).raw()`; серый JPEG — с `toColourspace('b-w')`,
   иначе `sharp` отдаёт сырое в sRGB тремя каналами. Предел пикселей — общий `decodePixelLimit`;
   не JPEG, превышение, сбой декода, каналов не 1 и не 3 → `null` (страница как есть, R24).
2. Белое бумаги по каналам — `rawPaperWhite`: перцентиль `PAPER_WHITE_PERCENTILE` яркости
   внутри обрезки `MARGIN_RATIO` по выборке каждой седьмой строки и колонки.
3. Полосы выходных строк по бюджету `WARP_BAND_PIXELS` 0,5 Мпикс (на 300 dpi A4 — 201 строка,
   18 полос; на 600 dpi — 100 строк, 71 полоса). В полосе: вертикальный сдвиг столбцов
   `y_src = y − (x − xc)·tanθ(y)` (Catmull-Rom по четырём соседям, у кромки — ближайшая строка,
   за кромкой — белое) из входа в новый буфер, затем сдвиг этих же строк на боковой дрейф
   `x_src = x + d(y)`, `d = skewLateralRows(tanθ, k = 1)`, на месте по строке через буфер-строку.
   Порядок проходов обратен спайку (там — сначала дрейф): ошибка перестановки второго
   порядка (≤ 0,2 px на 600 dpi при 0,8°), зато вход не портится и буферов два, а не три.
   Нулевой профиль — выход равен входу байт в байт. После полосы — `onChunk`, проверка
   `AbortSignal` и точка уступки (`setImmediate`).
4. Энкод `jpeg({quality: 92, chromaSubsampling: '4:4:4'})`, серый — `toColourspace('b-w')`
   (`STRAIGHTEN_ENCODING` = `jpeg-q92-444`). Плотность — `withJfifDensity`: APP0 JFIF вставляется
   сразу после SOI (mozjpeg в `sharp` его не пишет) или переписывается в существующем.
   `withMetadata({density})` у `sharp` 0.35 заодно переводит выход в sRGB с профилем ICC —
   серый становится трёхканальным, файл на ~3 КБ тяжелее, — поэтому плотность пишется руками,
   без профиля; сегменты выхода: `e0 db c0 c4 c4` (серый), ICC нет. `dpi: null` — плотность
   из JFIF входа, нет и её — без плотности, `dpi` в результате `null`.

### Производное выравнивания и жизненный цикл (M6, U5–U12)

Код — `src/core/storage/skew-scores.ts` (кэш исходов измерения), `straightened.ts` (выправленные
файлы и записи, `resolve` — единственный путь к файлу, `hold`), `limiter.ts` (две очереди
`normal` / `low`), `src/core/scan/straighten-flow.ts` (факты для статусов, очередь коррекции,
отказ сохранения, снимок и дайджест пакета), `save-flow.ts`, `src/shared/straighten.ts`
(`straightenMarkOf` — одно правило статуса на ядро и renderer, виды картинок). Тесты —
`straighten-flow*.test.ts`, `pass-service.straighten.test.ts`, `straightened*.test.ts`,
эмулятор: `test/integration/straighten*.emulator.test.ts`.

- **Каталоги.** `derived/<сессия>/skew/<ключ>.json` — исход измерения: `{ v: { geometry,
detector }, outcome, profile, contrast, fanMm, reason, source: { bytes } }`; запись с другой
  версией геометрии или детектора не читается — страница измеряется заново.
  `derived/<сессия>/straight/<ключ>.v<геометрия>.d<детектор>.jpg` + `.json` (`{ v, detector,
encoding, dpi, file: { name, bytes } }`; B-19, журнал 0029): один писатель
  (`straightened.store`), порядок — JPEG во временный файл, `fsync`, `rename`, затем запись; сбой
  второй записи убирает JPEG (сирот на полном диске нет). Пары прежнего формата `<ключ>.v<N>.*`
  без детектора (до B-19) читаются как пары с детектором «неизвестен» (`UNKNOWN_DETECTOR = 0`).
  При загрузке читаются пары с геометрией ≤ текущей любого детектора, `resolve` отдаёт пару
  текущих версий, а без неё — самую новую (геометрия, затем детектор); лишние пары ключа и сироты
  убираются; размер файла сверяется с записью — расхождение значит «файла нет». Годна для
  пропуска очереди только пара текущих версий (`isCurrentStraightened`); `store` пишет текущую
  пару рядом и убирает прочие пары ключа по листингу каталога (детекторы прежних пар наперёд не
  известны), под `hold` — после отпускания; `discard` снимает пару страницы, которой вердикт
  текущих версий ставит не «выправлять». Шаблоны чистки `STRAIGHT_FILE` / `STRAIGHT_THUMB_FILE`
  принимают оба формата. Миниатюры выправленных — `straight-thumbs/` под именем самого JPEG;
  адрес картинки несёт вид и обе версии
  (`duplexnt-page://<сессия>/straight-thumb/<геометрия>.<детектор>/<ключ>`), так что откат,
  пересчёт и смена любой версии меняют адрес, а не кэш.
- **Измерение по ходу прохода** (KTD-4): `sink` ставит страницу в кэш оценок без `await`, с
  приоритетом `low` в общем лимитере производного (два декода разом, `DERIVED_CONCURRENCY = 2`);
  приём страницы не ждёт. Скрытые пустые обороты не измеряются до «Это не пустая страница».
  Замер U9 (`straighten-intake-worst-case.test.ts`, `fan-600`, шесть косых 600 dpi серых,
  прямой исполнитель): проход «не трогать» 9,4 с, с выравниванием 9,3 с (×0,99) — коррекция
  всех шести закончилась внутри прохода; паузы цикла max 40 мс, p95 16 мс.
- **Очередь коррекции** — по одной странице, `enqueue` только при исходе «выправлять» с
  профилем, без записи текущей версии и без отсрочки; перед коррекцией проверка места:
  `free − bytes × STRAIGHT_SIZE_RATIO ≥ minFreeBytes`, иначе `deferred: noSpace` (не навсегда —
  повтор при следующем открытии сессии); сбой чтения, `null` от исполнителя, `ENOSPC` на записи
  → `noSpace` / `failed` до конца сессии. `abort()` отменяет текущую задачу сигналом (между
  полосами, до декода и перед кодированием) и очищает очередь; `settle()` дожидается конца —
  закрытие сессии и `will-quit` зовут его, каталог закрытой сессии не пересоздаётся (`alive`
  до и после `await`). Неудавшееся закрытие (`EBUSY`) возобновляет оценки пустоты (B-18),
  измерения и очередь.
- **Уведомления и снимок** (B-16, журнал 0028): на страницу прохода ядро шлёт 2–3 `notify()`
  (приём, вердикт пустоты, вердикт перекоса, исход коррекции; замер — 104 события на 50 лиц,
  154 на 50 оборотов), каждое — `snapshotChanged {seq}` в renderer. Хранилище снимка
  (`snapshot-store.ts`) склеивает: пока запрос в полёте, события поднимают флаг, по ответу —
  один повтор; на 100 страниц 259 → 184 запроса при снимке 0,35 мс и → 82 при 25 мс. Сборка
  снимка — в `getSnapshot` (не в `notify`), кэш сборки по `seq` — кандидат при дорогом снимке.
- **Статус** (`straightenMarkOf`): режим «не трогать», потерянная, пустая → `null`; файл
  известной версии есть → `straightened` / `kept` этой версии **даже без исхода текущих
  версий** (кэш оценок потерян — AE8; версия геометрии сменилась — AE13; найдено U9: иначе
  вчерашняя сессия ждала бы повторного измерения с отказом сохранения); иначе по исходу:
  `unmeasurable` (`measure` / `nohelp`), `level`, `willStraighten` без файла → `deferred` с
  причиной или `pending`. Сводка считает всё, кроме `null`; `pending` — только измерение или
  коррекция в полёте.
- **Сохранение** (KTD-8): отказ `straightenPending` при `pending > 0`; снимок выправленных
  пакета берётся в начале, дайджест — по ключам, версиям и размерам; на время пакета `hold()`
  удерживает прежние версии от удаления (гонка пересчёта под сборкой PDF); `retry` сверяет
  ревизию журнала и дайджест — иначе `batchStale`; файл из снимка пропал между снимком и
  записью — сбой документа `pageUnavailable`, не подмена оригиналом.
- **Смена версии геометрии или детектора** (AE13; B-19, журнал 0029; проверено с подменой
  констант: `straighten-version.emulator.test.ts`, `straighten-detector.emulator.test.ts`): пары
  прежних версий читаются, статусы и адреса — их версий, сохранение идёт прежним файлом без
  отказа; кэш оценок другого детектора не читается, повторное измерение и коррекция фоном пишут
  пару текущих версий и убирают прежнюю (после отпускания `hold`); страница, которой новый
  детектор ставит `level` / `unmeasurable`, теряет пару и следует вердикту; повтор неудавшегося
  пакета после пересчёта — `batchStale` (детектор — в дайджесте). Признак пересчёта — от ядра:
  факт несёт `detector` и `stale` (пара не текущих версий), пометка — `recalc`: `pending`
  (идёт или ждёт), `disk` / `fail` (отложен). Renderer констант версий не знает: порция поздних
  тостов — по `recalc: 'pending'`, отложенные порцию не держат и из неё выходят, тост — когда все
  закончили («Выравнивание пересчитано[ — выровнено ещё N стр.]»), порция из одних отложенных
  молчит; у выправленной с отложенным пересчётом инспектор говорит про прежний вид и причину.
  Первое открытие сессии с парами прежнего формата после обновления — фоновый пересчёт всех
  выправленных страниц и один тост на сессию; вручную чистить `derived/` больше не нужно.
- **Предел метода на пачке** (`fan-pack`, U9): косой текст, таблица, сетка, бедный лист —
  выправлены; фото и одна строка — «не по чему мерить»; две колонки в U9 — честно «не по чему
  мерить» (ловушка не прошла гейт; с детектора v4 — выправляются по половинам, журнал 0026);
  ровная страница — `level`, файла нет, в PDF байт в байт.

### Срок обработки картинки (B-21)

Код — `src/core/image/sharp-image.ts` (`processImage`, `ImageTimeoutError`, `isImageTimeout`);
страж — `test/guards/sharp-entry.test.ts`; тесты — `test/integration/sharp-image.test.ts`,
`image-timeout-paths.test.ts`. План — `docs/plans/2026-11-01-001-fix-b-21-image-timeout-plan.md`,
журнал — [solution 0032](solutions/0032-b-21-image-timeout.md).

- **Один вход.** Каждый вызов `sharp` над страницей пользователя в ядре — декод рабочей серой
  детекторов (`detect/gray.ts`), декод и кодирование выпрямления (`image/straighten.ts`),
  миниатюра (`storage/thumbnails.ts`) — идёт через `processImage`. Импорт `sharp` в `src/` вне
  помощника и пробы окружения (`imaging-probe.ts`) — красный страж, включая `import()` и
  `require()`.
- **Два слоя срока.** Срок libvips `IMAGE_TIMEOUT_SECONDS` 30 с (`timeout({ seconds })`) —
  настоящая отмена: `sharp` проверяет его в колбэке прогресса и прерывает обработку между
  кусками вывода; часы идут от начала обработки, ожидание потока libuv не считается. Срок
  кооперативный: зацикливание внутри одного вызова событий прогресса не даёт. Поэтому есть
  запасной срок приложения `IMAGE_DEADLINE_MS` 35 с — `Promise.race` с таймером: ожидание
  бросается, ячейка лимитера, `merge` и `settleDerived` свободны, а застрявший поток libvips
  остаётся занятым до своего конца или перезапуска (пул libuv общий с файловыми операциями).
  Запасной срок покрывает и чтение заголовка (`metadata()`), которое срок libvips не видит.
- **Предохранитель.** Пока висят две брошенные запасным сроком обработки (`MAX_ABANDONED`),
  помощник сразу отвечает сроком, не трогая `sharp`: два потока пула libuv (по умолчанию их 4)
  остаются файловым операциям, то есть записи файлов пользователя. Без него страница, которая
  зависает всегда, занимала бы новый поток на каждом повторе — миниатюра на каждом запросе
  (ревью кода B-21). Каждый срок — `console.warn` с видом входа и размером.
- **Распознавание.** Срок любого слоя — `ImageTimeoutError`: своя ошибка запасного срока; текст
  `timeout: N% complete` где угодно в сообщении (буфер ошибок libvips общий на процесс — при
  соседних обработках текст бывает не первым); любой отказ не раньше срока libvips по часам
  помощника (текст мог стереться). Помимо класса — по имени ошибки: при переносе обработки в
  поток или процесс (ADR 0008) прототип через `postMessage` не доходит.
- **Исходы по путям.** Пустота — «не пусто», страница в ленте; наклон — «не померить», без
  коррекции; оба — **только в памяти**, кэш не пишется, следующее открытие оценит заново
  (исход «не успели» не свойство страницы). Выпрямление — `null`, очередь откладывает страницу
  со сбоем (в памяти, как раньше); миниатюра — `thumbnailFailed` / `decode`, не кэшируется.
  Ничто не держит `merge`, «Сохранить» и `settleDerived` дольше запасного срока; страница из
  документа не исчезает. Интерфейс не меняется.
- **Нагрузка для теста срока.** Размытие и медиана libvips на 4000×4000 идут за 0,2–0,4 с —
  срок в 1 с их не ловит. Годится несепарабельная свёртка: ядро 121 на 3000×3000 — ~3,9 с без
  срока, отказ за ~1,1 с со сроком 1 с.

## 7. Просвечивание бумаги

На тестовых сканах отчётливо читается зеркальный текст с обратной стороны листа.
Тонкая бумага плюс подсветка насквозь. Для OCR это яд, визуально — грязь.

**Уникальная возможность приложения:** мы сканируем обе стороны одного листа,
то есть точно знаем, что именно просвечивает. Зеркалим оборот по горизонтали,
совмещаем с лицом, вычитаем. Обычные сканеры так не умеют — у них нет пары.

Два уровня:

- **мягкий** — подъём точки белого и гамма-коррекция, убирает бледные следы
- **агрессивный** — вычитание парного изображения; при плохом совмещении
  может съесть настоящий бледный текст, поэтому нужно превью «до/после»

В макете этой настройки пока нет — её нужно добавить в параметры сканирования.

## 8. Хранение профиля сканера

Писать в профиль **UUID и отпечаток сертификата**, а не только IP. SerialNumber в профиль не
входит: в объявлении mDNS его нет, искать по нему нечем (M5).
У тестового устройства: `00000000-0000-4000-8000-000000000000`.

Логика старта: пробуем сохранённый адрес → не ответил → ищем по mDNS
устройство с тем же UUID → нашли → молча обновляем адрес.
Пользователь не замечает смены адреса по DHCP.
Именно отсутствие этого бесит в штатных утилитах.
Реализовано в M5: найденное по UUID подтверждается отпечатком (UUID в TXT открыт — это ключ
поиска, не доказательство); правила и сроки — спека, «Подключение сканера».

**Сертификат:** запоминать отпечаток при первом подключении и сверять потом
(pinning). Разница между «доверяю чему угодно» и «доверяю этому устройству».

**Проверено на ET-3850 2026-10-25 (M5, U1)** — замер скриптом вне git, настоящие значения в
репозиторий не попадают:

- **Смена адреса не меняет сертификат.** Отпечаток SHA-256, SAN и срок действия после смены
  адреса — те же; после перезагрузки на новом адресе — тоже. Самоподписанный сертификат
  выпущен один раз (действует с 2010-01-01 по 2038-01-01, часы при выпуске не были
  выставлены), в SAN четыре записи и среди них **старый** IP — устройство SAN не обновляет. Значит,
  отпечаток доказывает «то же устройство» и на новом адресе, а проверка имени по SAN бесполезна
  (её и нет — сверяется только отпечаток).
- **UUID в TXT mDNS и `scan:UUID` в capabilities совпадают**, в том числе по регистру (нижний).
  Сравнение без учёта регистра остаётся страховкой для других устройств.
- **«Занят» на `GET` не бывает.** Во время печати (два прогона по 60 с, опрос раз в секунду)
  `ScannerCapabilities` и `ScannerStatus` отвечали `200`, состояние — `Processing`. `503` сканер
  даёт только на `POST /ScanJobs` и между страницами (раздел 2). Ожидание «занят» в пробе — страховка
  для других устройств.
- **Два поиска mDNS в одном процессе** (по экземпляру на интерфейс с `reuseAddr`) оба видят сканер
  за 0,1–1,2 с.
- После смены адреса первое объявление пришло за 1,2–2,0 с; `_uscan` и `_uscans` — на одном
  порту 443, иногда первым приходит одно из двух.

**Валидация при подключении:** проверяем наличие `AdfSimplexInputCaps`.
Нет автоподачи — устройство не подходит под сценарий приложения, так и говорим.
Дуплекс не проверяем: приложение делается именно под его отсутствие.

**Capabilities определяют UI.** Списки DPI, цветовых режимов и форматов
строятся из ответа устройства, а не хардкодятся. Иначе на другом железе
кнопки соврут.

## 11. Что уже решено в макете

Макет интерфейса существует отдельно (Claude Design, десктоп 1280×800).
Эти вопросы в нём закрыты — переизобретать не нужно, только реализовать.

### Экраны

`setup` — настройка и запуск · `scan` — процесс прохода ·
`flip` — инструкция по развороту · `merge` — сборка ·
`editor` — проверка и правка · модалки: `device`, `add`, `save`,
`mismatch`, `newscan`.

### Принятые решения

**Подключение сканера** — модалка со списком найденных устройств.
Устройства без автоподачи показаны приглушёнными с подписью «нет автоподачи»
и не выбираются. Ручной ввод адреса всегда на виду, порт/схема/путь —
под «Дополнительно».

**Несовпадение проходов** — модалка сообщает о расхождении и говорит, какой лист
остался без оборота. Документ уже собран по совпавшим парам.

> Пересмотрено после бутстрапа: трёх вариантов действия в модалке больше нет.
> Досканирование идёт обычным «Добавить» — там уже есть «один лист» и «после
> текущей страницы», отдельный механизм не нужен.

**Пустые обороты** — три режима в параметрах: скрывать, помечать, оставлять.
В редакторе есть переключатель показа скрытых и счётчик.
(В приложении с M4: режим — настройка приложения и поле сессии, не параметр устройства и не
capabilities; замораживается при старте первого прохода. Переключатель только показывает —
в файл идут нескрытые ядром страницы, вернуть страницу можно пометкой «Это не пустая
страница». При «Оставлять» детектор не работает; при «Помечать» — метка «ПУСТО», страница в
файле. UI_SPEC §6.9, handoff `docs/design/handoffs/2026-10-m4-states.md`.)

**Редактор страниц** — миниатюры с перетаскиванием, множественное выделение
(shift — диапазон, ctrl — по одной), поворот, удаление, пересканирование
отдельной страницы, крупное превью с навигацией.

**Несколько документов из одной пачки** — границы отмечаются на миниатюрах
кнопкой «Новый документ», каждый блок получает имя, при сохранении
выходит несколько файлов. Есть выбор «один файл / отдельные файлы».

**Правка порядка** — если пользователь двигал страницы, автосортировка
отключается. Любая правка показывает плашку «Есть ручные правки» с кнопкой «Вернуть»
(полный откат; M3 — «Порядок изменён» был бы неправдой после одного поворота).

**Проверка перед сохранением** — панель со сводкой: сколько пар
«лицо + оборот», сколько пустых скрыто, соответствует ли порядок схеме.
(В приложении: пары, пустые обороты и порядок — пункты блока ПРОВЕРКА в инспекторе,
UI_SPEC §6.4; сводка модалки `save` — «Файлов», «Страниц всего» по тем, что уйдут в файл, и
с M4 ряд «Пустых оборотов»: скрыто N / помечено N / не найдено, при «Оставлять» ряда нет —
UI_SPEC §7.3.)

**Новое сканирование** — модалка предупреждает о несохранённых страницах
и предлагает сначала сохранить.

**Добавление скана к документу** — модалка выбора: двусторонняя пачка,
односторонние листы, один лист. Плюс место вставки: в конец или после
текущей страницы. Добавленные страницы помечаются номером прохода.
(В приложении с M3.5 — две карточки без двусторонней и тег по номеру набора «Д1»,
UI_SPEC §6.2 и §7.2.)

### Что в макете нужно поправить

- В блоке «Дополнительно» дефолты неверны: стоит HTTP / порт 80 / `/eSCL`,
  а для ET-3850 нужно HTTPS / 443 / `/eSCL/`. На 80 порту только веб-морда.
- Схема задана текстовым полем, хотя вариантов ровно два — нужен переключатель.
- Разрешения захардкожены (200/300/600). Должны строиться из capabilities.
- Нет настройки подавления просвечивания.
- Нет аварийного переключателя «повернуть обороты на 180°» (раздел 5). В редакторе есть
  только поворот выбранной страницы. Без него неправильно уложенная пачка требует
  пересканирования.
- Анимация разворота (`turn180`) показывает только правильное действие. Ошибочного
  «перевернуть листы» на картинке нет, оно только словами — а это именно тот промах,
  который собирает документ молча и неправильно. Нужна пара «так / не так».
- Цикл `turn180` идёт 0° → 180° → 360°, то есть вторая половина отменяет показанное
  действие, а правильное конечное состояние держится ~0,3 с из 3,8 с. Физическое действие
  делается один раз — анимация должна доигрывать до конца и удерживать результат.
- Анимации бесконечные, без `prefers-reduced-motion` и без управления (пауза, повтор).
  Для инструкции, от которой зависит весь сценарий, нужен статичный кадр-результат.
- На листе в иллюстрации не сказано, что видимая сверху сторона — это обороты.
  Посылка сценария есть только в тексте.
