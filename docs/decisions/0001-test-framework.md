# 0001 — Тесты: vitest и эмулятор сканера на общих фикстурах

## Контекст

Политика тестирования (`docs/duplexnt.md` → «Тестирование») строит покрытие по риску: плотно
— пересчёт региона в 1/300 дюйма, `interleave` и сборка при несовпадении проходов, детектор
пустых оборотов, разбор `capabilities` / `status`, атомарность сохранения PDF; интерфейс —
смоуком. Всё рискованное завязано на устройство, которого в тестах нет. Решено в брейншторме
по стеку (`docs/brainstorms/2026-09-17-stack-requirements.md`, R15–R20), развилок две:

1. **Раннер** — чем гонять тесты TypeScript-кода ([[0002-language]]).
2. **Чем заменять сканер** — только записанные ответы в юнит-тестах или ещё и эмулятор,
   говорящий по настоящему протоколу.

До M0: кода нет, фикстур нет; в техбазе есть проверенные на ET-3850 ответы устройства и
описание протокола.

## Решение

### Раннер — vitest

**`vitest`**, окружение `node` для ядра и `jsdom` для интерфейса, `devDependency` — в
установщик не едет. Ключевой довод — не свойства раннера, а опыт: тот же раннер отработан
автором на Shelfory, и тесты пишет агент — знакомый Jest-подобный API даёт меньше кривых
тестов. `node:test` отклонён: для TypeScript, coverage и моков нужна обвязка, которая съедает
выигрыш «нулевой зависимости».

### Прогоны

- `test` — чистая логика и интерфейс. Не требует сети, сканера и окна.
- `test:integration` — слой с нативной зависимостью (`sharp`) и ядро против эмулятора по
  настоящему HTTP.
- `test:all` — оба; гейт вехи.
- Тесты против **живого устройства** — opt-in по переменной окружения с адресом сканера. Без
  неё пропускаются с предупреждением, прогон остаётся зелёным.

### Эмулятор сканера — с M1

Локальный HTTP-сервер, который отдаёт записанные `ScannerCapabilities` и `ScannerStatus` и
проводит задание по протоколу: `POST /ScanJobs` → `NextDocument` до `404` → `DELETE`.
Сценарии ошибок включаются параметром запуска и добавляются по мере вех: занятость (`503`) —
в M1, недостача и лишний лист во втором проходе — в M2.

Эмулятор и юнит-тесты читают **один набор фикстур** — второго источника правды об ответах
устройства нет. Приложение подключается к эмулятору ручным вводом адреса, как к настоящему
сканеру; особого режима в приложении для него нет. «Только юнит-тесты и живое железо»
отклонено: несовпадение проходов, двойной захват и чужие сканеры на железе воспроизводятся
хуже всего, а интерфейс без эмулятора не смоучится без бумаги.

## Альтернативы

- **`node:test` + `node:assert`** — отклонён: см. выше.
- **Демо-режим внутри приложения вместо эмулятора** — отклонён: это второй путь исполнения в
  продуктовом коде, который нужно поддерживать и который не проверяет клиент сканера.
- **Запись и воспроизведение HTTP-трафика библиотекой-перехватчиком** — отклонён: закрывает
  тесты, но не даёт ручного смоука интерфейса и не воспроизводит чужой сканер по присланному
  XML.

## Последствия

- Эмулятор — код на поддержке и может разойтись с реальным устройством. Де-риск: проверка на
  живом ET-3850 остаётся обязательной частью смоука перед закрытием вехи.
- Конвенция каталога фикстур и канонические ответы ET-3850 заводятся в M0; эмулятор — в M1
  вместе с клиентом сканера.
- Чужой сканер воспроизводится по присланному XML с capabilities: файл кладётся в фикстуры,
  эмулятор отдаёт его.
- Открытый хвост: нужен ли для `test:integration` запуск под electron-as-node. В Shelfory его
  потребовал `better-sqlite3`; здесь базы нет ([[0003-shell-build-delivery]]), а `sharp`
  поставляется N-API-бинарём. Решается фактом в M0.

## Амендмент 2026-09-19 — закрыт хвост про electron-as-node

Открытый хвост из «Последствий» снят фактом M0, в двух частях.

- **`sharp` — electron-as-node не нужен.** Prebuilt N-API ABI-стабилен между Node и Electron:
  один и тот же бинарник прошёл `test:integration` под обычным Node и отработал в main-процессе
  установленного приложения без пересборки. `test:integration` остаётся под обычным Node.
- **TLS — прогон под рантаймом Electron не нужен, пока тест проверяет факт отказа, а не код.**
  Спайк сравнил Node (OpenSSL) и main-процесс Electron (BoringSSL) напрямую: изоляция ослабления
  держится в обоих, но коды ошибок для одного и того же сертификата различаются. Регрессионный
  TLS-тест M1 пишется под обычный Node и утверждает «запрос отклонён». Если он когда-нибудь
  привяжется к конкретному коду ошибки — это повод переписать тест, а не заводить второй рантайм.

Итог: второго рантайма в тестовых прогонах нет. Подробности —
