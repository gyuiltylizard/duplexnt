# 0003 — Оболочка, слои, сборка и поставка: Electron + React + electron-vite

## Контекст

Язык зафиксирован: TypeScript strict ([[0002-language]]). Макет интерфейса — HTML с токенами
в CSS-переменных; `docs/design/UI_SPEC.md` описывает stateful-экраны: множественное
выделение, перетаскивание, границы документов, счётчики. Аудитория — автор и знакомые через
GitHub. Решено в брейншторме по стеку
(`docs/brainstorms/2026-09-17-stack-requirements.md`), развилки:

1. **Оболочка** — Electron, Tauri или нативный UI.
2. **Где живёт ядро** и как с ним говорит интерфейс.
3. **Стек интерфейса и локализация.**
4. **Хранилище.**
5. **Сборка и поставка.**

До M0: кода нет; дизайн-система и спецификация UI извлечены из макета.

## Решение

### Оболочка — Electron

Макет на веб-стеке становится референсом почти напрямую; нативный UI потребовал бы
перерисовать его руками. Ядру нужен доступ к сети мимо ограничений веб-страницы —
самоподписанный TLS, mDNS, — и в Electron это main-процесс на том же языке. Попутно
получается сборка под мак без отдельных усилий; сейчас она не делается и не тестируется.

### Слои

- **Ядро** — клиент сканера, сборка проходов, постобработка, PDF. Лежит слоем **без импортов
  Electron**; нарушение ловит линтер. Это делает ядро тестируемым без окна и оставляет
  открытой консольную утилиту, не делая её продуктом.
- **Main** — тонкая обвязка: окно, мост, файловые диалоги.
- **Мост** — `preload` с `contextIsolation`; интерфейс не обращается к сети, файлам и ядру
  напрямую. Вход моста валидируется на стороне ядра.
- **Интерфейс** — renderer.

Отдельный процесс или воркер для ядра **не заводится**: `sharp` асинхронный, а JPEG
вкладывается в PDF без перекодирования — почти побайтовое копирование. Числа, которое
требует воркера, нет; появится — пересматривается.

### Интерфейс и локализация

React + Vite (TSX). Локализация — `i18next` с первого экрана; плюрализация по правилам локали.
**Русская локаль первая и задаёт раскладку:** русские слова длиннее, и раскладка,
выдержавшая русский, выдержит английский — обратное неверно. Шрифты макета (Golos Text, IBM
Plex Mono) едут в установщике; обращений к внешним хостам за шрифтами нет. Токены
`DESIGN_SYSTEM.md` кодируются один раз как CSS-переменные.

### Сеть

Клиент работает по HTTP и HTTPS; схема, порт и путь — из mDNS или ручного ввода. Проверка
TLS-сертификата ослабляется **только для соединения со сканером**; глобального отключения в
процессе нет. До pinning (пост-MVP) приложение доверяет любому сертификату на адресе сканера
— принято как допустимое для локальной сети.

### Хранилище

Базы данных нет: профиль сканера и настройки — файл с маркером версии. Окончательно — ADR по
модели данных перед M1; этот ADR фиксирует только то, что стек базу не навязывает.

### Сборка и поставка

`electron-vite` — оркестратор трёх процессов; `electron-builder` → установщик NSIS с
деинсталлятором. **Без подписи кода и автообновления:** предупреждение SmartScreen для
аудитории «знакомые и GitHub» терпимо, обновление — новой сборкой. Обе вещи добавляются позже
без переделок.

### Спайк в M0 — exit-критерии и поведение при провале

Де-рискуются три места, все — живым репро на ET-3850, не юнит-тестом:

1. mDNS на чистом JS находит устройство на Windows **без установленного Bonjour** и отдаёт
   TXT-запись с `rs=`.
2. Запрос `ScannerCapabilities` по HTTPS с самоподписанным сертификатом проходит, при этом
   запрос из того же процесса к другому хосту с недействительным сертификатом отклоняется.
3. Собранный установщик ставится на чистую машину и приложение с `sharp` внутри запускается.

При провале: (1) — обнаружение остаётся за ручным вводом адреса, mDNS переносится, ADR
дополняется; (2) и (3) — блокеры, пересматривается сетевой слой или упаковка, итог —
амендмент сюда.

## Альтернативы

- **Tauri** — отклонён: сетевой слой пришлось бы писать на Rust, которого в проекте нет.
- **Нативный UI (Qt и подобные)** — отклонён: макет перерисовывается руками, теряется связь
  токенов с кодом.
- **pywebview поверх Python-ядра** — отклонён вместе с Python ([[0002-language]]).
- **Vanilla или Svelte в renderer** — отклонены: экраны stateful, а React уже отработан
  автором; знакомый стек снижает риск сильнее, чем более лёгкий незнакомый.
- **SQLite** — отклонён до появления числа: хранить нечего, кроме профиля и настроек, а
  нативный модуль усложняет упаковку и тесты.

## Последствия

- Зависимости рантайма: `react`, `react-dom`, `i18next` с привязкой к React, `sharp`,
  XML-парсер, mDNS-библиотека, библиотека PDF. Две последние выбираются позже: mDNS — по
  спайку, PDF — при планировании M2 своим ADR. Требование к PDF уже зафиксировано: JPEG
  вкладывается без перекодирования, поворот на 90° — свойством страницы, библиотека —
  поддерживаемая (оригинальный `pdf-lib` не обновлялся с 2022 года).
- `sharp` — нативная зависимость: остаётся внешней при сборке и распаковывается из asar.
- NSIS под правило «данные священны»: деинсталляция не удаляет пользовательские данные.
- Установщик весит порядка сотни мегабайт — цена Electron, принята.
- Знакомые — это чужие сканеры: «capabilities определяют UI» становится условием
  работоспособности, а мастер калибровки поднимается в приоритете после релиза.
- Детали каркаса — в плане M0.

## Амендмент 2026-09-19 — итоги спайка M0

Все три критерия пройдены живым репро на ET-3850; пересмотра сетевого слоя и упаковки не
требуется. Подробности и способы запуска — в журнале
[0001-m0-scaffold](../solutions/0001-m0-scaffold.md), скрипты — в `spikes/`.

| Критерий                                | Итог   | Чем подтверждён                                                                                      |
| --------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------- |
| 1. mDNS на чистом JS без Bonjour        | прошёл | служба Bonjour остановлена; найдены оба сервиса, в TXT есть `rs`                                     |
| 2. HTTPS с самоподписанным сертификатом | прошёл | Node (OpenSSL) и main-процесс Electron (BoringSSL); чистый проход, без ослабления протокола и шифров |
| 3. Установщик на чистой машине          | прошёл | Windows Sandbox, прогон автора; проба `sharp` зелёная, данные переживают деинсталляцию               |

### Что уточняется в решении

- **Библиотека mDNS — `bonjour-service`** (поверх `multicast-dns`). Проверена небандленной; как
  она ведёт себя внутри бандла main, выяснит M1. Два условия работы на Windows — часть решения,
  а не деталь реализации: `reuseAddr` обязателен (порт 5353 делят служба Bonjour, DNS-клиент
  системы и сторонние приложения), а обнаружение идёт **перебором внешних IPv4-интерфейсов** —
  по экземпляру на интерфейс. Без перебора один прогон из нескольких вернул пустой результат без
  единой ошибки; причина не установлена, перебор таких прогонов не дал ни разу.
- **Раздел «Сеть», фраза «схема, порт и путь — из mDNS».** ET-3850 объявляет на порту 443 **оба**
  сервиса, `_uscan._tcp` и `_uscans._tcp`, а по нешифрованному HTTP eSCL отвечает 404. Схему
  нельзя выводить из типа сервиса: клиент пробует HTTPS первым, и для этого устройства HTTPS —
  единственный транспорт. Ключи TXT сравниваются без учёта регистра: прошивка отдаёт `UUID` и
  `usb_MFG` с прописными, остальное строчными.
- **Ослабление TLS — выделенный `https.Agent` на профиль сканера**, приватный модулю транспорта.
  Проверено в обоих рантаймах: после успешного запроса к сканеру тот же процесс отклоняет и
  посторонний хост с плохим сертификатом, и сам сканер — через агент по умолчанию, глобальный
  `fetch` и сетевой стек Chromium. Коды отказа у Node и Electron для одного сертификата разные,
  поэтому клиент опирается на факт отказа проверки, а не на код. Остальные инварианты агента
  (привязка к origin, запрет авторедиректов, `Location` как данные) записаны в плане M0 и
  реализуются в M1; глобальные механизмы ослабления уже запрещены линтером по всему `src/`.
- **Размещение зависимостей — критерий механический:** нативное и небандлящееся — в
  `dependencies` (сейчас только `sharp`), чистый JS — в `devDependencies`, его бандлит Vite. Список
  «зависимости рантайма» в «Последствиях» читается с этой поправкой: React, i18next, XML-парсер,
  mDNS- и PDF-библиотеки едут в бандле, а не в `node_modules` установщика.
- **Упаковка:** состав установщика — белый список (`out/**` и `package.json`): по умолчанию
  `electron-builder` пакует весь каталог проекта и `.gitignore` не читает. `sharp` и `@img/*`
  распаковываются из asar явными паттернами; `npmRebuild` выключен — prebuilt N-API пересборки не
  требует.

### Наблюдения, не меняющие решения

- Отклонённый запрос файрвола Windows **не сломал** обнаружение: при блокирующих входящих правилах
  для exe приложения сканер находился в трёх прогонах из трёх. Причина не установлена; гипотеза —
  порт 5353 общий, и multicast-ответ проходит по правилу другого слушателя. Полагаться на это
  нельзя: на машине без других слушателей 5353 поведение может быть иным. Windows создаёт правило
  в момент показа запроса, блокирующее, и меняет его на разрешающее по ответу пользователя.
- Установленное приложение и отладочный запуск делят один каталог данных — имя берётся из `name`
  в `package.json`. Вход для ADR по модели данных перед M1.

## Амендмент 2026-10-02 — отпечаток сертификата сканера с M1

Раздел «Сеть» принимал доверие любому сертификату на адресе сканера до pinning в пост-MVP.
Проверка безопасности плана M1 (`docs/plans/2026-10-02-001-feat-m1-connect-single-pass-plan.md`)
показала, чего это стоит: устройство в локальной сети, подменившее адрес сканера, читает все
сканы и кормит своими ответами разбор в main-процессе, а UUID из mDNS защитой не служит — он
объявляется в сеть открыто. Решение автора при планировании M1:

- **Отпечаток запоминается при подключении и сверяется перед каждым заданием.** SHA-256
  сертификата записывается в профиль сканера и в запись прохода. Первое подключение остаётся на
  доверии: пользователь сам выбрал устройство в модалке.
- **Несовпадение — состояние «по адресу другое устройство».** Задание не начинается; повторное
  подключение в модалке запоминает новый отпечаток. Нового интерфейса нет.
- **Сверка — явный шаг модуля транспорта.** При ослабленной проверке Node не вызывает собственную
  проверку идентичности сервера, поэтому сравнение делает клиент на каждом новом соединении.
- **Переход на HTTP не обходит сверку молча:** он возможен только при интерактивном подключении
  без явной схемы, выбранная схема записывается в профиль и видна в интерфейсе.

В пост-MVP остаётся показ отпечатка пользователю и управление доверенными устройствами.

## Амендмент 2026-10-03 — причина пустого прогона mDNS уточнена замером

Амендмент «итоги спайка M0» приписал пустой прогон обнаружения отсутствию перебора
интерфейсов («перебор таких прогонов не дал ни разу»). Замер сессии 4 M1 на устройстве
(56 прогонов сырой библиотекой, 130 продуктовым кодом; журнал
[0002-m1-connect-single-pass](../solutions/0002-m1-connect-single-pass.md) → «Что показал
замер на устройстве») показал другую причину: **ET-3850 часто не отвечает на первый запрос**
— при прогонах вплотную почти всегда, в спокойном ритме в 7 из 24; изредка устройство молчит
несколько секунд при нескольких отправленных запросах. Перебор интерфейсов остаётся условием
работы (порт 5353 общий), но пустые прогоны лечит не он, а **повтор запроса** в течение
поиска. При поиске до 20 с сканер найден в 60 прогонах из 60; текст «ничего не нашлось»
через 10 с при идущем поиске (KTD-14) с этим согласуется.

## Амендмент 2026-11-02 — смена устройства подтверждает пользователь

Амендмент 2026-10-02 решил: «повторное подключение в модалке запоминает новый отпечаток. Нового
интерфейса нет». Решение автора при планировании B-29
(`docs/plans/2026-11-02-001-fix-b-29-shell-hardening-plan.md`) отменяет это место: подключение
устройства, которое не доказано тем же, что запомнено, не меняет профиль до подтверждения. Переход с
отпечатка на HTTP тоже считается сменой. Первое подключение остаётся на доверии, переезд по mDNS сверяет
транспорт. Показ отпечатка и управление доверенными устройствами остаются в пост-MVP.
