# CLAUDE.md — Duplexn't

Общайся на русском, неформально, на ты.

Источник правды по проекту и правилам — **`docs/duplexnt.md`**. Протокол eSCL,
возможности ET-3850 и всё проверенное на железе — **`docs/duplexnt-tech.md`**.
Перед архитектурными изменениями прочитай его целиком; раздел
«Правила и конвенции разработки» — операционные правила. Этот файл держит
только критичный минимум, который соблюдается всегда — даже без чтения спеки.

## Неизменные правила

- **Данные пользователя священны.** Запись в пользовательские файлы — только
  атомарно (temp → `fsync` → `rename`), с валидацией структуры до и после.
  Никаких деструктивных операций над файлами без явного подтверждения.
  Отсканированное не теряется: сбой второго прохода не трогает первый.
  Никогда не выбрасывать страницы молча (пустые обороты, лишний лист) — только предлагать.
  Транспорт — только eSCL по сети; WIA/TWAIN и поддержку дуплекса не добавлять.
- **<не определено: что durable, что derived — ADR по модели данных перед M1>.**
  Ничего невосстановимого в производном; восстановление идемпотентно (без дублей).
- **Граница слоёв:** UI не ходит к сканеру, сети и файлам напрямую — только через
  `preload`-мост, вход валидируется в ядре. Слой ядра не импортирует Electron — это ловит
  `lint`. Проверка TLS ослабляется только для соединения со сканером, глобально — никогда.
- **Один путь исполнения:** настоящий сканер, эмулятор и тесты ходят через один клиент;
  демо-режима в приложении нет.
- **UI строится из capabilities устройства**, а не из хардкода (DPI, режимы, форматы).
  Регион сканирования — всегда в 1/300 дюйма, пересчёт — одной функцией под тестом.
- **UI — по дизайн-системе:** следовать `docs/design/DESIGN_SYSTEM.md` и
  `docs/design/UI_SPEC.md`. **Новый UI — сначала мок и handoff**
  (`docs/design/`), реализация — по утверждённому handoff'у.
- **Готово =** typecheck + lint + format:check + тесты зелёные, смоук пройден,
  решение в `docs/solutions/`, изменения закоммичены. Форматирование — prettier:
  pre-commit hook правит застейдженное сам; `npm run format` — вручную по всему репо.
- **Git:** WIP-коммит перед сменой ветки; не переносить работу между ветками
  через `git stash`; никогда `git stash drop` без проверки восстановления.
  Коммит шага вехи несёт U-ID в теме (`feat(m4): U5 …`) — чтобы возобновление
  в новой сессии было точным.
- **Закрытие вехи:** веха зелёная (typecheck+lint+test:all) и доки-хвосты долиты
  в ту же ветку → **не вливать молча**: затребовать ручной смоук и приёмку у
  пользователя; merge `feat/<веха>` → `main` — только после явного ОК (детали —
  спека, «Закрытие вехи»).
- Крупные рефакторинги и смена архитектуры — только после обсуждения.
- **ADR в момент принятия.** Принял архитектурную развилку (часто — отвечая на
  вопрос агента) → сразу ADR в `docs/decisions/`, прежде чем двигаться дальше.
  Порог: только развилка, которая (а) впечатывается в архитектуру и (б) дорого
  переигрывается потом — стек / язык / ключевая библиотека / схема данных.
  Рутинные шаги и решённые баги — не ADR (баги → `docs/solutions/`). Нет
  развилок — ADR не пишем.

## Процесс

Планы → `docs/plans/`, бэклог → `docs/backlog.md` (раздел «Входящие»), баги →
`docs/bugs.md`, решения → `docs/solutions/`. Полный пайплайн — в спеке.

**Шаблоны доков — в `docs/templates/`.** Новый ADR → по `docs/templates/adr.md`;
новый solution-журнал → по `docs/templates/solution.md`; брейншторм / план / бриф /
handoff / смоук-чеклист — там же. Открывать шаблон, а не копировать формат «на глаз»
из предыдущих файлов.

**Крупные планы (не влезающие в одно контекстное окно) идут по сессиям** —
нарезаны на сессии (секция `## План по сессиям` в плане; небольшие планы не
нарезаются). Начиная работу над таким планом — определить позицию: `git log`
(U-ID в теме последнего коммита вехи) + solution-журнал вехи;
**сориентировать пользователя на стадию** (какая сессия/фаза, что закрыто, что дальше)
и лишь затем продолжать. В конце сессии — зелёный коммит на границе юнита (с
U-ID), **дописать solution-журнал и явно сказать, на чём встали**. Детали —
спека → «Процесс» → «Сессионная нарезка крупного плана».
